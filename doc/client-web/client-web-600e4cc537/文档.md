# 构建 client/web Docker 镜像与运行配置：需求梳理

## 1. 任务目标

为 `client/web`（Next.js 14.1.3 管理控制台）提供可在任意 Docker 环境独立构建、独立运行的生产镜像配置。镜像构建不得读取或复制宿主机的 `node_modules`，并能通过容器环境变量配置 API 代理目标。

本阶段仅完成需求梳理；不在本次修改 Docker 配置或业务代码。

## 3. 需交付的内容

后续实施阶段应完成以下文件和配置调整：

1. 新建 `client/web/Dockerfile`，作为本地、CI 和标准 `docker build` 的唯一入口。
2. 新建 `client/web/.dockerignore`，确保构建上下文不包含宿主依赖、已有构建产物、密钥和无关交付文件。
3. 处理现有 `client/web/.obelisk/custom/docker/Dockerfile`：不得继续保留旧的单阶段 `npm install` 方案。应使其与根 Dockerfile 使用同一套多阶段构建语义；若 Obelisk 支持指定 Dockerfile 路径，则改为使用根 Dockerfile，避免两份配置漂移。
4. 调整 `client/web/next.config.mjs` 的环境变量暴露方式，使 API 代理变量可以在**容器启动时**注入，且不得将服务端敏感变量暴露到浏览器构建产物。
5. 如当前环境文件没有可公开复用的变量说明，新增脱敏的 `client/web/.env.example`（或在现有部署说明中补充同等内容），仅包含变量名、示例值和用途，不提交真实地址、令牌或密钥。

## 4. Docker 构建设计要求

### 4.1 构建上下文与包管理器

- Docker 构建上下文固定为 `client/web`，示例：`docker build -t universe-client-web:local client/web`。
- 以 `package-lock.json` 为 Docker 构建的唯一依赖锁定依据，使用 `npm ci`，不使用会改写锁文件的 `npm install`。
- Node 基础镜像使用 Node 20 LTS 的固定 Debian 系列标签（例如 `node:20-bookworm-slim`）；选择 Debian 系列以降低 `sharp` 等原生依赖在 Alpine/musl 环境中的兼容风险。
- 不要求删除 `pnpm-lock.yaml`；本任务只需保证 Docker 路径使用 npm 且可复现。若后续统一包管理器，应另立任务同步两个锁文件和本地脚本。

### 4.2 多阶段镜像

Dockerfile 至少分为依赖/构建/运行三个职责清晰的阶段：

1. **依赖阶段**：仅复制 `package.json`、`package-lock.json`，执行 `npm ci`。该层应最大化利用 Docker 缓存。
2. **构建阶段**：复制依赖阶段安装出的依赖与应用源码，设置 `NEXT_TELEMETRY_DISABLED=1`，执行 `npm run build`，生成 `.next` 生产产物。
3. **运行阶段**：仅复制运行所需的 `.next`、`public`（存在时）、`package.json`、`next.config.mjs`（Next 启动仍会加载配置）以及由镜像内部依赖阶段生成的运行依赖；不得从宿主机复制 `node_modules` 或 `.next`。

运行阶段的额外要求：

- 使用非 root 用户运行 Node 进程。
- 设置 `NODE_ENV=production`、`NEXT_TELEMETRY_DISABLED=1`、默认 `PORT=7893`、`HOSTNAME=0.0.0.0`。
- 声明 `EXPOSE 7893`。
- 以 `npm run start` 或等效的 `next start -p "$PORT"` 前台启动，作为容器主进程；不使用 PM2、`nohup`、`start.sh` 或后台运行方式。
- 不启用 `next.config.mjs` 的 `output: 'standalone'` 作为本任务的前置条件，避免改变现有 `next start` 启动语义。后续若要优化镜像体积，可单独评估 standalone 产物和 API 代理依赖追踪。

## 5. `.dockerignore` 要求

至少排除以下内容：

- `node_modules`、`.next`、`coverage`、`*.tsbuildinfo`；
- `.git`、`.gitignore`、编辑器与系统垃圾文件；
- `.env`、`.env.*`（但保留 `.env.example`，如果该文件被新增）；
- `*.log`、npm/pnpm/yarn 调试日志；
- 本地打包产物，如 `package/`、`*.tar.gz`、`*.tgz`；
- 无需参与镜像构建的 Obelisk 本地构建目录和临时文件。

忽略规则不得排除运行必需的源码、`package.json`、`package-lock.json`、`next.config.mjs`、`public/`（若存在）或 `.env.example`。

## 6. 运行环境变量约定

| 变量 | 注入时机 | 是否公开给浏览器 | 必填 | 说明与示例 |
| --- | --- | --- | --- | --- |
| `SERVER_TARGET` | 容器运行时 | 否 | 是 | API 代理上游服务根地址，例如 `http://server-web-api:10001` |
| `APP_URL_PREFIX` | 容器运行时 | 否 | 是 | 将 `/api` 替换为的上游路径前缀，例如 `/api`；按实际网关路由配置 |
| `PORT` | 容器运行时 | 否 | 否 | Next 监听端口，默认 `7893`；若覆盖，Docker 端口映射须同步 |
| `HOSTNAME` | 镜像默认值/运行时可覆盖 | 否 | 否 | 默认 `0.0.0.0`，确保容器端口可被访问 |
| `NEXT_PUBLIC_LOCALE_PREFIX` | 镜像构建时 | 是 | 否 | 现有前端公开变量；若环境不同导致客户端表现不同，必须通过 Docker `--build-arg`/CI 构建环境注入并生成对应镜像 |
| `JWT_SECRET` | 不应由本控制台容器声明或注入 | 否 | 否 | 当前仅在 `next.config.mjs` 中映射，未发现业务使用。实现时应移除该映射，避免误打包进前端；若后续确有服务端用途，再以运行期私有变量恢复并补充使用点 |

### 关键实现约束

- 必须从 `next.config.mjs` 的 `env` 配置中移除 `SERVER_TARGET`、`APP_URL_PREFIX` 和 `JWT_SECRET`。Next 的 `env` 会在构建期间内联变量，既无法满足同一镜像按运行环境配置代理的目标，也存在暴露敏感信息的风险。
- API 代理路由继续通过 Node 运行时的 `process.env.SERVER_TARGET` 与 `process.env.APP_URL_PREFIX` 读取变量；容器启动命令或编排平台负责注入。
- 应在代理入口对缺失的必填变量进行清晰失败处理（启动期校验优先；若受现有路由结构限制，至少在首个代理请求时返回明确配置错误），不得向 `undefined` 目标转发。
- Docker 构建不得复制真实 `.env` / `.env.dev`。真实值通过容器编排、CI 密钥或 `docker run -e` 提供。

## 7. 使用与验收标准

### 7.1 构建验收

在仓库根目录执行：

```sh
docker build -t universe-client-web:local client/web
```

验收：命令成功，日志中依赖安装使用 `npm ci`，`npm run build` 成功；即使宿主 `client/web/node_modules` 已删除或内容不完整，构建仍成功。

### 7.2 运行验收

```sh
docker run --rm -p 7893:7893 \
  -e SERVER_TARGET=http://host.docker.internal:10001 \
  -e APP_URL_PREFIX=/api \
  universe-client-web:local
```

验收：

- 容器以前台 Node 进程持续运行，且进程用户不是 root；
- 访问 `http://localhost:7893` 返回 Next 页面；
- 通过 `/api/*` 访问时，代理使用运行命令传入的 `SERVER_TARGET` 和 `APP_URL_PREFIX`；
- 不传 `SERVER_TARGET` 或 `APP_URL_PREFIX` 时，产生可定位的配置错误；
- 使用 `docker image inspect` 和容器内文件检查确认不存在从宿主复制的 `node_modules`、`.next`、真实 `.env` 文件；依赖和 `.next` 均由镜像阶段产生。

### 7.3 配置一致性验收

- 根 Dockerfile 与 Obelisk 实际构建入口不产生不同的运行端口、包管理器或单阶段构建行为。
- `.env.example` 不包含真实凭据，且准确列出 `SERVER_TARGET`、`APP_URL_PREFIX`、`PORT` 与公开构建变量的约定。
- 修改后运行工程已有可用的构建验证命令（至少 `npm run build`）；若项目的 `lint` 脚本在 Next 14.1.3 下不可用，应记录为既有兼容性问题，不在本任务内扩展修复。

## 8. 非目标

- 不引入 docker-compose、Kubernetes 清单、镜像发布流水线或反向代理配置。
- 不迁移到 standalone output、不重构 Next API 代理、不调整业务路由。
- 不删除现有 `pnpm` 本地部署脚本，也不处理与 Docker 无关的发布包脚本。

## 9. 实施风险与决策记录

1. 当前 `next.config.mjs` 将服务端代理变量放进 Next `env`，会导致构建期固化；这是本任务中必须纠正的运行配置问题。
2. 现有 Obelisk Dockerfile 使用私有基础镜像、`npm install`、root 用户和单阶段 `COPY . .`，不符合本任务的可复现与隔离要求，后续不能保留为有效生产路径。
3. 参考项目没有 Docker 配置，不能直接复制；本方案以当前工程实际端口 `7893`、现有 `npm` 锁文件和 API 代理实现为准。
4. `next-plugin-antd-less` 位于 `devDependencies` 且由 `next.config.mjs` 导入。实施时运行阶段必须验证 `next start` 是否需要该模块；在未将其调整为生产依赖前，优先从镜像依赖阶段复制完整 `node_modules`，而非简单执行 `npm ci --omit=dev` 后启动，以保证现有配置可运行。镜像瘦身应在该行为验证后单独优化。
