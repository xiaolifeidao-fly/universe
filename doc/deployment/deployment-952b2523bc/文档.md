# 搭建 client/web Docker 镜像与构建脚本：需求梳理

## 1. 任务目标

为 `client/web` 建立可复现、可部署的生产 Docker 镜像能力，使部署编排能够以 `client/web` 为独立构建上下文完成依赖安装、Next.js 生产构建和容器启动。镜像必须以前台单进程方式提供 Web 服务，并允许在容器启动时配置后端代理目标，而不是把部署环境地址或秘密固化进镜像层。

本任务实施范围限定为前端容器化相关文件：`Dockerfile`、`.dockerignore`、Next.js 生产输出配置，以及确有必要的容器构建/启动脚本或 `package.json` 命令调整。不修改页面、接口契约、业务逻辑、设计样式或后端代码。

## 2. 当前工程核查结论（2026-08-14）

| 项目 | 当前事实 | 对实施的要求 |
| --- | --- | --- |
| 应用形态 | `client/web` 是 Next.js 14.1.3、React 18、TypeScript 应用，同时包含 App Router 页面和 Pages Router API 代理。 | 不能按纯静态站点部署，生产镜像必须保留 Node.js 服务端运行时。 |
| 构建与启动命令 | `package.json` 提供 `npm run build` 与 `npm run start`；`start` 实际执行 `next start -p 7893`。 | 容器统一监听 `7893`，并显式绑定 `0.0.0.0`；不能沿用 `stop.sh` 的 `7892` 或 `package.sh` 的 `9801`。 |
| 依赖锁文件 | 同时存在 `package-lock.json` 与 `pnpm-lock.yaml`；现有开发脚本和发布脚本使用 npm，`package-lock.json` 为 lockfile v3。 | Docker 构建选择 npm 作为唯一安装链路，使用 `npm ci` 保证锁定依赖；不在同一镜像流程中混用 pnpm。 |
| 本地生产构建 | 在当前工作区执行 `npm run build` 成功，生成 9 个 App Router 路由和 2 个动态 API 路由。 | 现有源码具备生产构建基础；Docker 实施不得用跳过类型检查或忽略构建失败来规避问题。 |
| 代理运行时 | `src/pages/api/[...all].js` 与 `src/pages/api/file/[...all].js` 在模块加载时读取 `SERVER_TARGET`、`APP_URL_PREFIX`。 | 这两个变量必须可在 `docker run`/Compose 启动时注入，并对同一镜像的不同部署环境生效。 |
| 配置固化风险 | `next.config.mjs` 的 `env` 块目前声明 `JWT_SECRET`、`SERVER_TARGET`、`APP_URL_PREFIX`，Next.js 会在构建时替换这些值。 | 实施时应移除这些服务端变量的 `env` 内联配置；尤其不得以 Docker `ARG` 或构建期 `.env` 固化代理地址和 `JWT_SECRET`。 |
| 本地环境文件 | `.env` 含本机后端地址和固定 `JWT_SECRET`，`.env.dev` 也属于开发配置。 | `.dockerignore` 默认排除 `.env*`，不得把这些文件复制进镜像；如后续新增脱敏示例，可仅显式允许 `.env.example`。 |
| 现有发布脚本 | `package.sh` 会先构建，再打包 `.next`、配置和启动脚本；包内首次启动执行 `npm ci --omit=dev`。`start.sh` 使用 `nohup`，`stop.sh` 通过端口杀进程。 | 可参考其“锁文件安装、构建、仅携带运行产物”的组织思路，但容器内不得使用 `nohup`、PID 文件、端口扫描或 stop 脚本管理生命周期。 |
| 上下文体积 | 当前 `node_modules` 约 1.7 GB，`.next` 约 697 MB。 | `.dockerignore` 必须排除依赖、构建缓存和发布包，否则构建上下文不可接受且可能污染镜像。 |
| Docker 环境 | 本机可用 Docker CLI 28.3.2 与 Docker Compose v2.38.2；本阶段未创建 Dockerfile。 | 实施阶段可直接执行真实镜像构建和容器启动验证；本阶段只记录验证命令和预期。 |

## 4. 目标构建上下文与产物

### 4.1 构建上下文

- Docker 构建上下文固定为 `client/web`。
- Dockerfile 默认路径为 `client/web/Dockerfile`。
- 后续 Compose 应使用等价配置：

```yaml
build:
  context: ./client/web
  dockerfile: Dockerfile
```

- Dockerfile 不得依赖上下文外的仓库文件，避免通过 `../` 或根目录上下文扩大传输范围。

### 4.2 镜像结构

采用多阶段构建，至少区分：

1. **依赖阶段**：只复制 `package.json` 与 `package-lock.json`，执行 `npm ci`，利用 Docker layer cache。
2. **构建阶段**：复制源码和必要配置，执行 `npm run build`。
3. **运行阶段**：只包含生产运行所需的 Next.js 产物、`public` 资源及最小 Node.js 运行环境，不携带源码开发缓存和完整构建工具链。

优先将 Next.js 配置为 `output: "standalone"`，运行阶段复制：

- `.next/standalone`
- `.next/static`
- `public`（目录存在时）

并以 `node server.js` 启动。这样可以由 Next.js output tracing 生成最小运行依赖，避免在最终镜像重复执行 `npm install` 或复制完整 `node_modules`。

若实施中确认 `next-plugin-antd-less` 与 standalone 输出存在不可解决的兼容问题，才允许退回 `next start` + 生产依赖方案，并在实现记录中说明原因和镜像体积差异；不得未经验证直接采用完整开发依赖作为运行镜像。

### 4.3 基础镜像与原生依赖

- 使用公开、可复现的官方 Node LTS 镜像，并固定到明确的大版本；建议 Node 20 LTS，与项目 `@types/node` 20 保持一致。
- 可选择 Debian slim 或 Alpine，但必须实际验证 `sharp` 在目标镜像和目标架构可安装、可加载；若 Alpine 需要额外兼容包，应在 Dockerfile 中显式安装。
- 镜像构建不得依赖公司内网私有基础镜像、宿主机已存在的 `node_modules` 或本地全局 npm 包。
- 构建应设置 `NEXT_TELEMETRY_DISABLED=1`，避免 CI 和容器运行发送 Next.js telemetry。

## 5. 运行方式与端口约定

### 5.1 容器进程

- 容器主进程必须以前台方式运行，使用 exec-form `CMD`/`ENTRYPOINT`，正确接收 SIGTERM/SIGINT。
- 禁止在容器内调用现有 `start.sh`、`stop.sh`、`package.sh`、`unpack-release.sh`，也禁止使用 PM2、`nohup`、PID 文件或 `lsof` 管理进程。
- 容器退出码应直接反映 Node/Next.js 进程结果。

### 5.2 端口与监听地址

统一约定：

| 配置 | 默认值 | 说明 |
| --- | --- | --- |
| `PORT` | `7893` | Next.js 容器监听端口；与 `package.json` 当前 dev/start 端口一致。 |
| `HOSTNAME` | `0.0.0.0` | 必须监听全部容器网卡，不能只绑定 localhost。 |
| `EXPOSE` | `7893` | 仅声明容器端口，不等于宿主端口发布。 |

standalone `server.js` 应直接读取 `PORT` 和 `HOSTNAME`。Compose 默认把宿主 `CLIENT_WEB_PORT` 映射到容器 `7893`，但镜像本身不硬编码宿主端口。

### 5.3 非 root 运行

最终运行阶段应创建或复用非 root 用户，并保证 standalone 文件、静态资源及必要的 Next.js 缓存目录可读写。容器启动后 `ps` 中 Web 主进程不应以 root 身份运行。

## 6. 环境变量约定

### 6.1 运行时变量

| 变量 | 必需性 | 默认/示例 | 作用与约束 |
| --- | --- | --- | --- |
| `SERVER_TARGET` | 部署时必填 | `http://web-api:10001` | Next API 代理的后端地址；容器环境必须使用 Compose 服务名或可解析内部地址，不能使用 `127.0.0.1`/`localhost` 指代后端。 |
| `APP_URL_PREFIX` | 可设默认 | `/api` | `/api/*` 转发到后端时使用的路径前缀；必须与 `web-api` 路由前缀一致。 |
| `PORT` | 可选 | `7893` | Next.js 监听端口。 |
| `HOSTNAME` | 可选 | `0.0.0.0` | Next.js 监听地址。 |
| `NODE_ENV` | 固定 | `production` | 最终镜像运行模式。 |
| `NEXT_TELEMETRY_DISABLED` | 固定 | `1` | 禁用 telemetry。 |

### 6.2 构建期与敏感配置

- `SERVER_TARGET`、`APP_URL_PREFIX` 不得声明为 Docker `ARG`，以免产生“每个环境重建镜像”的耦合。
- `JWT_SECRET` 当前没有被 `client/web/src` 业务代码直接读取，只出现在 `next.config.mjs` 的 `env` 块和本地 `.env`；本任务应从内联配置中移除，不将其纳入镜像接口。
- `NEXT_PUBLIC_*` 变量若未来确实用于浏览器 bundle，天然属于构建期配置；本任务不新增此类变量，也不把服务端代理地址改成 `NEXT_PUBLIC_*`。
- 不将任何真实秘密写入 Dockerfile、构建参数、镜像 label、镜像层或提交到仓库的环境文件。

### 6.3 运行时生效验证

必须验证同一个镜像在不重建的情况下，通过不同 `SERVER_TARGET` 值产生不同代理行为。最低验证方式：先以无效目标启动，确认 `/api/healthz` 返回可定位的代理失败；再用可访问的后端地址重启同一 image ID，确认代理成功。此验证用于证明变量未在 `next build` 时固化。

## 7. `.dockerignore` 要求

`client/web/.dockerignore` 至少排除：

```text

.next
package
*.tar.gz
*.tgz
*.log
*.pid
.env
.env.*
.git
.gitignore
.DS_Store
tsconfig.tsbuildinfo
coverage
.nyc_output
```

同时考虑排除编辑器目录、测试缓存和临时文件。若存在需要进入构建上下文的脱敏环境示例，应在排除 `.env.*` 后使用 `!.env.example` 精确放行。

验收重点：

1. 宿主的 1.7 GB `node_modules` 与 697 MB `.next` 不进入 Docker build context。
2. 本地 `.env`、`.env.dev`、日志、PID、离线发布包不进入镜像层。
3. `public`、`src`、`package.json`、`package-lock.json`、`next.config.mjs`、TypeScript/PostCSS 配置等生产构建必需文件仍可复制。

## 8. 必要文件调整范围

实施阶段预期修改如下：

| 文件 | 预期动作 | 目的 |
| --- | --- | --- |
| `client/web/Dockerfile` | 新增 | 多阶段安装、构建、最小运行镜像、非 root 用户、端口和前台启动。 |
| `client/web/.dockerignore` | 新增 | 排除依赖、构建缓存、本地环境、日志和发布包。 |
| `client/web/next.config.mjs` | 调整 | 开启 standalone 输出；移除会固化服务端代理变量/秘密的 `env` 配置。 |
| `client/web/package.json` | 视实现最小调整 | 如需让本地与容器启动命令统一支持 `HOSTNAME`/`PORT`，可调整 `start`；不得无关升级依赖。 |
| `client/web/docker-build.sh` | 可选新增 | 仅在项目需要独立镜像构建入口时提供，负责从脚本目录调用 `docker build` 并支持镜像标签参数。 |

若新增构建脚本，要求：

- 使用 `#!/usr/bin/env bash` 与 `set -euo pipefail`。
- 无论调用者当前目录为何，都以脚本所在的 `client/web` 作为构建上下文。
- 镜像名默认具有项目语义，例如 `universe-client-web:local`，并允许通过位置参数或环境变量覆盖。
- 不在脚本中注入代理地址、JWT 或其他秘密，不自动启动容器，不调用 `sudo`。

现有裸机发布脚本可保留以兼容旧流程，但 Dockerfile/Compose 不依赖它们。本任务不要求顺带重构或删除这些脚本。

## 9. 验收标准与验证步骤

### 9.1 静态检查

在仓库根目录执行：

```bash
# 确认构建上下文规则存在且未放行本地依赖/环境文件。
sed -n '1,240p' client/web/.dockerignore

# 确认服务端运行变量不再由 next.config.mjs 构建期内联。
rg -n 'SERVER_TARGET|APP_URL_PREFIX|JWT_SECRET|output' client/web/next.config.mjs

# 检查 Dockerfile 基本入口。
docker build --check -f client/web/Dockerfile client/web
```

验收：Dockerfile 语法检查通过；standalone 已配置；`next.config.mjs` 不再通过 `env` 暴露上述服务端变量；`.dockerignore` 包含所有强制排除项。

### 9.2 镜像构建

```bash
docker build \
  --progress=plain \
  -t universe-client-web:local \
  -f client/web/Dockerfile \
  client/web
```

或使用实施阶段新增的等价构建脚本。

验收：

1. 从干净 Docker cache 也能仅凭 `client/web` 上下文成功构建。
2. 依赖安装使用 `npm ci`，锁文件与 `package.json` 不一致时明确失败。
3. 构建日志包含成功的 `next build`，不复制宿主 `node_modules`、`.next`、`.env*`。
4. 最终镜像不包含完整源码、开发依赖和构建缓存；可用 `docker history`/临时容器抽查。

### 9.3 容器启动与首页

```bash
docker run --rm -d \
  --name universe-client-web \
  -p 7893:7893 \
  -e SERVER_TARGET=http://host.docker.internal:10001 \
  -e APP_URL_PREFIX=/api \
  universe-client-web:local

curl -fsS http://127.0.0.1:7893/ >/dev/null
docker logs universe-client-web
docker inspect universe-client-web --format '{{.Config.User}} {{.State.Status}}'
docker stop universe-client-web
```

验收：容器保持运行，首页返回 2xx，日志显示生产服务监听 `0.0.0.0:7893`，主进程为 Node/Next.js 且非 root；`docker stop` 可正常终止，无 PID 文件或后台残留进程。

### 9.4 代理与运行时变量

在可访问 `web-api` 的 Docker 网络中启动：

```bash
docker run --rm -d \
  --name universe-client-web \
  --network <deployment-network> \
  -p 7893:7893 \
  -e SERVER_TARGET=http://web-api:10001 \
  -e APP_URL_PREFIX=/api \
  universe-client-web:local

curl -fsS http://127.0.0.1:7893/api/healthz
```

验收：请求由前端 API route 转发至 `${SERVER_TARGET}${APP_URL_PREFIX}/healthz` 并返回后端成功响应；不发布后端宿主端口也能工作。重新以另一合法 `SERVER_TARGET` 启动同一镜像时无需重新 build。

### 9.5 架构验证

若交付环境包含 amd64 Linux，而开发机为 Apple Silicon，应至少执行一次目标平台构建：

```bash
docker buildx build \
  --platform linux/amd64 \
  -t universe-client-web:amd64-test \
  -f client/web/Dockerfile \
  --load \
  client/web
```

验收：`sharp` 等原生依赖可在目标平台安装和运行；若最终发布多架构镜像，应由后续 CI/发布任务明确 `linux/amd64,linux/arm64` 和镜像仓库策略，本任务不自行引入推送流程。

## 10. 非目标

本任务不包含：

- 修改任何页面、路由业务、API 请求协议或登录逻辑。
- 修复代理代码中未使用 import、错误码映射或 multipart 行为。
- 为后端创建 Dockerfile、数据库或 Compose 编排。
- 引入 nginx、静态导出、PM2 cluster、Kubernetes 配置或镜像仓库推送。
- 升级 Next.js、React、Ant Design、锁文件格式或统一 npm/pnpm 的全仓依赖治理。
- 删除现有裸机打包、启动、停止脚本。

## 11. 风险与实施决策

1. **运行时变量是首要正确性要求**：若保留 `next.config.mjs.env`，构建时读取到的 `.env` 会覆盖容器启动变量，导致镜像无法跨环境复用，并可能把 `JWT_SECRET` 写入客户端 bundle；实施必须先解除该固化点。
2. **standalone 必须真实启动验证**：配置 `output: "standalone"` 不等于产物一定完整，需确认 `.next/static`、`public` 被复制，且 Pages Router API 代理及 `sharp` 在最终镜像可加载。
3. **端口必须收敛到 7893**：当前脚本存在 `7892`、`7893`、`9801` 和 PM2 `80` 多套历史值；Docker 镜像及后续 Compose 统一采用 `7893`，不顺带改造旧裸机流程。
4. **开发机已有产物不能成为隐式依赖**：当前工作区存在大型 `node_modules` 与 `.next`，镜像必须在 `.dockerignore` 生效且 Docker cache 清理后仍可构建，才能证明可复现。
5. **双锁文件不在本任务治理**：当前实际 npm 流程明确，Docker 选择 `package-lock.json`。删除 `pnpm-lock.yaml` 或切换 pnpm 会扩大变更面，留待单独依赖治理任务。
6. **健康检查不强行新增业务路由**：首页 2xx 可用于镜像独立烟测；Compose 启动依赖以后端 `/healthz` 为准。除非实施发现明确需要且不涉及业务行为，否则本任务不新增前端健康 API。

## 12. 完成定义

满足以下全部条件才视为实施完成：

1. `client/web` 上下文可成功构建生产镜像。
2. 最终镜像以非 root、前台单进程方式监听 `0.0.0.0:7893`。
3. 首页可访问，Pages Router `/api` 代理可在容器网络中访问后端。
4. `SERVER_TARGET` 与 `APP_URL_PREFIX` 在容器启动时生效，同一镜像可跨环境复用。
5. `.dockerignore` 排除 `node_modules`、`.next`、缓存、日志、PID、发布包和本地环境文件。
6. 镜像不包含真实环境地址、JWT、密码、Token 或其他秘密。
7. Docker 构建与运行命令、产物结构、端口和变量约定在本需求文档及必要脚本中清晰可执行。
