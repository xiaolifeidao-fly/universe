# 建立 `client/web` 与 `server/web-api` 统一 Docker 编排和验收流程：需求梳理

## 1. 任务目标

在前置任务分别提供 `client/web` 与 `server/web-api` 可复现 Docker 镜像的基础上，为两项服务建立一套仓库级统一 Docker Compose 部署入口，使开发、测试和交付人员可以用一致命令完成构建、启动、停止、查看状态、查看日志和端到端检查。

本任务重点是把两个应用镜像按真实运行依赖连接起来，统一环境变量示例、Docker 网络、端口映射、健康检查、服务依赖、管理脚本和部署说明。数据库仅按当前 `web-api` 的启动要求接入；仓库没有现成数据库编排时，默认连接外部已初始化的 MySQL，不为本需求扩展 Redis、消息队列、监控、反向代理或其他无关基础设施。

本阶段只完成需求梳理并固化后续实施依据，不新增 Compose、脚本或镜像文件，不执行任务状态流转。

## 3. 已确认的应用运行契约

### 3.1 `client-web`

| 项目 | 约定 |
| --- | --- |
| Compose 服务名 | `client-web` |
| 构建上下文 | `client/web` |
| Dockerfile | `client/web/Dockerfile` |
| 容器端口 | `7893` |
| 默认宿主端口 | `${CLIENT_WEB_PORT:-7893}` |
| 后端地址 | `SERVER_TARGET=http://web-api:10001` |
| API 前缀 | `APP_URL_PREFIX=/api` |
| 对外入口 | `http://127.0.0.1:${CLIENT_WEB_PORT:-7893}` |

前端 Pages Router 的 `/api/**` 代理在运行时读取 `SERVER_TARGET` 和 `APP_URL_PREFIX`。Compose 必须使用 Docker DNS 服务名 `web-api`，不得把容器内目标配置为 `127.0.0.1` 或宿主机地址。端到端检查以 `GET /api/healthz` 经前端代理到后端为准。

前置任务要求移除 `next.config.mjs.env` 对服务端变量的构建期固化，并启用 Next.js standalone 产物；本任务实施不得用 Compose build args 绕过该要求。

### 3.2 `web-api`

| 项目 | 约定 |
| --- | --- |
| Compose 服务名 | `web-api` |
| 构建上下文 | `server` |
| Dockerfile | `server/web-api/Dockerfile`，Compose 中相对 `server/` 上下文写为 `web-api/Dockerfile` |
| 容器端口 | `10001` |
| 默认宿主端口 | 不发布；调试 profile 可映射 `${WEB_API_PORT:-10001}` |
| 监听地址 | `WEB_API_ADDR=:10001` |
| 健康检查 | `GET http://127.0.0.1:10001/healthz` |
| 必填秘密 | `WEB_API_SQLCONN`、`WEB_API_AUTH_TOKEN_SECRET` |

`web-api` 在创建路由前先读取 `configs/application.properties` 并连接 MySQL；数据库不可达、DSN 缺失或配置文件生成失败时，服务不会健康。Compose 的健康检查和 `client-web` 的启动依赖必须体现这一事实。

服务启动不执行数据库建表或迁移。部署前必须按 `server/SCHEMA.md`、`server/delivery.sql` 及适用的 `server/migrations/` 脚本完成数据库初始化；统一 `up` 命令不得隐式修改数据库结构。

### 3.3 Docker 网络与暴露面

- 两个应用加入同一个由 Compose 管理的 bridge 网络，建议显式命名服务网络为 `app-network`，实际 Docker 网络名可由 Compose project name 加前缀。
- `client-web` 通过 `http://web-api:10001` 访问后端，不经过宿主端口。
- 默认只向宿主发布前端 `7893`，减少后端管理接口的直接暴露面。
- 如交付或排障确实需要宿主直连后端，应通过 Compose profile 或单独 override 文件显式开启 `10001:10001`，而不是默认发布。
- 本任务不引入 nginx、Traefik、TLS 终止、域名或公网防火墙规则；这些属于环境级入口治理。

## 4. 后续实施交付物

### 4.1 根级 `compose.yaml`

建议在仓库根目录新增 `compose.yaml`，原因是它需要同时引用 `client/web` 与 `server` 两个构建上下文，并作为统一命令的稳定入口。文件必须满足：

1. 定义 `web-api` 与 `client-web` 两个核心服务。
2. 使用前置任务约定的 Dockerfile 和构建上下文，不复制或内嵌另一份镜像构建逻辑。
3. 镜像名与标签可由环境变量覆盖，默认值应可用于本地，例如：
   - `${CLIENT_WEB_IMAGE:-universe-client-web}:${IMAGE_TAG:-local}`
   - `${WEB_API_IMAGE:-universe-web-api}:${IMAGE_TAG:-local}`
4. `web-api` 注入 `WEB_API_SQLCONN`、`WEB_API_AUTH_TOKEN_SECRET`、`WEB_API_AUTH_TOKEN_TTL_SECONDS`、`WEB_API_ADDR` 和可选 `TZ`。
5. `client-web` 注入 `SERVER_TARGET=http://web-api:10001`、`APP_URL_PREFIX=/api` 和可选 `TZ`；这两个内部路由变量应由 Compose 给出安全默认值，不要求操作者重复填写。
6. `web-api` 使用镜像自带或 Compose 定义的 `/healthz` 健康检查。
7. `client-web` 使用 `depends_on.web-api.condition: service_healthy`，避免后端数据库尚未连接时前端被误判为整套系统可用；同时文档必须说明 `depends_on` 只控制启动顺序，不替代运行期故障恢复。
8. 两个服务配置合理的重启策略，建议本地默认 `unless-stopped`；不得用无限快速重启掩盖缺少必填变量或数据库不可达的问题。
9. 默认仅发布 `${CLIENT_WEB_BIND:-127.0.0.1}:${CLIENT_WEB_PORT:-7893}:7893`。如需要局域网或公网监听，由部署环境显式把 `CLIENT_WEB_BIND` 改为 `0.0.0.0`，并自行承担访问控制。
10. 不挂载源代码、宿主 `node_modules`、`.next`、Go 缓存、日志或 PID 目录；目标是验证生产镜像，而不是开发热更新。
11. 不把真实 `.env`、数据库配置、密钥文件复制进镜像或写入 Compose 默认值。

### 4.2 环境变量示例

建议新增根级 `.env.example`，仅提供变量名、安全占位符、格式说明和非敏感默认值。真实运行文件使用根级 `.env`，并将其加入根级 `.gitignore`；如项目最终采用 `deploy/.env`，则文件位置和脚本参数必须全程一致，不得出现多套隐式搜索路径。

建议变量契约：

| 变量 | 必填 | 默认/示例 | 说明 |
| --- | --- | --- | --- |
| `COMPOSE_PROJECT_NAME` | 否 | `universe` | 固定容器、网络和资源名前缀，便于多项目隔离。 |
| `IMAGE_TAG` | 否 | `local` | 两个本地镜像的统一标签。 |
| `CLIENT_WEB_IMAGE` | 否 | `universe-client-web` | 可替换为镜像仓库地址。 |
| `WEB_API_IMAGE` | 否 | `universe-web-api` | 可替换为镜像仓库地址。 |
| `CLIENT_WEB_BIND` | 否 | `127.0.0.1` | 前端宿主监听地址。 |
| `CLIENT_WEB_PORT` | 否 | `7893` | 前端宿主端口。 |
| `WEB_API_PORT` | 否 | `10001` | 仅调试 profile 发布后端时使用。 |
| `WEB_API_SQLCONN` | 是 | `user:password@tcp(host:3306)/database?...` | MySQL DSN；必须指向容器可访问地址。 |
| `WEB_API_AUTH_TOKEN_SECRET` | 是 | `<replace-with-strong-secret>` | 令牌签发与校验秘密，不得使用仓库开发值。 |
| `WEB_API_AUTH_TOKEN_TTL_SECONDS` | 否 | `604800` | 正整数秒数。 |
| `TZ` | 否 | `Asia/Shanghai` | 两个容器的统一显示时区；需与 DSN 的 `loc` 策略一致。 |

约束：

- `.env.example` 不得出现实际内网地址、账号、密码、Token、API key 或可直接使用的弱秘密。
- Compose 变量替换对 `$` 等字符有语义，部署说明必须建议复杂秘密使用受控 env file、CI secret 或部署平台 secret 注入，并说明需要按 Compose 规则转义；不得在脚本中 `eval`。
- 外部 MySQL 地址不能写 `127.0.0.1` 来代表宿主机。Docker Desktop 本地可按环境使用 `host.docker.internal`；Linux 或生产环境应使用真实可路由 DNS/IP，文档不得承诺该名称跨平台必然存在。
- 由于 `WEB_API_SQLCONN` 和令牌秘密最终会进入容器环境，`docker inspect` 权限应视为敏感权限。引入 Docker secrets 需要应用入口支持文件型变量，若前置任务未提供则不在本任务擅自扩展。

### 4.3 统一管理脚本

建议新增根级 `scripts/docker-stack.sh`，以 `docker compose --project-directory <repo-root> --env-file <repo-root>/.env -f <repo-root>/compose.yaml` 为唯一底层入口。脚本必须从任意工作目录调用都能正确定位仓库根目录，并提供至少以下命令：

| 命令 | 行为 |
| --- | --- |
| `config` | 执行 Compose 配置解析校验；输出时必须避免在共享日志中泄露插值后的秘密。 |
| `build [service]` | 构建全部或指定服务镜像。 |
| `up` | 后台启动核心服务，并在返回成功前等待服务健康或执行等价就绪检查。 |
| `down` | 停止并删除本项目容器和默认网络；默认不删除镜像、不删除外部数据库、不使用 `-v`。 |
| `restart [service]` | 重启全部或指定服务。 |
| `status` | 显示 Compose 服务状态和健康状态。 |
| `logs [service]` | 查看全部或指定服务日志，支持跟随模式或清晰的参数透传。 |
| `check` | 执行端到端验收：容器健康、前端首页、前端代理 `/api/healthz`。 |

脚本要求：

1. 使用严格模式，明确检查 `docker`、`docker compose`、环境文件和必填变量。
2. Docker daemon 不可用、端口冲突、变量缺失、构建失败、健康超时或 HTTP 检查失败时返回非零。
3. 不在日志中打印 DSN、令牌秘密或完整 Compose 插值配置。
4. `up` 的健康等待设置有限超时并输出可操作诊断，例如失败服务的 `docker compose ps` 与最近日志；不得无限等待。
5. `check` 默认检查：
   - `web-api` 为 `healthy`；
   - `client-web` 为运行状态；
   - `GET http://127.0.0.1:${CLIENT_WEB_PORT}/` 返回 2xx/3xx；
   - `GET http://127.0.0.1:${CLIENT_WEB_PORT}/api/healthz` 返回 2xx，证明 Docker DNS、前端运行时变量和后端路由同时正确。
6. 若 `CLIENT_WEB_BIND` 不是本机回环地址，检查 URL 应允许用独立变量覆盖，不能机械地把 `0.0.0.0` 当作客户端访问地址。
7. 不自动执行 SQL、迁移、默认管理员初始化、镜像推送、数据清理或 `docker system prune`。

可额外提供轻量根级包装入口，例如 `./scripts/docker-stack.sh up`，但不要求引入 Makefile。若实现选择 Makefile，也必须复用同一脚本，避免两套行为漂移。

### 4.4 部署说明

建议新增 `doc/deployment/docker-compose.md` 或等价仓库级说明，并至少包含：

1. 前置条件：Docker Engine、Compose v2、两个前置镜像任务已实施、可访问且已初始化的 MySQL。
2. 首次部署：复制 `.env.example`、填写秘密、构建、启动、检查。
3. 日常操作：状态、日志、重启、停止、重新构建。
4. 数据库初始化边界：链接到 `server/SCHEMA.md`、`server/delivery.sql` 和适用迁移，明确不会自动执行。
5. 端口与网络：默认只开放前端 `7893`，后端通过内部服务名访问，调试开放后端的方法。
6. 配置变更：修改 `.env` 后需重建还是仅重建容器；运行时变量变更不得要求重新构建镜像。
7. 常见故障：Docker daemon 未启动、MySQL 地址从容器不可达、鉴权秘密缺失、端口占用、`web-api` unhealthy、前端首页正常但 `/api/healthz` 失败。
8. 安全提示：限制 `.env` 文件权限、禁止提交、禁止在工单/日志粘贴真实值、默认绑定回环地址。
9. 清理语义：`down` 不删除数据库；数据库是外部依赖时，Compose 无权管理其生命周期。

## 5. 数据库与基础设施接入边界

### 5.1 默认方案：外部 MySQL

当前仓库没有数据库 Compose，默认方案是通过 `WEB_API_SQLCONN` 连接已存在、已初始化且容器可访问的 MySQL。这样满足 `web-api` 的真实启动依赖，同时不把数据库版本、字符集、持久卷、备份恢复、初始化幂等和生产数据生命周期等新责任塞进本任务。

### 5.2 可选本地数据库 profile 的条件

只有在实施阶段发现仓库已有经过验证的 MySQL 编排可直接复用，或用户另行明确要求时，才可增加 `infra`/`local-db` profile。即使增加，也必须满足：

- 默认 `up` 不自动启动或销毁数据库。
- 数据库版本、字符集、时区、健康检查和持久卷明确。
- 初始化脚本可验证且不会误改已有库。
- `down` 默认不删除数据卷。

当前核查没有发现此类现有编排，因此本需求不要求实现本地 MySQL 容器。Redis 等当前不构成 `web-api` 启动必需依赖，同样不纳入 Compose。

## 6. 统一验收流程

### 6.1 静态验收

1. `docker compose --env-file .env -f compose.yaml config --quiet` 成功。
2. Compose 只定义本需求需要的应用服务和网络；默认不包含无关基础设施。
3. `client-web` 构建上下文为 `client/web`；`web-api` 构建上下文为 `server`。
4. `client-web` 内部目标为 `http://web-api:10001`，不是 `localhost`。
5. 默认只发布前端端口，真实秘密不在 Compose、示例文件、镜像 build args 或文档示例中。
6. `.env` 已被根级 `.gitignore` 排除，`.env.example` 保持可提交。
7. 管理脚本通过 `bash -n` 和可用的项目 shell 格式检查。

### 6.2 构建验收

在 Docker daemon 可用且两个前置 Dockerfile 已落地后：

```bash
cp .env.example .env
# 填写 WEB_API_SQLCONN 与 WEB_API_AUTH_TOKEN_SECRET
./scripts/docker-stack.sh build
```

验收：两个服务都从约定上下文成功构建；构建不依赖宿主 `node_modules`、`.next`、Go 二进制或真实配置；秘密未作为 build args 进入镜像层。

### 6.3 启停与健康验收

```bash
./scripts/docker-stack.sh up
./scripts/docker-stack.sh status
./scripts/docker-stack.sh check
./scripts/docker-stack.sh down
```

验收：

1. `web-api` 在数据库可达时进入 `healthy`。
2. `client-web` 保持运行并监听容器内 `7893`。
3. 首页通过宿主映射访问成功。
4. `/api/healthz` 经前端代理返回后端 2xx。
5. 默认无法通过宿主 `127.0.0.1:10001` 直接访问后端；开启调试 profile 后才可访问。
6. `down` 后两个应用容器和项目默认网络被删除，镜像保留，外部数据库及其数据不受影响。

### 6.4 故障验收

至少验证以下失败场景：

1. 缺少 `WEB_API_SQLCONN` 或 `WEB_API_AUTH_TOKEN_SECRET`：脚本在启动前明确失败，且不打印秘密。
2. MySQL 地址不可达：`web-api` 不健康，`up`/`check` 在有限超时后非零退出并给出诊断。
3. 前端宿主端口被占用：Compose 启动失败并保留可定位错误。
4. `SERVER_TARGET` 被错误覆盖：首页可能正常，但 `/api/healthz` 必须失败，从而证明端到端检查能发现代理断链。
5. Docker daemon 未启动：管理脚本在执行 Compose 前明确失败。

### 6.5 配置复用验收

同一批镜像通过修改运行时 `.env` 后重新创建容器，应能切换：

- 前端宿主端口或绑定地址；
- 外部 MySQL 地址；
- 鉴权秘密和 Token TTL；
- 时区；
- 可选镜像仓库地址或标签。

除镜像名/标签或源代码变化外，不应要求重新构建镜像。

## 7. 非目标

本任务不包含：

- 重新实现或替代两个前置任务的 Dockerfile、构建脚本和镜像内部入口逻辑。
- 修改前端页面、API 协议、代理业务行为、后端路由或领域逻辑。
- 自动创建、迁移、备份、恢复或删除生产数据库。
- 默认新增 MySQL、Redis、消息队列、对象存储、监控、日志平台等基础设施容器。
- 引入 nginx、Traefik、TLS、域名、证书、Kubernetes、Helm 或云厂商部署资源。

## 8. 风险与实施决策

1. **前置产物尚未落地是当前主要阻塞**：本任务可先实现静态编排文件，但真实 build/up/check 必须等 `client/web/Dockerfile` 与 `server/web-api/Dockerfile` 存在。
2. **数据库健康决定后端健康**：`web-api` 不是无依赖 HTTP 服务，数据库未初始化或不可达时 `/healthz` 不会可用。验收环境必须提供真实可访问数据库。
3. **`depends_on` 不是运行期熔断**：它只帮助初始启动排序。后端运行中故障时，前端仍可能保持运行，必须依靠 `check`、健康状态和日志发现。
4. **默认不暴露后端端口**：这减少攻击面，也意味着后端直连排障需要显式 profile/override；文档和脚本必须提供清晰入口。
5. **环境变量可能被 inspect 读取**：当前前置入口以环境变量生成 properties，部署主机 Docker 权限即敏感权限。未建立文件型 secret 契约前，不虚构“使用 Docker secret 即完成安全治理”。
6. **Compose project name 必须稳定**：否则容器、网络和脚本状态查询可能因调用目录不同而漂移。统一脚本应固定 project directory，并通过 `COMPOSE_PROJECT_NAME` 提供一致命名。
7. **检查不能只看首页**：Next.js 首页成功不代表后端代理可用；`/api/healthz` 是本任务最关键的跨服务验收点。
8. **配置解析日志可能泄密**：`docker compose config` 会展开变量，脚本默认应使用 `--quiet`，排障文档需提醒不要把完整输出上传到共享渠道。
9. **跨平台宿主地址不同**：`host.docker.internal` 可用于部分本地 Docker 环境，但生产/Linux 不应依赖其存在，外部数据库应使用部署网络可路由地址。

## 9. 完成定义

后续实施满足以下全部条件才视为完成：

1. 仓库根目录存在统一 `compose.yaml`，可构建并运行 `client-web` 与 `web-api`。
2. 存在无敏感信息的 `.env.example`，真实 `.env` 被版本控制忽略。
3. 存在统一管理脚本，可执行 `config`、`build`、`up`、`down`、`restart`、`status`、`logs` 和 `check`。
4. 两个服务通过 Compose 内部网络和服务名通信，默认只发布前端 `7893`。
5. `web-api` 健康检查反映数据库连接和 HTTP 可用性，`client-web` 启动依赖后端健康。
6. 外部 MySQL 的配置、初始化前提和生命周期边界清晰；默认编排不扩展无关基础设施。
7. 首页和 `/api/healthz` 端到端检查均通过，错误场景能以非零状态和可操作日志暴露。
8. 运行时变量变化可通过重新创建容器生效，不需要重建相同镜像。
9. 部署说明覆盖首次部署、日常操作、故障排查、安全和清理语义。
10. Compose 与镜像中不包含真实数据库凭证、令牌秘密、内部地址或其他敏感配置。
