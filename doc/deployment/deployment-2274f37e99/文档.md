# 验证 Docker 部署链路并补充部署说明：需求梳理

## 1. 任务目标

在前置任务完成 Docker 镜像与 Docker Compose 编排后，对仓库根目录的部署入口进行一次**不使用真实密钥**的可复现验证，并补充面向部署操作者的说明。验证范围必须覆盖镜像构建、Compose 启动、容器健康状态、宿主访问前端，以及前端 `/api` 代理到 `web-api` 的容器网络联通。

本任务产出的是验证记录与部署说明；不新增业务功能、不修改外部基础设施拓扑，也不在仓库中提交任何真实 DSN、密码、Token、JWT 密钥或第三方 API Key。

## 4. 部署配置要求

后续实施的 `deploy/.env.example` 只能包含变量名、端口及安全占位符，不含任何可用秘密。建议最少包含：

| 变量 | 用途 | 示例要求 |
| --- | --- | --- |
| `CLIENT_WEB_PORT` | 宿主暴露的前端端口 | 可使用非特权端口，例如 `7893`。 |
| `WEB_API_ADDR` | 后端容器监听地址 | 固定为容器内 `:10001` 或等价值。 |
| `WEB_API_SQLCONN` | 后端测试 MySQL DSN | 仅在未跟踪的 `deploy/.env` 或 CI Secret 中填写；示例值必须是不可用占位符。 |
| `SERVER_TARGET` | 前端容器到后端的目标地址 | `http://web-api:10001`，不得为 `127.0.0.1` 或宿主 `localhost`。 |
| `APP_URL_PREFIX` | 前端 `/api` 的后端路径前缀 | 需与实际后端路由一致；当前后端将业务路由注册在 `/api`，预计为 `/api`。 |
| `JWT_SECRET` | 前端认证相关密钥（若运行确有需要） | 仅以部署 Secret 注入；不得进入 Docker build args、镜像层、示例文件或日志。 |

部署实现必须同时满足：

- `web-api` 不对宿主公开端口，除非部署场景明确需要排障；`client-web` 是默认唯一公开服务。
- `client-web` 通过 `depends_on.condition: service_healthy` 等待后端健康，而不是固定 `sleep`。
- 后端 healthcheck 调用容器内 `http://127.0.0.1:10001/healthz`；健康检查工具及配置必须随镜像提供。
- `.dockerignore` 排除 `.env*`（必要时保留明确允许的示例文件）、日志、运行目录、构建产物和依赖目录，避免真实配置与无关文件进入构建上下文。
- 前端代理变量必须在最终运行形态生效。若继续保留 `next.config.mjs` 的 `env` 内联方式，部署说明必须明确它们为**构建时非敏感配置**，并要求在 `docker compose build` 前从无密钥环境提供；`JWT_SECRET` 不得按此方式注入。更优方案是调整代理代码只在 Node 运行时读取环境变量。

## 5. 验证流程与验收标准

以下命令以最终 `deploy/` 脚本为唯一入口；实现时可按脚本实际参数微调，但不得绕开 Compose。

### 5.1 验证前检查

```bash
docker info
docker compose version
test -f deploy/.env
grep -E '^(WEB_API_SQLCONN|SERVER_TARGET|APP_URL_PREFIX)=' deploy/.env | cut -d= -f1
```

验收：Docker daemon 可用；`deploy/.env` 已创建但未被 Git 跟踪；输出中只能记录变量名，不能回显变量值。

### 5.2 构建

```bash
./deploy/build.sh
docker compose --env-file deploy/.env -f deploy/docker-compose.yml images
```

验收：前后端镜像均构建成功；构建日志、Docker history 和镜像配置中不出现测试 DSN、密码、JWT 或 API Key。必要时以变量名或受控扫描工具检查，禁止把秘密原文打印到记录中。

### 5.3 启动与健康检查

```bash
./deploy/up.sh
docker compose --env-file deploy/.env -f deploy/docker-compose.yml ps
curl --fail --show-error --silent http://127.0.0.1:${CLIENT_WEB_PORT}/
docker compose --env-file deploy/.env -f deploy/docker-compose.yml exec -T web-api \
  wget -qO- http://127.0.0.1:10001/healthz
```

验收：`web-api` 状态为 `healthy`，`client-web` 为运行中；前端首页返回 2xx；后端健康响应包含 `success=true`、`code=0`、`data=ok`。如果镜像未提供 `wget`，应改用镜像内已有的等价 HTTP 客户端，并在部署说明中写明。

### 5.4 前后端联通

```bash
curl --fail --show-error --silent \
  http://127.0.0.1:${CLIENT_WEB_PORT}/api/healthz
```

验收：请求经 `client-web` 的 `/api` catch-all 代理抵达 `web-api`，返回与后端 `/healthz` 一致的成功 JSON。若返回 404，应优先核对 `APP_URL_PREFIX` 与后端路由前缀；若返回 500，应检查 `SERVER_TARGET` 是否为 `http://web-api:10001`、前端变量是在构建期还是运行期生效，以及 Compose 网络/DNS 状态。不得通过暴露后端宿主端口来替代该验证。

### 5.5 运维命令与清理

部署说明至少列出并实际验证以下命令：

```bash
./deploy/status.sh
./deploy/logs.sh
./deploy/logs.sh web-api
./deploy/down.sh
docker compose --env-file deploy/.env -f deploy/docker-compose.yml ps
```

验收：状态与日志命令不泄露环境变量；`down.sh` 可重复执行并清理容器和网络；是否删除卷必须在说明中明确，默认不得删除外部数据库数据。

## 6. 应补充的部署说明内容

后续实现应在 `deploy/README.md`（或仓库根 README 的部署章节）记录：

1. Docker / Compose 版本要求、端口占用检查、Docker daemon 启动要求，以及外部 MySQL 的网络可达性。
2. 从 `.env.example` 创建未跟踪 `.env` 的步骤；每个变量的用途、是否敏感、提供渠道和禁止提交规则。
3. 标准构建、启动、状态、健康检查、日志、停止与更新命令。
4. 通过 `http://127.0.0.1:${CLIENT_WEB_PORT}/api/healthz` 验证前后端联通的方法与期望响应。
5. 故障排查顺序：Docker daemon → `.env` 必填项 → 镜像构建 → `web-api` 日志/数据库连接 → healthcheck → `SERVER_TARGET` 与 `APP_URL_PREFIX` → 浏览器访问。
6. 已知限制：本 Compose 不编排 MySQL、Redis、LLM、Ark 等外部依赖；后端启动需要 MySQL；当前鉴权中间件仍为 passthrough；前端环境变量可能受 Next.js 构建期内联影响。

## 7. 本阶段完成定义

本次「梳理需求」完成后，后续执行者应能仅凭本文件：

- 判断当前无法开始真实 Docker 验证的具体原因；
- 知道必须等待的前置文件和运行环境；
- 在不接触真实密钥的前提下准备测试配置；
- 按统一命令完成构建、启动、健康检查、前后端代理验证、日志查看和清理；
- 将结果、失败原因、镜像/容器状态和已知限制写入部署说明，而不记录任何秘密原文。
