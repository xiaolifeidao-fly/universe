# 设计本机爬虫客户端与平台对接方案：需求梳理

## 1. 任务目标与本阶段边界

为首个甲方设计一个运行在**甲方授权用户电脑**上的本机数据采集客户端（下称“客户端”），明确其部署、运行、配置、安全、采集、上报、重试、日志和隐私边界；同时定义平台侧需要提供的机器接口及新增甲方的适配约定。

本文件是后续设计、开发、联调和负责人评审的需求基线。本阶段不实现浏览器自动化/爬虫代码、不创建平台业务页面、不变更数据库或既有 API，也不假定能够绕过第三方网站的访问控制、验证码、反自动化机制或服务条款。

## 2. 当前工程核查结论（2026-08-14）

| 核查项 | 当前事实 | 对本方案的影响 |
| --- | --- | --- |
| 服务端形态 | `server/web-api` 是当前聚合 HTTP 进程，路由统一挂载于 `/api`，健康检查为 `GET /healthz`。 | 采集端接口首期可随 `web-api` 聚合发布；接口代码归属仍应放在后续新增的对应 `*-api/pkg/` 子域，不能写入 `web-api/pkg/`。 |
| 分层约束 | `service/README.md` 规定领域逻辑在 `service/`，跨领域只传 `contract` 数据形状，领域包之间以 `ports.go` 解耦。 | 客户端接入应成为 task/resource 范围的新子域；HTTP DTO 放对应 `dto/`，稳定跨域事件/数据结构放 `contract`。 |
| 业务线能力 | 已实现 `zt_bizline_def`、`zt_bizline_capability`；初始化脚本会创建 `whatsapp` 业务线，能力声明含 `min_agent_version`。 | 首个甲方先以 `bizLine=whatsapp` 作为暂定归属；客户端必须上报 `agentVersion` 和能力集版本，平台按业务线、版本控制可领取任务。 |

| 任务领域 | `service/task`、资源设备、端侧拉取与采集结果模型尚未落地。 | 本文定义的是目标接口契约；后续实施需先新增该领域模型、表与 API，不能误认为现有交付看板接口可用于生产采集调度。 |

## 3. 总体架构与责任边界

```text
平台控制台 / 调度服务
        │（配置甲方、数据源、采集策略、审批与查看结果）
        ▼
平台采集接入 API（HTTPS /api/collector/...）
        │  设备注册、授权、任务租约、结果接收、审计
        ▼
甲方用户电脑：Collector Host（单机守护进程）
        ├─ 本地受保护配置、凭证、队列、日志
        ├─ Adapter：first-party-whatsapp（首个甲方实现）
        └─ Browser/HTTP Driver（仅在授权范围内访问目标系统）
```

### 3.1 平台负责什么

- 维护甲方/业务线、客户端设备、数据源、采集范围、任务、结果索引、失败状态与审计记录。
- 只向已注册且状态正常的客户端下发与其 `bizLine`、`adapterKey`、`agentVersion`、能力集匹配的任务。
- 对采集任务做去重、租约控制、幂等入库、权限校验和敏感字段访问控制；平台不得要求客户端上传未经约定的原始浏览器资料。
- 提供暂停、撤销、吊销设备凭证、范围变更和数据删除的管理能力；撤销后的客户端不得继续拉取或上传新结果。

### 3.2 客户端负责什么

- 以单一宿主进程运行，维护本地任务队列、任务租约、重试退避和最小必要日志；同一 `deviceId` 同时只允许运行一个活跃实例。
- 在甲方本机浏览器/网络环境中执行**经负责人确认且用户已授权**的数据读取；不提供远程交互式控制、键盘记录、屏幕录制、密码导出或规避访问限制能力。
- 只上传任务要求字段、状态和经脱敏的诊断信息；原始页面、Cookie、完整网络包、浏览器用户目录默认不得上传。
- 发现凭证失效、账号风险、需人工验证、范围不一致或本地环境异常时，停止该任务并按指定错误码回传，不自行扩大采集范围或无限重试。

### 3.3 非目标与强制限制

- 不支持无用户知情的后台安装、静默自启、提权安装或跨用户运行；安装、首次授权、卸载和更新均应由本机用户可见并可操作。
- 不存储或传输第三方系统密码、Cookie、二次验证代码、完整聊天内容、联系人全量通讯录或未在任务字段白名单中的个人信息。
- 不处理验证码、反爬/风控规避、代理轮换、账号批量登录、绕过访问频率限制；遇到此类情形回传 `COLLECTOR_AUTH_CHALLENGE` 或 `SOURCE_ACCESS_DENIED`。
- 不以本机客户端替代平台的数据治理、账号授权、人工审批与删除请求处理。

## 4. 客户端部署、启动与本地配置

### 4.1 推荐部署形态

首期交付为受签名安装包安装的本机常驻应用，包含 `collector-host` 宿主、已审核的适配器包及必要的浏览器驱动依赖。优先支持 Windows 10/11 x64（以首个甲方实际办公环境为准）；macOS/Linux 仅在负责人确认后纳入支持矩阵。

| 项目 | 约定 |
| --- | --- |
| 安装权限 | 默认按当前用户安装，不要求管理员权限；如企业软件分发要求系统级安装，必须单独评审。 |
| 启动方式 | 用户完成一次显式授权后，使用操作系统受管的用户级服务/登录项守护；不使用 `nohup`、隐藏窗口或自行创建不可见计划任务。 |
| 单实例 | 基于本地锁（锁文件/命名互斥）保证每个安装实例仅一个宿主进程；第二实例退出并写本地事件。 |
| 更新 | 平台仅发布带版本、哈希和签名的更新清单；客户端下载后校验签名与哈希，失败则保留当前可运行版本。首期不做静默强制更新。 |
| 离线行为 | 无网时不执行新任务；允许保留尚未确认的结果并按本地加密队列重试，超过保留期自动删除。 |
| 卸载 | 清除服务/登录项、任务缓存、刷新令牌和日志；需提供“保留诊断日志”可选项，并在界面说明保留内容。 |

### 4.2 本地配置与密钥边界

客户端配置分为“受平台签名的远程策略”和“本机安装配置”。本机配置仅保存 API 基地址、设备标识、非敏感运行开关、刷新凭证引用和日志等级；凭证应使用 OS 凭据库或等效加密存储，不可明文写入 JSON/YAML、命令行、日志或崩溃转储。

```yaml
# 示例：仅说明字段，不可将真实 token、Cookie、账号或采集数据提交到仓库。
apiBaseUrl: https://collector-api.example.com/api
deviceId: dev_01H...
tenantId: first-party-pending
bizLine: whatsapp
agentVersion: 0.1.0
adapterKey: first-party-whatsapp
policyVersion: 2026-08-14.1
pollIntervalSeconds: 60
logLevel: info
resultRetentionHours: 72
```

策略中的采集字段白名单、频率上限、并发数、允许数据源、任务有效期和隐私规则由平台下发，并须包含 `policyVersion`、`issuedAt`、`expiresAt` 和签名。客户端校验失败或策略过期时进入 `POLICY_EXPIRED`，停止领取新任务。

## 5. 身份鉴别、授权与传输安全

### 5.1 设备身份模型

1. 管理员在平台创建一次性激活码，绑定 `tenantId`、`bizLine`、`adapterKey`、允许的版本范围和失效时间。
2. 用户在客户端输入激活码并完成企业确认页；客户端生成本机密钥对，并通过 TLS 向平台注册 `deviceId`、公钥、环境摘要与能力集。
3. 平台校验激活码后签发短期访问令牌（建议 15 分钟）和可吊销刷新凭证（建议 30 天，存 OS 凭据库），同时记录设备状态为 `active`。
4. 每个请求带 `Authorization: Bearer <device-access-token>`、`X-Device-Id`、`X-Request-Id`；结果请求额外带请求体 SHA-256 摘要。令牌的主体必须是设备，不复用人工用户 JWT。
5. 平台可把设备置为 `suspended`、`revoked` 或 `retired`；客户端收到或拉取到该状态后删除本地刷新凭证、停止任务并只保留必要的本地告知。

首期所有通讯必须使用 HTTPS/TLS 1.2+，校验服务端证书与域名；禁止 HTTP、跳过证书校验和把访问令牌放入 URL 查询参数。双向 TLS 可作为二期增强，不作为首期前置条件。

### 5.2 权限范围

设备令牌至少包含或由平台会话关联以下约束：`deviceId`、`tenantId`、`bizLine`、`adapterKey`、`scopes`、`exp`、`jti`。首期 scope 固定为 `collector:register`、`collector:policy:read`、`collector:task:pull`、`collector:task:heartbeat`、`collector:result:write`、`collector:log:write`；不得具备控制台管理、用户管理或跨甲方读取权限。

## 6. 平台通信接口（目标契约）

### 6.1 通用约定

- 基路径：`/api/collector/v1`；JSON 使用 UTF-8，时间统一 RFC 3339 UTC，字段采用 lowerCamelCase。
- 每个写请求必须带 `X-Request-Id`（UUID/ULID）；平台按 `deviceId + requestId` 保证至少 24 小时的幂等处理。结果另以 `taskId + attemptId + resultId` 去重。
- 响应统一返回 `{ "code": "OK", "message": "", "data": {}, "requestId": "..." }`；HTTP 状态表示协议/鉴权类失败，业务状态使用 `code`。
- 客户端仅可读取自己的设备、策略和已分配任务；平台侧所有数据查询必须强制按 `tenantId`、`bizLine` 和 `deviceId` 过滤。

| 接口 | 方法 | 用途 | 幂等键 |
| --- | --- | --- | --- |
| `/devices/activate` | `POST` | 激活码换取设备身份和初始令牌 | `activationCode + publicKeyFingerprint` |
| `/sessions/refresh` | `POST` | 刷新短期访问令牌 | 刷新凭证轮换标识 |
| `/devices/me` | `GET` | 查询设备状态与允许范围 | 无 |
| `/policies/current` | `GET` | 拉取当前已签名采集策略 | `If-None-Match` / policy version |
| `/tasks:pull` | `POST` | 长轮询/短轮询领取最多一个可执行任务 | `requestId` |
| `/tasks/{taskId}/heartbeat` | `POST` | 续租、回传进度或声明不可执行 | `taskId + leaseId + sequence` |
| `/tasks/{taskId}/results` | `POST` | 上报结构化结果、部分结果或终态失败 | `taskId + attemptId + resultId` |
| `/tasks/{taskId}/ack` | `POST` | 确认平台已接受终态；可选，结果响应已确认时省略 | `taskId + attemptId` |
| `/events` | `POST` | 上报非任务级诊断/生命周期事件 | `requestId` |

### 6.2 任务拉取与租约

请求：

```json
{
  "bizLine": "whatsapp",
  "adapterKey": "first-party-whatsapp",
  "agentVersion": "0.1.0",
  "capabilities": ["account-profile-read", "conversation-summary-read"],
  "maxTasks": 1,
  "lastPolicyVersion": "2026-08-14.1"
}
```

成功响应中的任务必须包含：`taskId`、`attemptId`、`leaseId`、`leaseExpiresAt`、`policyVersion`、`adapterKey`、`operation`、`sourceRef`、`fieldAllowlist`、`timeRange`、`maxRecords`、`dedupeKey`、`traceId`。客户端发现任务的业务线、适配器、策略版本或字段白名单与本机已验证策略不一致时，不执行，使用 `TASK_POLICY_MISMATCH` 终止该次尝试。

租约建议 5 分钟，客户端每 60 秒心跳一次；网络中断时可继续处理至租约到期，但不得在租约到期后开始新的源站操作。平台收到同一 `taskId` 的新租约后，旧 `leaseId` 的结果必须返回 `TASK_LEASE_EXPIRED`，客户端保留结果但不自动改投给新任务。

### 6.3 结果上报结构

```json
{
  "taskId": "ct_01H...",
  "attemptId": "ca_01H...",
  "leaseId": "lease_01H...",
  "resultId": "cr_01H...",
  "status": "succeeded",
  "startedAt": "2026-08-14T09:00:00Z",
  "finishedAt": "2026-08-14T09:01:12Z",
  "source": {
    "sourceRef": "approved-source-001",
    "observedAt": "2026-08-14T09:01:00Z",
    "sourceCursor": "opaque-cursor-or-null"
  },
  "records": [
    {
      "recordId": "sha256:...",
      "recordType": "conversationSummary",
      "schemaVersion": "1.0",
      "data": {}
    }
  ],
  "stats": { "read": 20, "accepted": 18, "skipped": 2 },
  "error": null,
  "traceId": "trace_01H..."
}
```

`records[].data` 只能含任务的 `fieldAllowlist` 明确列出的字段；`recordId` 对同一逻辑数据应稳定，以便平台去重。批量结果建议单请求不超过 500 条或 1 MiB（以先达到者为准）；超出时分批并保持同一 `attemptId`。平台应返回每批的 `acceptedRecordIds`、`rejectedRecords[]` 和是否接受终态，客户端仅重试可重试的整批/子集。

## 8. 采集执行、状态回传与异常处理

### 8.1 状态机

```text
queued → leased → running → reporting → succeeded
                    │           └──────→ partial_succeeded
                    ├→ retry_wait → leased
                    ├→ blocked
                    ├→ failed
                    └→ cancelled
```

- `queued`、`leased` 由平台维护；客户端从收到租约后进入 `running`。
- `partial_succeeded` 表示平台接受了部分记录，客户端必须携带拒绝条目和原因，不能伪装为全量成功。
- `blocked` 用于人工登录、用户授权、策略确认、验证码或源站权限问题，默认不自动重试。
- `failed` 是不可恢复或超过重试上限的终态；`cancelled` 表示平台或本机用户在安全点取消，客户端必须停止后续源站动作。

### 8.2 错误码与重试规则

| 代码 | 含义 | 客户端动作 | 自动重试 |
| --- | --- | --- | --- |
| `AUTH_TOKEN_EXPIRED` | 设备访问令牌过期 | 刷新一次并重放原请求。 | 是，1 次 |
| `DEVICE_REVOKED` | 设备被吊销/停用 | 删除刷新凭证，停止所有任务并提示用户。 | 否 |
| `POLICY_EXPIRED` | 本地策略到期或签名无效 | 拉取策略；仍无有效策略则停止新任务。 | 是，限 3 次 |
| `TASK_LEASE_EXPIRED` | 租约过期或被重新分配 | 停止上报该租约，保留本地审计摘要。 | 否 |
| `TASK_POLICY_MISMATCH` | 任务与本地签名策略不一致 | 不执行，回传诊断。 | 否 |
| `SOURCE_UNAVAILABLE` | 授权源站临时不可用/网络失败 | 指数退避重试。 | 是，最多 5 次 |
| `SOURCE_ACCESS_DENIED` | 源站拒绝访问或权限不足 | 停止该任务，提示用户检查授权。 | 否 |
| `COLLECTOR_AUTH_CHALLENGE` | 出现验证码、二次验证或人工验证 | 停止自动操作，转人工。 | 否 |
| `DATA_VALIDATION_FAILED` | 平台拒绝字段、类型、长度或 schema | 丢弃违规字段并回传条目级错误。 | 否，待策略/代码修复 |
| `LOCAL_STORAGE_FULL` | 本地加密队列无法写入 | 停止领取，提示用户释放空间。 | 否 |
| `INTERNAL_ERROR` | 未分类本地异常 | 记录脱敏栈摘要，指数退避。 | 是，最多 3 次 |

可重试任务采用带随机抖动的指数退避（建议 30 秒、2 分钟、10 分钟、30 分钟、2 小时），并受 `leaseExpiresAt` 和策略中 `maxAttempts` 限制。任何重试不得导致对源站的访问频率超过策略上限；请求超时、5xx 和网络错误不等同于可无限重复执行的采集动作。

## 9. 日志、隐私、审计与保留

| 数据类别 | 本地存储 | 上报平台 | 默认保留 |
| --- | --- | --- | --- |
| 访问/刷新凭证 | OS 凭据库或本地加密区 | 不上报明文 | 吊销或卸载时删除 |
| 待上报结果 | 加密队列 | 仅字段白名单内容 | 最多 72 小时，成功确认后删除 |
| 运行日志 | 轮转文本/结构化日志 | 仅严重级别摘要 | 本地 14 天或 100 MiB；平台 90 天（待合规确认） |
| 审计事件 | 本地最小摘要 | 设备、任务、策略、时间、结果计数、错误码 | 平台按甲方合规策略 |
| 敏感诊断 | 默认不落盘 | 默认不上报 | 仅经人工授权的受控支持流程 |

日志中必须对 `Authorization`、刷新凭证、激活码、Cookie、账号标识、手机号、消息正文及可能的个人信息进行脱敏；错误日志只能保留错误码、调用阶段、时间、`taskId`/`traceId` 和受限长度的非敏感上下文。支持人员如需排障包，客户端应让用户预览并明确同意，导出包加密且有过期时间。

## 10. 新增甲方适配器的扩展约定

### 10.1 适配器包契约

每个甲方/数据源使用独立 `adapterKey`，不得在 `first-party-whatsapp` 中通过大量 `tenantId` 条件分支兼容新甲方。适配器必须实现：

```text
Manifest() -> adapterKey, adapterVersion, supportedOperations, recordSchemas, requiredPermissions
Preflight(policy, localEnvironment) -> pass | blocked(errorCode)
Execute(task, policy, checkpoint) -> records, checkpoint, stats, terminalStatus
Normalize(sourceRecord) -> versioned record payload
Redact(error/log context) -> safe diagnostic payload
Cancel(taskId) -> graceful stop at safe checkpoint
```

适配器清单需声明最低宿主版本、支持平台策略版本、字段 schema 版本、所需本机权限、可处理的数据源类型和升级兼容范围。宿主只加载平台签名且与设备策略匹配的适配器；不允许从任务内容下载或执行任意脚本。

### 10.2 新甲方接入流程

1. 创建独立 `tenantId`、`bizLine`（复用时需说明）和 `adapterKey`，登记数据控制者、授权材料与负责人与失效日期。
2. 编写版本化 `recordSchema` 与字段白名单，明确每个字段的来源、目的、敏感级别、保留期和删除规则。
3. 定义 `capabilities` 和最小 `agentVersion`；平台以现有 `zt_bizline_capability` 思路管理可下发能力，后续 task 域据此过滤任务。
4. 通过模拟数据、批准的测试账号和异常用例验证 `Preflight`、去重、取消、断网恢复、令牌吊销和字段拒绝；不得使用未获授权的生产数据进行开发调试。
5. 经负责人、甲方业务方和安全/合规确认后，发布签名适配器和对应策略；灰度到指定设备并可一键停用。

### 10.3 后续服务端落地边界

后续实现建议新增 `resource` 的设备注册/状态能力与 `task` 的采集任务、租约、结果接收能力；表按既有约定采用 `zt_resource_*`、`zt_task_*` 前缀，带 `biz_line`，索引以 `biz_line` 打头。采集记录的跨域稳定形状放入 `server/contract`，具体采集逻辑留在 task/resource 对应领域，避免把客户端协议混入 `delivery` 看板领域。
