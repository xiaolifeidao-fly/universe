# 编排前后端 Docker Compose 与部署脚本：需求梳理

## 1. 任务目标

在仓库部署入口提供一套面向生产形态的 Docker Compose 编排与统一运维脚本，串联前置任务产出的 `client/web` 和 `server/web-api` 容器镜像。操作者应能在仓库根目录通过统一命令完成镜像构建、服务启动/停止、状态查看和日志跟踪，而无需分别进入前后端目录执行本地的 `start.sh`、`stop.sh` 或后台脚本。

本任务只负责编排、部署配置示例及脚本；依赖任务 `client-web-600e4cc537` 与 `server-03a0d67cd4` 先完成各自镜像、运行时配置和健康检查入口的实现。本阶段仅完成需求梳理，不创建 Compose、Dockerfile 或部署脚本。

## 3. 前置任务接口与依赖边界

后续实施本任务前，应先确认下列前置交付已落地并可独立验证；若未完成，Compose 不应以临时 Dockerfile、裸宿主进程或真实本地配置绕过。

1. **前端镜像任务（`client-web-600e4cc537`）**
   - 提供 `client/web/Dockerfile` 和 `.dockerignore`，可用 `docker build -t universe-client-web:local client/web` 构建。
   - 容器以非 root 前台 Node 进程启动，监听 `0.0.0.0:7893`，可通过 `PORT` 覆盖。
   - `SERVER_TARGET`、`APP_URL_PREFIX` 必须在容器运行时由 `process.env` 读取，不可被 `next.config.mjs` 的构建期 `env` 内联；真实 `.env` 不进入镜像。

2. **后端镜像任务（`server-03a0d67cd4`）**
   - 提供 `server/web-api/Dockerfile`、`server/.dockerignore` 与前台容器 entrypoint；构建命令在 `server/` 内执行 `docker build -f web-api/Dockerfile -t universe-web-api .`。
   - 运行时通过 `WEB_API_ADDR`、`WEB_API_SQLCONN` 等环境变量生成或选择无敏感默认值的 `configs/application.properties`；缺少必填 MySQL 连接配置时必须快速失败，不能回退到构建期写入的 DSN。
   - 容器默认监听 `10001`，并配置可用的 `/healthz` Docker healthcheck。

3. **本任务不负责的事项**
   - 不提供 MySQL、Redis、LLM、Ark 或其他外部依赖服务容器；这些连接由部署环境通过环境变量提供。
   - 不改变前端代理路由、后端 HTTP 路由、数据库模型、鉴权逻辑或 CI/CD 镜像发布流程。
   - 不复用本地后台进程脚本：容器服务由 Compose 生命周期管理，不应生成 PID 文件、使用 `nohup` 或重定向容器日志到文件。

## 4. 后续实施范围与文件布局

建议在仓库根目录新建独立的 `deploy/` 目录，作为唯一人工部署入口；具体文件名可微调，但最终应保持单一、清晰的入口，避免同一编排复制到前后端目录。

| 建议文件 | 职责 |
| --- | --- |
| `deploy/docker-compose.yml` | 定义 `web-api` 与 `client-web` 两个应用服务、私有网络、环境变量、端口映射、健康检查依赖和可选持久化卷。Compose 文件应可由根脚本通过 `-f` 显式引用。 |
| `deploy/.env.example` | 仅列出部署时需要填写的变量名、脱敏示例、用途和是否必填；不包含真实 IP、DSN、账号、令牌、密码或现有 `.env` 内容。 |
| `deploy/build.sh` | 严格模式下执行 Compose build；支持透传构建/Compose 参数的方式必须在 usage 中明确。 |
| `deploy/up.sh` | 启动前校验 Docker/Compose、部署环境文件和关键必填变量，随后执行 Compose `up -d --build`（或等效拆分命令）并输出服务访问与排障提示。 |
| `deploy/down.sh` | 以可预测方式停止并删除本编排容器和默认网络；默认不得删除命名卷或外部数据，只有显式确认参数才允许执行 `down -v`。 |
| `deploy/logs.sh` | 以 Compose `logs` 为唯一日志入口，默认/可选参数应支持服务过滤与跟随输出。 |
| `deploy/status.sh`（建议） | 包装 Compose `ps`，展示容器状态、端口和健康状态，减少直接记忆 Compose 文件路径的需要。 |
| `deploy/README.md`（建议） | 说明首次配置、日常命令、端口、外部依赖和故障排查；不得替代 `.env.example` 中的变量说明。 |

实施时需要评估是否额外提供根级 `Makefile` 或短包装脚本；若提供，其职责只能转发到 `deploy/*.sh`，不能形成第二套部署逻辑。

## 5. Docker Compose 编排要求

### 5.1 服务、构建上下文与命名

- Compose 至少定义两个服务：`web-api` 和 `client-web`；服务名是内部 DNS 名称，应稳定用于服务间通信。
- `web-api` 的 build 配置必须以 `server/` 为上下文，并指定 `web-api/Dockerfile`；不得错误地以 `server/web-api` 为上下文，否则相对 `replace` 的相邻 Go 模块不可用。
- `client-web` 的 build 配置以 `client/web` 为上下文，并使用其前置任务提供的 Dockerfile。
- 镜像名可通过 `.env` 中的命名空间/标签变量参数化；默认应为本地可辨识的 `universe-web-api`、`universe-client-web` 语义，不能依赖私有镜像仓库基础镜像或预构建镜像存在。
- 容器名不应成为服务发现或脚本判断的必要条件；优先使用 Compose 项目名、服务名与 `docker compose` 子命令，避免不同部署目录并发时产生硬编码容器名冲突。

### 5.2 网络与调用链

- 两个服务加入同一 Compose 私有 bridge 网络，例如 `universe`；网络应由 Compose 管理，不需要配置宿主机可访问的固定容器 IP。
- `client-web` 必须注入 `SERVER_TARGET=http://web-api:10001`（或由 `.env` 参数化后的等效内部地址），`APP_URL_PREFIX=/api`；不得使用 `127.0.0.1`、`localhost` 或宿主机端口访问后端。
- 浏览器访问流为：宿主浏览器 → `client-web:<前端宿主端口>` → Next API 路由 `/api/*` → `web-api:10001`。后端端口对宿主是否暴露应通过环境变量控制，但内部网络连通不能依赖该映射。
- 后端应设置 `WEB_API_ADDR=:10001`，保证容器内监听全部网卡；Compose 不能依赖后端配置文件中可能存在的本地端口。

### 5.3 端口与访问约定

- 默认前端宿主端口为 `7893`，映射容器端口 `7893`；以 `CLIENT_WEB_PORT`（命名可实现时微调）支持覆盖，避免与其他本地服务冲突。
- 默认后端容器端口为 `10001`。为减少攻击面，默认不需要向宿主发布该端口；若调试、健康排查或外部调用需要发布，使用明确的 `WEB_API_PORT` 可选变量映射，且 README 说明此端口不应作为前端内部调用依据。
- 应在 `.env.example` 清晰标注变量作用域：`CLIENT_WEB_PORT` 是宿主映射；前端 `PORT` 是容器监听；`WEB_API_ADDR` 是后端容器监听；`WEB_API_PORT` 是可选宿主映射，不等于服务发现地址。

### 5.4 启动顺序、健康检查与重启

- `web-api` 必须配置或继承前置任务已验证的 `healthcheck`，以 `http://127.0.0.1:10001/healthz` 判定健康；间隔、超时、重试和启动宽限应适配首次连接 MySQL 的时间。
- `client-web` 应使用 `depends_on` 的 `service_healthy` 条件依赖 `web-api`；这只协调首次启动顺序，前端代理错误处理仍须保留自身的可定位错误日志。
- 两个服务应采用适用于长期运行的重启策略（例如 `unless-stopped`）；若项目既有平台约定不同，以平台约定为准并在 README 中说明。
- 前端如无稳定轻量的健康端点，不得用首页 HTML 作为强制健康依赖的前置条件；本任务可只让后端健康检查参与启动编排。若前端镜像任务新增健康端点，可补充 `client-web` healthcheck。

### 5.5 配置、机密与持久化

- Compose 通过 `env_file`（例如被 git 忽略的 `deploy/.env`）或明确 `environment` 传入变量；真实部署文件必须不被 Git 跟踪，并由 `.env.example` 复制生成。
- 后端至少将 `WEB_API_SQLCONN` 标为必填；与现有后端 entrypoint 的最终变量命名保持一致。Redis、LLM、外部业务服务、默认管理员凭据等变量仅在前置任务 entrypoint 已支持时透传，不能由本任务凭空定义一套与后端不一致的配置协议。
- 禁止在 `docker-compose.yml`、`.env.example`、脚本、README、构建参数或日志中写入真实 DSN、用户名、密码、token、内网地址或现有 `application.properties` 的值。
- 本任务不创建数据库服务和数据卷。若后端后续需要上传文件、日志或其他运行数据持久化，应仅为明确的业务路径定义具名 volume，并同时说明宿主备份/清理责任；不得把整个应用工作目录或源码目录 bind mount 到生产容器。
- Compose 服务日志保持 stdout/stderr，由 `docker compose logs` 查看；不挂载或依赖仓库内 `logs/`、`run/` 目录。

## 6. 部署脚本行为与错误处理

所有 `deploy/*.sh` 均应使用以下基础约定，风格与 `server/web-api/*.sh` 一致：

```bash
#!/usr/bin/env bash
set -euo pipefail
```

并应以脚本所在目录反推出仓库根目录，不依赖调用者当前目录。每个脚本必须在失败时返回非零状态，不应以 `|| true` 吞掉关键命令失败；只有“服务未运行”“可选日志参数缺失”等明确幂等场景可以受控处理。

### 6.1 共同前置校验

- 检查 `docker` 命令及 `docker compose` 子命令可用；Docker daemon 不可达时给出可行动的错误信息。
- 检查 `deploy/docker-compose.yml` 存在，读取路径始终使用绝对或由 `ROOT_DIR` 推导的路径。
- `up.sh` 在启动前检查实际环境文件存在（例如 `deploy/.env`）；若不存在，提示从 `.env.example` 复制并退出，不自动生成含秘密的文件。
- 使用 `docker compose --env-file <实际环境文件> -f <compose 文件>` 的统一参数组装，确保所有脚本操作同一项目。可通过 `COMPOSE_PROJECT_NAME` 或脚本计算的项目名隔离不同部署实例，但命名规则必须文档化。
- 对 `WEB_API_SQLCONN` 等必填变量进行非空校验；绝不 `source` 无约束 shell 文件执行任意内容。可使用 Docker Compose 解析 `.env` 的机制，并在脚本中以安全方式读取/验证键值，或由 Compose `${VAR:?message}` 失败机制兜底；最终行为需在 README 中说明。

### 6.2 命令语义

| 命令 | 预期行为 |
| --- | --- |
| `./deploy/build.sh` | 执行 `docker compose build`；默认构建全部服务，可接受已文档化的服务名参数以仅构建指定服务。 |
| `./deploy/up.sh` | 验证环境后执行 `docker compose up -d --build`；启动后执行 `ps`，并对后端健康状态进行有限时轮询或提示执行 `logs.sh web-api`。任何等待超时都必须返回非零。 |
| `./deploy/down.sh` | 执行 `docker compose down --remove-orphans`；默认保留命名卷。仅传入明确的危险参数（如 `--volumes`）才可增加 `-v`，并在 usage 中标注会删除持久化数据。 |
| `./deploy/logs.sh [service ...]` | 默认输出全部服务日志；支持 `-f/--follow` 与一个或多个合法服务名，参数非法时打印 usage 并返回非零。脚本不读取容器日志文件。 |
| `./deploy/status.sh` | 执行 `docker compose ps`；退出码和输出直接反映 Compose 状态，方便自动化或人工排障。 |

- 脚本不要调用前后端已有的 `start.sh`、`stop.sh`、`build.sh`，也不要额外写入 PID、端口占用或 `nohup` 管理逻辑；镜像 Dockerfile 和 Compose 是容器生命周期的唯一责任方。
- 允许透传 Compose 项目名、镜像标签和端口等非敏感配置；脚本不得打印完整包含机密值的环境内容。

## 7. 示例环境文件要求

`deploy/.env.example` 至少应包含以下脱敏字段，并以注释说明哪些值需按环境修改。字段最终名称可以与 Compose 实现保持一致，但不能改变其语义。

```dotenv
# Compose 项目隔离名称；可选。
COMPOSE_PROJECT_NAME=universe

# 镜像标签；本地默认值可用于 docker compose build。
IMAGE_TAG=local

# 宿主机访问前端的端口。
CLIENT_WEB_PORT=7893

# 前端容器内监听端口与后端内部服务地址。
CLIENT_WEB_CONTAINER_PORT=7893
SERVER_TARGET=http://web-api:10001
APP_URL_PREFIX=/api

# 后端容器监听地址；默认必须绑定全部网卡。
WEB_API_ADDR=:10001

# 必填：由安全的部署密钥/环境管理系统提供，不填写真实连接信息到示例文件。
WEB_API_SQLCONN=replace-with-secure-mysql-dsn

# 可选：仅在后端容器 entrypoint 已支持这些同名变量时填入。
# WEB_API_REDIS_ADDR=
# WEB_API_REDIS_PASSWORD=
# LLM_API_KEY=
```

- 示例中的 `replace-with-secure-mysql-dsn` 仅是占位符；`up.sh` 和/或 Compose 应明确拒绝该占位符，避免误将示例值用于实际启动。
- 实际 `deploy/.env` 必须加入 `.gitignore`；若仓库已有全局忽略策略，也仍应以就近规则显式保护该文件。
- 不将 `client/web/.env`、`client/web/.env.dev` 或 `server/web-api/configs/application.properties` 作为 `env_file` 引入。

## 8. 验收标准与验证步骤

### 8.1 静态配置验证

在仓库根目录完成实现后：

```bash
cp deploy/.env.example deploy/.env
# 通过安全渠道编辑 deploy/.env，填写有效 WEB_API_SQLCONN；不要提交该文件。
docker compose --env-file deploy/.env -f deploy/docker-compose.yml config
```

验收：配置可解析，恰好包含 `web-api`、`client-web` 及其专用网络；前端 `SERVER_TARGET` 指向 `http://web-api:10001`；不出现本地真实配置、`localhost` 后端目标或明文秘密。

### 8.2 构建与启动验证

```bash
./deploy/build.sh
./deploy/up.sh
./deploy/status.sh
curl -fsS http://127.0.0.1:7893/
curl -fsS http://127.0.0.1:7893/api/healthz
./deploy/logs.sh web-api client-web
```

验收：

1. 两个镜像均使用各自前置任务规定的 Docker 构建上下文构建成功，且没有从宿主复制 `node_modules`、`.next` 或真实后端配置。
2. `web-api` 健康后 `client-web` 才开始；`docker compose ps` 显示后端健康、前端运行。
3. 浏览器/`curl` 通过 `7893` 访问前端成功，`/api/healthz` 经前端 Next API 代理到 Compose 网络中的 `web-api:10001` 并返回成功。
4. 未发布后端宿主端口时，前端代理仍可正常通信；如启用可选 `WEB_API_PORT`，其映射不影响内部 `SERVER_TARGET`。
5. `docker compose logs` 可获取两服务日志，仓库工作区不产生 PID 文件、后台日志文件或依赖容器内 `nohup` 的进程。

### 8.3 失败与清理验证

```bash
# 缺少实际环境文件时应失败且给出复制 .env.example 的提示。
rm -f deploy/.env
./deploy/up.sh

# 使用示例占位符或缺少 WEB_API_SQLCONN 时应在启动前/启动期失败。
cp deploy/.env.example deploy/.env
./deploy/up.sh

# 默认停止不删除持久化卷；仅显式传参才允许删除。
./deploy/down.sh
./deploy/down.sh --volumes
```

验收：缺失/占位配置不会启动到错误后端或使用镜像内秘密；所有失败返回非零并指向具体变量或恢复命令；默认 `down.sh` 不附带 `-v`，危险清理必须显式选择。

## 9. 实施决策与风险

1. **服务发现优先于端口映射**：容器内 `localhost` 仅表示自身，故前端到后端必须使用 Compose 服务名 `web-api`；发布 `10001` 到宿主仅用于可选调试，不是依赖条件。
2. **前置任务是实现前提**：本任务不能单独保证运行时前端变量不被构建期固化、也不能单独移除后端真实配置；在两个镜像任务完成前，Compose 验证只能停留在配置设计层，不能以不安全的临时文件替代。
3. **外部基础设施不纳入本编排**：当前应用启动已硬依赖 MySQL，Redis/LLM 等依赖随配置和业务功能变化；将其伪造为 Compose 本地服务会掩盖真实环境拓扑并超出任务边界。
4. **前端 API 健康路径需按实际代理行为验证**：`/api/healthz` 会由 Next API catch-all 路由改写为 `${SERVER_TARGET}${APP_URL_PREFIX}/healthz`。当前后端 `request.path=/api`，所以默认 `APP_URL_PREFIX=/api` 可形成 `/api/healthz`；若后端路由实际未带该全局前缀，则应在实施验证时修正 `APP_URL_PREFIX`，而不是通过宿主端口绕开服务发现。
5. **脚本幂等性与安全性并重**：`down.sh` 对未运行项目应安全退出；`up.sh` 可重复执行并收敛到期望服务状态；但缺少 Docker、Compose、环境文件或必填变量必须失败，不能悄悄降级。

## 10. 本阶段结论

后续实施应以 `deploy/docker-compose.yml`、`deploy/.env.example` 和严格模式的 `deploy/build.sh`、`up.sh`、`down.sh`、`logs.sh`（建议附 `status.sh`）作为唯一部署入口，编排 `client-web` 与 `web-api` 的私有网络、前端宿主端口、后端健康依赖和运行时环境变量。实际部署配置必须从无敏感示例复制并通过安全渠道填充外部 MySQL 等连接信息；不得复用工程中现有真实环境文件或本地后台启动脚本。
