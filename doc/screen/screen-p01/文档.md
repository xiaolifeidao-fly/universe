# 数据延迟大 · 几乎没有打标动作

## 背景

- 当前业务数据以 T+1 到达且存在字段、记录或状态缺失。数据尚未完整或不能确认最新状态时，运营人员无法判断是否应打标、打什么标以及是否可将标签用于下游流程。
- 前置任务《甲方白名单不额外增加》限定：数据只能通过甲方已授权的账号、接口和配额获取；接口受限、额度不足或数据超时后，应使用最近可用数据并转入待甲方确认、人工补录或文件补齐，不能通过新增账号、绕过频控或未授权采集解决。
- 因没有明确的数据准入、时效展示、待处理队列和复核闭环，现有打标动作基本不发生；即使发生也难以追溯标签基于哪一版数据、是否因迟到数据而需要复核。

## 目标

- 建立“可打标数据集”准入规则，仅将字段完整、来源可追溯、处于允许时效窗口且未被阻断的数据交给打标人员。
- 将 T+1、延迟、缺失、待补齐和数据更新等状态明确呈现在打标工作台，支持按优先级形成待打标队列，而不是把不确定数据静默混入正常任务。
- 支持人工打标、保存草稿、提交复核、审核发布、撤销/更正和迟到数据触发复核，使每个标签均可追溯至数据版本、操作人和审批记录。
- 对不满足准入条件的数据建立补齐与告警闭环；对持续延迟的数据量、打标吞吐和积压情况可监控、可统计。

## 范围

### 纳入范围

- 面向已授权接口、文件导入、人工补录等来源的业务数据，生成可打标、待补齐、待复核和不可打标状态。
- 打标任务队列、数据详情、标签定义与版本、人工操作、审核发布、回退更正和审计记录。
- 与数据采集优先级、缓存数据新鲜度、异常告警、人工/文件补齐流程的状态衔接。
- 打标质量、时效、积压及数据阻塞原因的看板指标与导出。

### 不纳入范围

- 新增甲方白名单账号、提升未获授权的调用额度、轮换账号规避频控，或任何未授权的数据抓取方式。
- 在本任务中建设模型训练、自动推断或通过模型自动发布标签；如后续需要，自动建议必须以本任务产生的已审核标签和版本化数据为输入，并独立评审。
- 替代前置任务的数据采集、配额管理、接口限流和人工补录能力；本任务只消费其标准化数据状态并发起补齐事项。

## 角色与权限

| 角色 | 权限 |
| --- | --- |
| 打标员 | 查看被分配且数据可打标的记录；创建、修改和保存草稿标签；提交复核；不得直接发布标签或修改原始数据。 |
| 复核员 | 查看待复核记录与证据；通过、驳回或要求补充；对迟到数据造成的影响进行复核；不得修改原始采集记录。 |
| 运营负责人 | 配置标签集、适用范围、优先级和服务时限；处理例外放行申请；查看指标和积压。 |
| 数据运营/补录人员 | 处理待补齐事项、导入或补录数据并提交确认；不得通过补录静默覆盖已确认原始数据。 |
| 审计管理员 | 查看标签、数据版本、审批、导入和权限操作日志；无业务标签编辑权限。 |

## 数据准入与状态

### 必备数据契约

每条候选记录至少应具备以下字段，缺失时不得进入“可打标”：

- 业务唯一键、业务类型/数据域、所属业务线和来源类型（`partner_api`、`file_import`、`manual`）。
- 数据版本或来源批次号、采集/导入时间、源数据业务发生时间、最近成功更新时间和完整度状态。
- 与当前标签集相关的必填业务字段，以及字段来源、确认状态和脱敏展示规则。
- 数据新鲜度状态、延迟原因（如接口限流、甲方未返回、文件待收、人工待补）和是否存在未解决差异。

### 打标准入规则

- 仅当记录完整度为“完整”、当前标签集所需字段齐全、来源可追溯、无未解决关键差异且处于对应业务类型的时效窗口内，状态才可为“可打标”。
- 对 T+1 数据，工作台必须显示业务发生日、数据到达时间、当前延迟时长和数据版本；不得以到达日冒充业务发生日。
- 状态为“部分缺失”“待甲方确认”“待人工补录”“存在差异”“数据过期”或“来源不可用”的记录，默认不可打标，并展示阻塞字段、责任方和建议补齐方式。
- 运营负责人可针对非关键标签发起例外放行；例外必须记录适用记录、风险说明、有效期、审批人和允许使用范围。涉及结算、风控或其他关键下游的记录不得例外发布。
- 同一业务唯一键同一标签集在一个数据版本内只保留一个生效标签版本；并发操作应加锁或提示冲突，避免重复打标。

### 状态流转

`待数据 → 待补齐/待确认 → 可打标 → 打标草稿 → 待复核 → 已发布`

- 数据缺失、过期或存在关键差异时进入“待补齐/待确认”，创建或关联前置任务约定的待处理事项。
- 打标员开始操作后进入“打标草稿”；草稿不得供下游正式使用。
- 提交后进入“待复核”；复核通过才成为“已发布”，驳回后回到“打标草稿”并保留意见。
- 已发布记录若收到更高版本数据、补录、对账结论或来源撤回，进入“待复核（数据更新）”；复核前下游必须能识别原标签对应的数据版本与风险状态。
- 取消、失效或更正标签时，不得覆盖历史结果；应生成新的标签版本并记录原因、操作者、审批人和生效时间。

## 功能需求

### 可打标队列

- 按业务优先级、数据新鲜度、到期时间、阻塞状态、分配状态和提交时间生成队列；P0/P1 的关键记录优先于可延后的运营类记录。
- 提供“可打标、待补齐、待复核、已发布、数据更新待复核、超时”视图，并支持按业务线、数据域、来源、标签集、责任人和日期筛选。
- 队列项展示业务唯一键、脱敏摘要、业务发生时间、数据到达时间、延迟时长、完整度、数据版本、优先级、当前状态和阻塞原因。
- 对相同业务唯一键、标签集和数据版本去重；重复任务合并到同一工作项，保留请求来源和优先级。
- 支持领取、分配、退回和超时提醒；分配变更记录操作日志，离岗或超时任务可由负责人重新分配。

### 数据详情与证据

- 在打标页面展示允许当前角色查看的原始字段、字段完整度、字段来源、数据版本、更新时间、差异状态和历史变更摘要。
- 必填字段缺失或超出时效窗口时，禁用提交复核，并明确显示缺失字段、阻塞原因、补齐责任方及可跳转/关联的补齐事项。
- 标签操作时固定引用当前数据版本；数据在编辑期间更新时提示比较差异，要求基于新版本重新确认后才能提交。
- 敏感字段按权限脱敏展示；不得在标签备注、导出内容或普通操作日志中复制未脱敏原值。

### 标签定义与打标操作

- 标签集按业务域、适用记录类型和版本管理；每个标签定义名称、说明、标签值类型、必填条件、互斥/依赖规则、适用时效和是否需要复核。
- 支持单选、多选、枚举、布尔、数值区间和文本备注等受控标签值；自由文本需设置长度、敏感信息校验和可见范围。
- 对互斥标签、必填标签、依赖条件和不允许的值组合进行实时校验；校验不通过不得提交。
- 支持暂存草稿、批量打标和快捷复制；批量操作必须先显示受影响记录数、统一标签值、无法应用的记录及原因，并对每条记录写入独立审计记录。
- 标签备注应填写依据或引用证据类型；若结论来自人工判断，需标记判断依据和不确定性，不得伪造数据来源。

### 复核、发布与更正

- 复核队列展示提交人、标签变更、数据版本、证据、优先级和超时时间；复核员可通过、驳回或要求补充并填写理由。
- 高风险、结算关键、例外放行或数据延迟超过阈值的标签必须双人复核；一般标签是否抽检由标签集配置决定。
- 发布后向已授权下游提供标签值、标签版本、数据版本、生效时间、质量/风险状态；草稿和被驳回标签不得作为正式输入。
- 当数据更新影响标签字段时，系统比较字段变更与标签依赖关系：无影响可保留；有影响则自动创建复核事项并标记原标签为“数据已更新待复核”。
- 更正、撤销和失效均需填写原因；如已向下游发布，记录下游通知/重新消费状态，确保变更可追踪。

### 补齐与异常闭环

- 不可打标记录应按业务唯一键、缺失字段、数据版本和阻塞原因关联或新建补齐事项，避免同一问题重复派发。
- 补齐事项接收来自前置任务的数据状态、最近错误、建议补齐方式和责任方；处理完成后重新执行准入检查，再进入可打标队列。
- 对甲方接口限流、额度不足或缓存过期导致的延迟，只能展示前置任务提供的状态并等待授权通道恢复或人工/文件补齐；不得触发绕过频控的自动重试策略。
- 当数据延迟、待补齐积压或打标超时超过阈值时，通知对应责任人；告警应合并去重，并保留确认、处理和恢复记录。

### 指标与审计

- 看板至少统计：可打标率、数据完整率、T+1 到达率、数据延迟分位值、待补齐量、打标完成率、平均打标时长、复核通过率、驳回率、超时量和队列积压时长。
- 指标可按业务线、数据域、来源、标签集、优先级和时间范围拆分；所有指标注明统计口径、时区和数据更新时间。
- 审计日志记录数据准入判定、队列分配、草稿保存、标签变更、复核、发布、例外放行、补录关联和导出操作，包含操作者、时间、对象标识、前后状态/版本及原因。
- 支持按权限导出任务和指标；导出数据遵循字段脱敏、最小权限和审计留痕要求。

## 业务规则与验收标准

1. 对任一关键标签记录，缺失必填字段、存在未解决关键差异或数据超过标签集时效窗口时，系统必须阻止提交复核，并在页面显示具体阻塞原因。
2. 对一条完整且在时效窗口内的记录，打标员可保存草稿；提交后未经规定复核不得向正式下游发布。
3. 已发布标签收到影响标签依赖字段的新数据版本后，系统应在该记录上生成待复核事项，并保留原标签和新旧数据版本的关联。
4. 同一业务唯一键、标签集和数据版本的并发打标不得产生两个生效结果；冲突操作必须被拒绝或提示合并。
5. 每一次标签创建、修改、复核、发布、撤销和例外放行均可追溯至操作人、时间、数据版本和原因；历史版本不可被覆盖删除。
6. 接口额度不足、频控或账号异常时，系统不得新增未授权采集或规避频控动作；不可打标记录必须转入待补齐/待确认并可追踪。
7. 指标可区分“因数据不完整/延迟不可打标”与“已具备可打标数据但未处理”，使运营可定位积压根因。

## 待确认项

- 各业务域和标签集分别依赖哪些字段？哪些字段缺失会绝对阻断打标，哪些仅影响标签置信度？
- T+1 的具体到达承诺、标签集时效窗口、P0/P1/P2/P3 的处理服务时限和超时阈值分别是什么？时区是否统一使用 `Asia/Jakarta`、`Asia/Shanghai` 或业务发生地时区？
- 第一批需要上线的标签集、标签值、互斥/依赖规则、风险级别和下游使用场景是什么？
- 哪些标签、业务类型或例外放行需要双人复核？复核角色、抽检比例和驳回时限如何定义？
- 数据更新后的标签影响判定由字段级依赖配置还是人工规则维护？原标签在复核期间是否允许下游继续使用？
- 当前人工补录、文件导入、甲方确认的责任人、SLA、通知渠道和关闭条件是什么？
- 标签与数据审计日志、敏感字段、导出文件的保存期限、脱敏规范和访问审批要求是什么？
