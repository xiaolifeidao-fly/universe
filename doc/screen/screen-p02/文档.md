# 无人群分层

## 背景

- 现有案件进入处理队列后缺少统一、可解释的价值判断，低价值、时效已过或信息不足的案件与高价值、强时效案件被分配相同的人工跟进、外呼/消息触达和复核动作。
- 这种“一案一策缺失、所有案件同一套动作”的方式会挤占有限的坐席、触达通道和复核产能，使高价值案件不能在有效窗口内优先处理，也无法量化低价值案件消耗的产能。
- 前置任务《数据延迟大 · 几乎没有打标动作》已定义数据完整度、时效、标签发布和数据更新复核规则。本任务只消费已发布标签及其数据质量状态；不得把缺失、过期或未复核的数据伪装成高价值信号。

## 目标

- 建立面向单个案件的可配置人群分层机制，按业务价值、紧急度、触达可行性、风险/合规约束和数据可信度形成可解释的处置层级。
- 为每个层级配置不同的默认动作、触达节奏、人工介入等级、复核要求和停止条件，使有限产能优先服务高价值且仍可行动的案件。
- 让运营人员可查看“为何归入该层、哪些事实和标签参与判断、推荐何种动作、何时需要重算或人工复核”，并能对例外决策全程审计。
- 提供分层规模、动作消耗、有效触达、转化/回收、时效损失和人工覆盖率等指标，用于持续校准规则和容量配置。

## 范围

### 纳入范围

- 基于案件基础信息、已发布标签、数据完整度/新鲜度、案件状态、历史合法触达结果和经批准的业务规则，对案件计算分层结果。
- 分层规则版本、阈值、优先级、互斥条件、阻断条件、推荐动作矩阵、产能配额、人工覆盖和例外处理。
- 案件分层队列、案件详情中的分层解释、人工复核/调整、重算、动作领取/执行反馈和审计记录。
- 分层结果向后续触达、人工任务或编排模块提供标准化的“可执行动作建议”；下游仍需独立校验其自身权限、频控、同意状态和合规限制。
- 以分层、动作和结果为维度的运营看板、导出及告警。

### 不纳入范围

- 本任务不新建未授权数据源、账号或采集方式，也不绕过甲方接口额度、频控和数据使用范围。
- 本任务不直接发送消息、拨打电话、修改案件核心业务状态或替代后续触达执行模块；仅生成可被下游消费的建议和优先级。
- 本任务不以黑箱模型自动决定强制处置。若后续接入模型，其输出只能作为建议特征，必须受本任务的硬性阻断、人工复核、版本留痕和可解释要求约束。
- 本任务不以分层结果作出授信、拒绝服务、定价、处罚等高影响自动决定；涉及此类结果必须由具备授权的业务流程另行评审和确认。

## 角色与权限

| 角色 | 权限 |
| --- | --- |
| 运营负责人 | 配置、发布和停用分层规则及动作矩阵；设置容量配额、服务时限和告警阈值；审批高风险例外。 |
| 案件运营人员 | 查看本人有权限的案件及分层解释；按允许的推荐动作领取和处理案件；提交人工调整申请，不得修改已发布规则。 |
| 复核员 | 复核高价值、高风险、规则冲突和人工调整案件；通过、驳回或退回补充，不得篡改原始数据和历史分层版本。 |
| 策略/数据运营人员 | 维护特征映射、标签依赖、阈值草案和回测样本；无权自行将草案发布到生产。 |
| 审计管理员 | 查询规则、分层、动作建议、人工调整、审批和导出日志；无业务编辑权限。 |

## 分层数据契约

### 输入条件

每次分层计算必须绑定不可变的输入快照，至少包含：

- 案件唯一键、所属业务线、业务类型、当前案件状态、创建/到期/业务发生时间和责任归属。
- 参与判断的已发布标签及标签版本、标签来源、发布时间、置信/确认状态；草稿、待复核或已撤销标签不得作为正式分层依据。
- 数据版本、完整度、新鲜度、延迟原因和关键字段差异状态；需要使用的数据字段及其脱敏展示规则。
- 合法可用的历史动作摘要，例如最近触达时间、结果、次数、退订/拒绝标志和冷却期；不得把完整敏感内容复制到分层说明或导出中。
- 适用的规则集版本、动作矩阵版本和计算时间。

### 前置阻断

- 数据完整度不满足该规则集的关键字段要求、存在未解决关键差异、输入超过允许时效或标签仍待复核时，案件不得进入可执行层级，状态为“待补齐/待复核”，并明确阻断字段、责任方和重算触发条件。
- 存在退订、明确拒绝联系、法定/业务禁止触达、冻结、关闭、已结案或其他合规禁止标记时，任何推荐动作均必须为“停止触达/转人工核验”；高价值分数不得覆盖该硬性限制。
- 处于触达冷却期、已达到该业务类型最大触达次数或没有可用授权通道时，案件可保留价值层级，但必须标记为“暂不可执行”，不得再次进入待执行队列。

## 分层模型与规则

### 分层维度

第一期采用规则驱动、可配置且可解释的方式，不以单一分数直接决定动作。每个规则集应按以下维度计算或判定：

| 维度 | 含义 | 典型依据 |
| --- | --- | --- |
| 业务价值 | 案件在当前业务目标下的预期价值或损失影响 | 案件金额/规模、客户等级、关键业务节点、已确认价值标签。 |
| 时效紧急度 | 继续等待导致价值显著下降的程度 | 到期时间、逾期天数、剩余有效窗口、承诺处理时限。 |
| 处置可行性 | 采用建议动作后获得有效结果的前提是否具备 | 已授权渠道、近期成功触达、联系人可用性、冷却期和触达上限。 |
| 风险与合规 | 是否需要限制、转人工或停止动作 | 退订/拒绝、投诉、敏感案件标记、异常/争议状态、权限限制。 |
| 数据可信度 | 输入是否足以支持当前分层 | 数据完整度、新鲜度、标签审核状态、关键差异和来源可追溯性。 |

- 规则必须区分硬性条件与可排序条件：硬性阻断优先于任何价值、紧急度或可行性结果；可排序条件只在案件可进入分层后用于比较优先级。
- 每项规则需配置适用业务线/业务类型、字段或标签依赖、判定逻辑、阈值、权重或优先级、失效时间、规则负责人和发布状态。
- 如采用综合分数，必须记录每个维度得分、权重、命中规则和最终排序依据；不得只保存总分。不同业务类型可使用不同阈值，但不得共用语义不一致的标签字段。

### 建议层级

第一期默认使用以下五个互斥处置层级；具体阈值由运营负责人按业务类型配置并经发布流程生效：

| 层级 | 含义 | 默认处置方向 |
| --- | --- | --- |
| `S0_阻断` | 数据、状态或合规条件不允许执行 | 停止自动动作；转补齐、合规核验或人工处理。 |
| `S1_优先` | 高业务价值且处于有效时限，具备可执行条件 | 占用优先产能，按最短 SLA 进入人工或已批准的高优先级动作队列。 |
| `S2_重点` | 有明确价值和可行动性，但紧急度或价值低于 S1 | 在标准 SLA 内安排适配动作；容量紧张时排在 S1 之后。 |
| `S3_培育` | 价值/时效较低但仍可能产生结果 | 采用低成本、低频动作或延后处理；不得占用 S1/S2 预留人工产能。 |
| `S4_观察` | 暂无足够价值或行动信号，且不存在硬性阻断 | 不主动消耗人工/高成本通道；仅保留观察、数据更新后重算或按周期复评。 |

- `S0_阻断` 是处置状态，不参与可执行优先级排序；`S1` 至 `S4` 是业务分层。系统在页面和接口中必须同时返回“层级”和“可执行状态”，避免把高价值但受冷却期限制的案件误认为可立即执行。
- 相同层级内按剩余时效、业务价值、规则优先级、最后有效触达时间和入队时间排序；排序字段及同分规则必须配置化并记录在规则版本中。
- 同一案件在同一业务线、业务类型和有效输入快照下只能有一个当前生效的分层结果；新结果生效后历史结果只读保留。

## 功能需求

### 规则与动作矩阵管理

- 支持以草稿、待审批、已发布、已停用管理规则集和动作矩阵版本；已发布版本不可原地修改，变更必须创建新版本并说明生效时间、影响范围、变更原因和回滚版本。
- 支持配置层级准入、阻断条件、维度规则、阈值、排序、分层 SLA、渠道/人工产能配额、最大触达次数、冷却期、推荐动作和停止条件。
- 每个层级可配置零个或多个候选动作，动作至少包括动作类型、目标渠道、优先级、执行窗口、频率上限、所需授权/同意状态、人工复核要求和失败后的下一步。候选动作按优先级顺序输出，但下游只能执行通过自身校验的一项。
- 发布前必须对规则依赖字段、标签版本、互斥条件、阈值冲突、无动作层级、动作越权、容量总量和回滚版本进行校验；校验失败不得发布。

### 分层计算与队列

- 对满足输入条件的案件执行首次计算；数据、标签、案件状态、触达结果、合规标记、规则版本或时间窗口变化时，按事件触发或定时批量重算。
- 计算结果至少包含：案件唯一键、分层层级、可执行状态、综合排序值（如适用）、维度判定、命中/未命中规则、阻断/降级原因、推荐动作列表、输入快照版本、规则版本、计算时间和下次复评时间。
- 为 `S1`、`S2`、`S3` 分别建立待执行队列；队列须显示剩余 SLA、推荐动作、是否已领取、阻断/冷却原因和最近重算时间。`S4` 不进入默认人工待办，`S0` 进入补齐或核验队列。
- 当案件由低层级升至 `S1`/`S2`，或距离到期阈值进入配置的紧急窗口时，应提升队列优先级并通知责任人；当降级、结案、进入冷却或受合规限制时，必须撤销未领取的执行建议。

### 案件详情与人工复核

- 案件详情必须展示当前层级、可执行状态、推荐动作、排序位置、规则版本、输入数据版本、命中理由、未命中关键条件、阻断原因、历史层级变化和已执行动作摘要。
- 分层解释采用“事实 → 规则 → 结论”格式，例如“剩余有效窗口小于 24 小时（事实）→ 命中紧急规则 R-12（规则）→ 提升为 S1（结论）”；不得展示无来源的推断性结论。
- 运营人员可发起人工调整或动作例外申请，必须填写目标层级/动作、原因、有效期和支持证据。涉及 `S1` 升级、高风险动作、突破默认频率/冷却限制或从 `S0` 放行的申请，必须由复核员或运营负责人审批。
- 人工调整只覆盖指定案件和有效期；输入数据、合规状态或规则版本变化后必须重新校验。任何硬性合规阻断均不得通过普通人工调整解除。

### 产能与动作保护

- 为人工、各触达渠道及复核能力分别配置每日/班次容量、并发上限和 `S1`/`S2` 预留配额；`S3` 不得在预留配额未释放前占用高优先级产能。
- 队列派发前检查当前容量、动作上限、冷却期、案件状态和下游授权条件；不满足时标记具体原因、下次可执行时间并保留在相应观察或等待队列。
- `S1` 超过 SLA 未被领取、`S1` 预留产能不足、`S2` 持续积压、动作失败率异常或分层重算积压时，系统应告警到配置的责任人，并给出受影响层级和案件数量。
- 对同一案件、同一动作类型和同一有效窗口须去重；并发领取、重算或执行反馈不得创建重复动作建议或重复占用产能。

### 结果回流与审计

- 下游执行模块应回传动作领取、执行、送达/接通、成功、失败、拒绝、退订、投诉、人工关闭等标准结果；回流结果用于更新案件可行性、冷却期、触达上限和后续重算。
- 审计日志记录规则创建/审批/发布/回滚、每次计算、队列进出、动作建议生成或撤销、人工调整、审批、容量拦截、动作回流和导出，至少包含操作者/系统、时间、案件标识、规则/输入版本、前后结果和原因。
- 导出和看板按最小权限展示，敏感字段、联系方式和完整交互内容遵循数据契约中的脱敏规则；导出行为必须可审计。

## 状态流转

```text
待分层
  ├─ 输入不完整 / 待复核 / 合规阻断 → S0_阻断（待补齐、待核验或停止触达）
  └─ 输入合格 → 规则计算 → S1 / S2 / S3 / S4
                                      ├─ 可执行 → 对应待执行队列 → 领取/执行 → 结果回流 → 重算
                                      ├─ 冷却、容量或授权受限 → 暂不可执行 → 到期或条件变化后重算
                                      └─ 数据、标签、案件或规则变化 → 重算 → 新层级生效
```

- 已结案、撤销、合规停止或超过业务有效期的案件必须退出待执行队列，并保留最终分层和退出原因。
- 规则发布不应直接覆盖正在执行的动作；已领取动作由下游按其执行状态完成、取消或人工核验，未领取建议根据新规则重新生成。

## 指标与验收标准

### 指标口径

- 分层规模：各业务线、业务类型、层级和可执行状态下的案件数量及占比。
- 产能效率：各层级的人工工时、触达次数、复核量、单位有效结果成本和高优先级预留配额使用率。
- 业务结果：各层级的领取率、及时处理率、有效触达率、转化/回收结果（以业务确认口径为准）、结案率和超时率。
- 质量与风险：被人工调整率、复核驳回率、规则命中异常率、重复动作拦截数、合规阻断数及因数据不完整导致的不可执行数。
- 时效：从数据可用到分层、从分层到领取、从领取到结果回流的耗时分布，以及 `S1`/`S2` SLA 违约数量。

### 验收标准

1. 对输入完整、无合规阻断的案件，系统能依据已发布规则生成唯一的当前层级、可执行状态、排序理由、输入版本和规则版本；同一输入重复计算不得产生不同结果或重复待办。
2. 对缺失关键数据、标签待复核、存在关键差异或命中停止触达条件的案件，系统必须阻止进入可执行动作队列，并展示具体阻断原因和后续处理入口。
3. `S1`、`S2`、`S3` 的动作矩阵和容量策略可独立配置；当容量紧张时，`S3` 不得挤占配置给 `S1`/`S2` 的预留人工或渠道产能。
4. 每个推荐动作都能追溯到层级、规则版本、输入快照、授权/冷却检查和停止条件；并发派发或重复回流不会生成重复动作建议。
5. 数据、已发布标签、案件状态、触达结果、合规标记或规则版本变化后，受影响案件会在配置时限内重算；已不适用的未领取建议被撤销或失效。
6. 人工调整、例外放行和规则发布均需记录申请人、审批人、理由、证据、有效期和前后结果；普通调整不能绕过硬性合规阻断。
7. 运营看板可区分高价值案件未及时处理、低价值案件产能消耗、数据问题导致的不可执行和渠道/容量限制导致的等待，并支持按权限导出审计数据。

- 下游执行模块能够回传哪些动作结果？结果字段的标准枚举、回流时效、失败重试边界和人工关闭条件是什么？
- 规则灰度范围、发布窗口、回测样本、成功判定阈值和紧急回滚负责人如何确定？
- 分层解释、审计日志、导出数据和联系方式的保留期限、访问权限与脱敏规则是什么？
