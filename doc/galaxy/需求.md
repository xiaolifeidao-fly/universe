# Galaxy 共享算力池 · 需求文档

## 1. 背景与目标

### 1.1 背景

任务面板「设计初衷」第四个场景描述了这样一件事：有人机器闲置，有人任务排队，但两边的算力无法互通；用户之间直接共享机器又要自行解决连接、授权与信任问题。现有系统里，每个用户只能用自己的机器执行自己的任务：命令队列按 `user_id` 分区，领取、租约、工作目录映射全部绑定本人，`requireOnlineCommandWorker` 在提交时就要求本人机器在线。

同时，`galaxy/ai-bridge` 已经实现了节点侧的中转能力：用本机 Claude Code / Codex 订阅登录态，把 Anthropic Messages 与 OpenAI Responses 请求原样转发到上游，带 token 鉴权、scope 与三层并发闸门。缺的是把这些分散在各台机器上的能力汇聚成一个公共池，并让其他用户能付费使用。

### 1.2 目标

建设 Galaxy 共享算力池，形成一个**双边市场**：

- **算力提供者**（挂机用户）把本机订阅能力或本机计算能力的一部分授权到共享池，自主决定贡献哪几种、贡献多少、什么时段贡献。
- **算力使用者**（消费者）购买额度后，通过平台把请求转发到提供者的机器上执行，结果经平台回传到自己的客户端。
- **平台**代为鉴权、调度、计量、结算与风控，双方不直接连接、互不知晓对方身份。

同一套通道要能承载三类业务形态，并为后续业务（多模态、视频类）预留扩展：

1. **中转站**：LLM API 请求原样转发（Claude、Codex 订阅）。
2. **任务宇宙**：现有交付任务面板的 agent 会话，带业务上下文，可续接。
3. **视频养号 / 视频剪辑**：长任务、大文件、进度回传、多步骤流水线。

### 1.3 成功标准

- P0：至少 3 个提供者节点挂机并被消费者真实使用，请求全程经平台调度，token / 时长 / 次数三维额度同时生效并可对账。
- P1：消费者可购买额度并按用量扣费，提供者可查看贡献与收益，失败请求按规则不计费。
- P2：新增一个业务（如视频剪辑）只需新增契约、适配器与节点 provider，通道层与传输层不改动。

## 2. 术语表

| 术语 | 定义 |
|---|---|
| Hub（中转站） | 平台侧服务，进程为 `galaxy-api`。对上接收消费者请求，对下持有节点通道，负责鉴权、放置、额度、计量、结算 |
| 节点（Node） | 提供者的一台机器上运行的 `ai-bridge` pool 模式进程。一台机器一个节点 |
| 贡献（Contribution） | 节点上被主人勾选共享出去的一种能力，如「Claude / sonnet 系列」。**供给的最小单元**，座位、额度、队列、绑定都按贡献组织。一个节点可有多个贡献 |
| 座位（Seat） | 一个贡献同时服务的消费者数量上限。默认 3。座位是消费者与贡献之间的粘性绑定，不是并发数 |
| 座位并发 | 一个座位上同时在跑的请求数上限，默认 2 |
| 通道（Lane） | 节点拉取工作的逻辑队列，一个贡献一条通道 |
| 原语（Primitive） | 通道层对工作形态的三种抽象：relay（同步流式）、session（有状态多回合）、job（异步长任务） |
| kind | 一种业务能力的注册名，如 `llm.chat`、`delivery.task`、`video.edit.render`。kind 决定原语、计量单位、亲和策略、schema |
| 工作单元（WorkUnit） | 通道层的统一信封，一次请求 / 一个回合 / 一个任务 |
| 产物（Artifact） | 大文件输入或输出，存 OSS，通道中只传引用 |
| 计量单位（MeterUnit） | 额度与计费的度量，如 `llm.output_tokens`、`time.seconds`、`llm.calls`、`video.output_seconds` |
| 三维额度 | 提供者授权的 token / 小时 / 次数三个上限，同时生效，任一触顶即停止接单。是 LLM kind 的默认单位组合 |
| 窗口（Window） | 额度的重置周期：day / week / month / total |
| 亲和（Affinity） | 消费者请求是否倾向或必须回到同一贡献：none / soft / hard |
| 上下文账本（Ledger） | 服务端保存的 session 业务上下文：回合摘要、工具调用、改动文件、产物引用 |
| 适配器（Adapter） | Hub 侧按 kind 解释业务参数、取路由键、写回响应的模块 |
| Provider | 节点侧按 (kind, provider) 真正执行工作的模块 |
| 契约（Contract） | Hub 与节点共用的 JSON Schema 与 kind 注册文件 |
| 算力密钥 | 消费者购买额度后由平台签发的 `sk-` 密钥，绑定额度余额、有效期与允许范围；请求凭它进入共享池 |
| 同意记录 | 提供者加入时对条款的明示同意、消费者密钥签发时对数据告知的确认，均记录版本与时间 |
| 积分（Credit） | 提供者收益的记账单位，P1 只记账，P2 可提现 |

## 3. 角色

| 角色 | 描述 | 主要诉求 |
|---|---|---|
| 算力提供者 | 拥有 Claude / Codex 订阅或本机计算资源的用户 | 自主选择贡献什么、贡献多少；随时能停；机器不被滥用；看得到贡献与收益 |
| 算力使用者 | 需要 LLM / agent / 视频处理能力的用户或团队 | 用官方 SDK 就能接；延迟可接受；按量付费；用量透明；失败不扣费 |
| 平台运营 | 运营共享池的团队 | 池子水位可见；结算可对账；作弊可识别；节点可封禁；争议可处理 |
| 业务开发者 | 接入新业务形态的研发 | 只写契约、适配器、provider，不碰通道 |

## 4. 范围

### 4.1 本期范围（P0）

- `ai-bridge` 新增 pool 模式：不监听端口、纯出站、贡献配置、三端点拉取与回传。
- `server/service/galaxy` 与 `server/galaxy-api`：节点通道、消费者密钥、放置、单位化额度引擎、平台侧计量、账本骨架。
- 适配器 `relay`（kind `llm.chat`，Anthropic 与 OpenAI 两个协议族）。
- 消费者通过官方 SDK 兼容路径接入。
- Redis 控制面、MySQL 权威存储、OSS presigned 基础设施。
- 提供者与消费者的用量查询接口；平台后台只读接口。

### 4.2 后续范围

- P1：额度商品、支付、双账本结算、失败退款、争议处理；适配器 `delivery`（session 原语）与上下文账本的回合级同步；节点信誉与随机抽检。
- P2：job 原语、适配器 `videofarm`、数据引力、DAG 业务服务；对外开放注册；提现与分成；manager 后台完整功能。

### 4.3 不做的事

- 不在节点上开放任何入站端口，不要求提供者配置公网 IP 或端口转发。
- 不把订阅凭据（OAuth token、auth.json）上传到平台或任何第三方。
- Hub 不代理产物字节，不在 Redis 中存放响应内容。
- 不做「借用订阅额度但在消费者本机执行」的形态（CLI 不是可转发的端点）。
- 不改造现有 `zt_delivery_command` 命令通道，任务宇宙先以新适配器接入，老通道原地运行。
- 不合成 Claude Code / Codex 身份，只透传真实客户端请求（沿用 ai-bridge 已知边界）。

## 5. 业务模式

### 5.1 中转站（relay）

- 消费者用 Anthropic SDK / OpenAI SDK，把 `base_url` 指向 Hub，带 Hub 签发的密钥。
- 请求原样转发到提供者机器，由其订阅登录态向上游发起，响应（含 SSE 流）原样回传。
- 上下文由消费者客户端自持（每次带全量 messages），允许换节点；为了 prompt cache 命中优先回原节点。
- 唯一硬约束：OpenAI Responses 的 `previous_response_id` 引用上游账号侧状态，必须回原节点。

### 5.2 任务宇宙（session）

- 现有交付任务面板的执行阶段（需求梳理、拆解、动作执行、测试等）以「回合」为单位经共享池执行。
- 上下文分三层：业务层在服务端账本，执行层在节点 CLI thread，工作区层在 Git 远端。
- 会话活着时钉在同一贡献；节点掉线或额度耗尽时可迁移到新节点续接。

### 5.3 视频养号 / 视频剪辑（job）

- 任务时长分钟到小时级，输入输出为 GB 级文件，过程有进度与预览。
- 输入输出全部走 OSS 引用，节点直传直取。
- 业务由多个步骤组成 DAG（探测、转码、剪切、混音、字幕、渲染），编排在业务领域服务中，每个步骤是一个独立的 job。
- 步骤幂等，可在任意节点重跑；优先落在缓存了输入产物的节点。

### 5.4 未来：多模态模型

- 同步的图片 / 音频 API 走 relay 原语（提高该 kind 的内联体积上限）。
- 异步的视频生成 API（提供者持有其订阅或 API key）走 job 原语，节点侧用通用 `job-api` provider 骨架加每家适配。

## 6. 功能需求

### 6.1 算力提供者

| 编号 | 需求 | 说明 |
|---|---|---|
| P-01 | 配对加入 | 平台出一次性配对码，节点 CLI 换取长期 node token；撤销即断连 |
| P-02 | 能力探测 | 节点探测本机可用能力（Claude 登录态、Codex 登录态、ffmpeg、GPU 等），探测结果仅供主人选择，不自动申报 |
| P-03 | 选择贡献 | 主人从探测结果中勾选贡献哪几种；每种贡献独立配置；未勾选的能力 Hub 不可见 |
| P-04 | 模型白名单 | 每个贡献可配置 allow / deny 模型模式（如只放 sonnet、不放 opus） |
| P-05 | 三维额度 | 每个贡献配置 token / 小时 / 次数上限与窗口（day / week / month / total），三者同时生效，任一触顶停止接单 |
| P-06 | 座位 | 每个贡献配置同时服务人数（默认 3）与每座位并发（默认 2）；平台可设上限 |
| P-07 | 挂机时段 | 每个贡献可配置只在指定时段接单，时段外自动排空 |
| P-08 | 运行时调整 | 增删改贡献、暂停 / 恢复不需重启节点；停掉的贡献排空在途后释放座位 |
| P-09 | 紧急闸 | 一键停挂；拉黑某个消费者（匿名标识）；在途请求按失败语义处理 |
| P-10 | 额度预警 | 到 80% 预警，100% 停止新单但不中断在跑请求 |
| P-11 | 上游限流感知 | 节点被上游 429 时自动临时退出候选，不影响同机其他贡献 |
| P-12 | 凭据失效感知 | 贡献的登录态失效时自动摘除并通知主人 |
| P-13 | 用量与收益 | 查看每个贡献的实时余量、历史用量、贡献记录、收益（P1） |
| P-14 | 执行记录 | 查看「我的机器上跑过什么」的匿名化日志（kind、时间、用量、结果），不含消费者内容 |
| P-15 | 无入站端口 | pool 模式不监听任何端口，攻击面仅为「主动连了谁」 |
| P-16 | 加入同意 | 加入共享池前强制阅读并同意条款（订阅条款风险、数据经本机处理、平台调度与结算规则），记录同意版本与时间；未同意不签发配对码 |
| P-17 | 授权对象是平台 | 提供者把贡献授权给平台，不指定消费者；请求路由到哪个贡献由平台算法决定 |

| C-04 | 子会话亲和 | 可选请求头 `x-galaxy-session` 让同一密钥下的不同 agent 分别绑座位 |
| C-05 | 排队 | 无可用贡献时排队至多 `maxWaitMs`，超时返回 503 与 `retry-after`，不计费 |
| C-06 | 产物上传下载 | 申请 presigned PUT 上传输入；用引用获取 presigned GET 下载输出 |
| C-07 | 会话与回合 | 任务宇宙类业务：创建 session，按 seq 提交回合，读取回合事件与上下文摘要 |
| C-08 | 长任务 | 提交 job，查询进度与预览，取消，获取产物引用 |

| C-10 | 购买与签发 | 购买额度包后签发带额度与有效期的算力密钥（P1；P0 由后台为内测用户签发） |
| C-11 | 失败不扣费 | 上游故障、节点故障、排队超时不扣费；消费者主动断开按已产出计 |
| C-12 | 匿名 | 不知道也无法知道请求落在哪个提供者机器 |
| C-13 | 数据告知 | 密钥签发时明示请求数据将经第三方提供者机器处理，确认后方可使用；记录确认版本与时间 |

| S-02 | 有效座位 | 按余量与窗口剩余时间动态计算贡献当前可接纳的消费者数，低于保护线不再接新绑定 |

| S-04 | 平台侧计量 | 次数、时长由 Hub 计；token 由 Hub 从透传的 SSE 流中解析；节点自报仅作对账 |
| S-05 | 预留—结算 | 派单前按预估原子预留，终态按实际回补；三维各扣各的 |
| S-06 | 失败语义 | 首字节前可改派不计费；首字节后节点掉线不改派、建议全免；消费者取消按已产出计；上游 429 改派不计费 |

| S-08 | 风控 | 内容策略与异常请求拦截（保护提供者账号）；节点造假抽检与信誉；自充自跑套现识别 |
| S-09 | 后台 | 池水位、供需缺口、成交与结算、节点信誉与封禁、争议工单、审计 |
| S-10 | 可观测 | 每请求 requestId 贯穿三段；指标：等待时长、首字节、成功率、改派率、限流率、Redis 操作数 |
| S-11 | 版本兼容 | kind / 契约 / 信封版本化；节点与 Hub 契约版本不匹配在 hello 阶段拒连 |

## 7. 三维额度规则

1. 授权对象是**贡献**，不是节点。同机两个贡献各自独立。
2. 三个维度**同时生效**：token、小时（`time.seconds`，按派单到终态的租约时长累计）、次数（`llm.calls`）。任一触顶该贡献停止接新单，在跑的跑完。
   - token 维度按 `llm.input_tokens` 与 `llm.output_tokens` **两个单位分别计量、分别定价**；提供者授权时可设合计上限（两者之和），也可分别设上限，缓存读取 token 计入 input。
3. 每个维度独立配置窗口与归零时刻（按提供者时区）。
4. 软阈值 80% 预警，硬阈值 100% 摘除。
5. 保护线：任一维度剩余低于 5%（可配）时不再接新绑定。
6. 小时维度剩余低于 `minSessionSec`（默认 15 分钟）时不再接新绑定。
7. 上游自身限流优先于额度：被 429 的贡献临时退出，直到 `throttledUntil`。
8. 额度以 Hub 为权威；节点本地只保留展示副本与 kill switch。
9. 额度引擎本身按「任意计量单位集合」实现，三维是 LLM kind 的默认单位；视频类 kind 用自己的单位集合，同一套规则。

## 8. 算力密钥与路由模型

```
提供者 ──授权贡献──▶ 平台（共享池）◀──购买额度── 消费者
                          │ 签发算力密钥（额度 + 有效期 + 允许范围）
                          ▼
   请求携带密钥 ──▶ 平台校验（有效期 / 余额 / 范围）──▶ 放置算法选贡献 ──▶ 提供者通道
```

1. 提供者把贡献授权给**平台**，与任何消费者无关；消费者也不选择提供者。
2. 消费者购买额度后，平台签发算力密钥：绑定额度余额、有效期、允许的 kind / provider / 模型档、并发与速率。P0 由后台签发内测密钥。
3. 密钥生命周期：签发 → 有效 → 到期（请求返回 `key_expired`）→ 冻结期内可续期或换发（余额转入新密钥）→ 冻结期满余额按规则处理；可随时吊销。
4. 每次请求由平台算法在满足密钥允许范围的贡献中路由（详见设计文档第 4 节），消费者与提供者互不可见。
5. 共享池按**平台维度**运行，不按空间隔离；池内数据的 `biz_line` 固定为 `galaxy`。任务宇宙等按空间运行的业务在各自适配器中携带真实空间，其归属规则待各业务定义。

## 9. 通道与上下文需求

| 编号 | 需求 |
|---|---|
| T-01 | 节点主动出站，Hub 永不主动连节点 |
| T-02 | 节点用 HTTP 三端点：长轮询领活、chunked 上行推流、短请求报终态；不引入 WebSocket 依赖 |
| T-03 | 节点只拉自己有空位的通道（贡献）的工作；Hub 只在对应队列上阻塞 |
| T-04 | 响应字节直推持有消费者连接的 Hub 实例，不经 Redis |
| T-05 | 取消信号搭在长轮询 / 进度上报的响应里，取消延迟不超过一个上报周期 |
| T-06 | 帧语义与传输解耦，未来可换 WebSocket 而不改业务逻辑 |
| T-07 | relay 通道允许换节点；session 通道硬亲和，迁移是显式操作并交接上下文 |
| T-08 | session 每回合结束把结构化上下文增量交给服务端账本；节点不在了服务端也拥有完整业务上下文 |
| T-09 | 跨节点续接：新节点 fetch 工作区到记录的 commit、从账本重建 thread 或导入 checkpoint；未推送的工作区改动丢失要明示 |
| T-10 | job 幂等：输入在 OSS，可在任意节点按 attempt 重跑；带租约续期与进度上报 |

## 10. 扩展性需求

|---|---|
| X-01 | 新增业务 = 新增 kind 注册 + 契约 + Hub 适配器（Go module）+ 节点 provider（TS），通道层与传输层零改动 |

| X-04 | 契约以 JSON Schema 为唯一事实来源，Go 与 TS 两侧用同一份校验，CI 双端 golden 测试 |

## 11. 非功能需求

| 类别 | 要求 |
|---|---|
| 延迟 | relay 请求经 Hub 的附加首字节延迟 ≤ 150ms（同机房）；已绑定请求放置 ≤ 3 次 Redis 操作 |
| 吞吐 | 单 Hub 实例支持 ≥ 500 节点长轮询与 ≥ 1000 并发流 |
| 可用性 | Hub 无状态可水平扩展；节点掉线不影响其他节点；Redis 不可用时拒绝新单但不丢账 |
| 一致性 | MySQL 为账目权威；Redis 计数器与 MySQL 流水可对账；预留—结算幂等 |
| 安全 | 凭据不出本机；节点白名单自校验；presigned 短期单 key；日志不记内容与凭据 |
| 隐私 | 消费者与提供者互相匿名；提供者日志不含消费者内容；产物按 kind 保留期清理 |
| 可观测 | requestId 贯穿；指标可按 kind / provider / 贡献 / 密钥聚合 |
| 兼容 | 官方 SDK 路径语义与官方一致；限流与追踪响应头原样透传 |

## 12. 约束与不变式

1. Redis 是唤醒与控制面，不承载响应字节与产物。
2. MySQL 是账目与业务状态的权威。
3. Hub 不代理产物字节，只签发 presigned URL。
4. 节点不监听端口，不保存消费者内容，`complete` 后删除本地副本。
5. 上游凭据永不离开节点。
6. 供给单元是贡献；座位、额度、队列、绑定、限流全部以贡献为主键。
7. 通用层对 `inputs` 不透明。
8. 每个 `WorkUnit` 有全局唯一 id；session 用 seq、job 用 attempt 作幂等键。
9. 每张表带 `biz_line`，索引以其打头；跨层引用用字符串业务键。
10. 领域包之间零 import；跨层能力走 `ports.go` 注入。

## 13. 合规与风险

| 风险 | 说明 | 应对 |
|---|---|---|
| 订阅条款 | 将个人 Claude / Codex 订阅席位按量转售属于账号共享与转售，两家均检测并封号，被封的是提供者账号 | 加入时强制明示同意并记录版本（P-16）；模型白名单；速率限制降低触发概率；合规替代形态为 BYOK / 商用 API 组池 |
| 节点造假 | 节点可不调上游直接伪造响应骗取计费 | Hub 侧随机影子请求比对；消费者投诉；信誉分；追回与封禁 |
| 内容滥用 | 消费者违规内容烧的是提供者账号 | 网关内容策略；异常请求拦截；提供者可拉黑；争议记录 |
| 数据泄露 | 提供者可见经过其机器的请求内容 | 协议约束；匿名化；准入审核；信誉；密钥签发时明示告知并记录确认（C-13） |
| 套现 | 自充自跑刷收益 | 同主体识别；结算延迟；异常模式检测 |
| 上游限流 | 多个消费者集中到一个账号触发 429 | 座位与并发上限；限流感知退出；软亲和分摊 |

## 14. 验收标准

### P0

- 节点以 pool 模式启动后不监听任何 TCP 端口（`lsof` 验证）。
- 提供者只勾选 Claude 时，Hub 的贡献表中仅有 Claude 贡献，节点长轮询请求体中仅含该通道。
- 消费者用官方 Anthropic SDK 指向 Hub 完成一次流式对话，响应 SSE 事件与直连一致（除限流头值）。
- 消费者用官方 OpenAI SDK 指向 Hub 完成一次 Responses 流式请求；带 `previous_response_id` 的后续请求落在同一贡献。
- 未记录条款同意的提供者无法获得配对码；到期密钥的请求返回 `key_expired`，续期后恢复。
- 一次对话的扣费明细中 input 与 output token 分别列出、按各自单价计算。
- 三维额度任一触顶后该贡献停止接新单，在跑请求正常完成；窗口重置后恢复。
- Hub 解析出的 usage 与上游响应中的 usage 一致（golden 用例）。
- 消费者断开后 3 秒内节点侧上游请求被 abort。
- 首字节前节点掉线，请求被改派且不计费；首字节后掉线返回 502 且不计费。
- 已绑定请求的放置路径 Redis 操作 ≤ 3 次（埋点验证）。
- Hub 与节点契约版本不一致时 hello 被拒。

### P1

- 消费者购买额度、扣费明细、失败退款与账本对平。
- 任务宇宙 session 跨节点续接成功，账本包含全部回合摘要，未推送改动的丢失被明示。
- 随机抽检发现伪造响应的节点被自动摘除。

### P2

- 新增视频剪辑业务不修改 `service/galaxy`、`galaxy-api/pkg/agent`、传输层代码。
- 一次剪辑 DAG 的各步骤落在不同节点，中间产物经 OSS 传递，失败步骤单独重跑。
