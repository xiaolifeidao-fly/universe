积分与额度

使用端有两种「钱」：积分挂在人名下，用来买东西； 额度挂在密钥名下，调用时被烧掉。 这份文档把它们从运营充值一路讲到请求结算 —— 每一步谁调谁、写哪张表、什么时候碰 Redis、哪一段在同一个事务里、失败回滚到哪儿。

两种钱，一次转换

整条链路只有一次「换钱」：买套餐的那一刻，积分变成额度。这一步之前的钱是人的，之后的钱是密钥的。 两边的单位、住的表、改它的人、过期方式都不一样，分开看就不会乱。

 积分额度
挂在谁名下 人（cu_…） 一把密钥的一个计量单位（ck_… × unit）
单位 微积分，1 积分 = ¥1，库里存 1_000_000 表示 1 分 计量单位本身：token、call、秒……按 unit 分别记
余额表 zt_galaxy_points_account zt_galaxy_consumer_balance
流水表 zt_galaxy_points_ledger zt_galaxy_consumer_ledger
谁让它变多 运营充值 recharge、分享返现 referral 订单履约（签发 / 充值）topup、续期换发转移
谁让它变少 买套餐 purchase（负数） 调用结算 settle
会不会过期 不会。它是钱，没有有效期 跟着密钥：密钥到期即冻结，冻结期内换发可整体转移
用户在哪儿看 Orbit「积分」页：余额、流水、邀请 Orbit「密钥」页：每把密钥的剩余额度
谁能直接改 只有运营（manager-api）。使用端只能花 没有直接改的入口：只能买进来、烧掉；争议裁决退额度走同一张表的反向流水
为什么积分不是「余额」两个字。它一开始叫余额，改成积分是因为它不能退：运营在线下收钱， 系统里记的是「实付多少钱换了多少积分」（base_amount），两者不必相等，也不构成一个可退款的账户。 口径统一成 1 积分 = ¥1，是为了让套餐标价、返现比例、充值实付三处不用换算。
01

运营给使用者充积分

入口只有管理端一处。使用端没有任何能让自己积分变多的接口 —— 购买和返现都由服务端在别的流程里顺带记账。

  1. 请求号在前端生成，不在服务端

    运营打开充值框的那一刻就有了请求号。服务端拿它当幂等键，因此「网络超时了、我再点一次」和「我要再充一笔」 是两件能分清的事 —— 后者得关掉框重新打开。

    client/manager/src/app/(console)/galaxy/components/PointsRecharge.tsx
  2. 经手人只信凭证

    operator 字段不从请求体读，取的是管理端登录凭证里的账号 id。请求体里带一个别人的名字进来是没用的。

    server/manager-api/pkg/galaxy/handler.go:436
  3. 先挡住手滑和串台

    积分必须大于 0、单次不超过 100 万（挡的是多打几个 0）、实付金额不能是负数、账号必须存在且是使用端账号。 共享端账号没有积分这回事，充进去就成了一笔谁也解释不了的账。

    server/service/galaxy/points.go:145
  4. 加余额和写流水在同一个事务里

    CreditPoints 是一次 upsert（账户不存在就建，存在就 balance + ?）， 紧接着插一行 type=recharge 的流水，txn_id 是 recharge:<请求号>。 流水行还记下 balance_after，事后对账不用重新累加。

    service/galaxy/points.go:203 · repository/points.go:31
  5. 插不进去就整个回滚

    流水表在 (biz_line, txn_id) 上有唯一索引，插入带 ON CONFLICT DO NOTHING。 影响 0 行意味着这个请求号已经充过了：事务回滚，余额一分没动，然后把原来那一行读出来原样返回成功。 报「重复」的话，运营会以为没充上，再充一遍才是真的多充。

    service/galaxy/points.go:175
  6. 同一个请求号换了人或数额，才是真错

    读回来的那一行如果主人、类型、积分数对不上，说明前端把请求号用串了。这时才报错： 「充值请求号已被另一笔充值用过，请关掉充值框重新打开」。

    service/galaxy/points.go:185
没有第二张「充值明细」表。管理端看到的充值明细就是 type=recharge 的流水行。 两处各记一份的话，对不上的时候谁也说不清哪边是对的。
02

使用者用积分买套餐

这是整套设计里最要紧的一段：扣积分、把订单推到已付、签发或充值，三件事在同一个事务里。 不存在「积分扣了、密钥没到」的中间态，也就不需要事后补偿。

  1. 页面为每一单准备一个请求号

    请求号存在 useRef 里，买成了才换新的：失败的那次事务整个回滚了，原样重试不会被当成重复。 按钮在请求飞行期间是禁用的，双击也只会发出去一次。

    orbit/webview/…/store/components/StoreBoard.tsx:78
  2. 先按请求号查一次流水

    超时重试最常见的情况是「第一次其实已经成了」。先查 purchase:<请求号>，查到就直接把那一单还回去。 少了这一步，重试会先建出一张多余的待支付单，余额刚好够一单时还会被报成「积分不足」。

    service/galaxy/points.go:250
  3. 建单：校验和渠道支付共用一份

    套餐得在架上；充进已有密钥时，密钥必须是本人的且没吊销；要签发新密钥时，数据告知的确认是硬前置，下单时就挡住。 订单上还落两个快照：额度（套餐之后改量不影响已下的单）和绑定的模型（之后改绑不影响这一单的返现口径）。

    service/galaxy/order.go:146
  4. 扣积分：条件更新，不会扣成负数

    UPDATE … SET balance = balance − ? WHERE balance ≥ ?。影响 0 行就是余额不够， 直接 errInsufficientPoints 回滚 —— 不需要先读再判，也就没有「读到的时候够、写的时候不够」这种缝。

    repository/points.go:50
  5. 写流水：撞键就当作重放

    txn_id 优先用 purchase:<请求号>，老客户端不带请求号时退回 order:<订单号>:pay。 并发的两次提交会各建一张待支付单，但只有第一张能把这行流水写进去，后到的那次在事务里撞键、整体回滚。

    service/galaxy/points.go:268
  6. 订单推到已付，再履约

    pending → paid 是条件更新；履约要么签发一把新密钥（同时写入额度和一行 topup 账本）， 要么把额度充进指定的那把密钥，最后 paid → fulfilled。两处都是条件更新，并发时只有一个能赢。

    service/galaxy/order.go:241 · order.go:304
  7. 失败的收尾：回滚 + 关单

    事务已经把积分和订单状态退回去了，但那张 pending 的单子还在，它已经付不了也不该留着，所以额外关一次。 重放那条路同样：把这次多建出来的单关掉，返回第一次的订单。对连点两下的人来说，他只买了一次。

    service/galaxy/points.go:300
  8. 明文只在这一次响应里出现

    新签发的密钥明文随这次响应回一次，响应带 Cache-Control: no-store。 重放返回的那一单不带明文 —— 要拿密钥去密钥页取（那里有单独的取回接口，服务端存的是 AES-GCM 密文）。

    galaxy-api/pkg/consumers/handler.go:236
事务里的那个 service 是个副本。履约要调 IssueKey 这些本来用普通连接的方法， 所以有个 scopedTo(tx) 把读写全部落在这个事务上。它只带 repository、配置、密钥加解密和 kind 定义， 不带放置、等待队列这些进程内状态 —— 那些东西不该在事务里碰。
03

分享返现

被邀请的人每完成一笔订单，平台按实付金额的一个比例返积分给邀请人，下单的人自己一分不少。 只返给分享人一层，返现本身不再产生返现。

  1. 邀请关系在注册那一刻定死

    注册时填的邀请码会先解析成邀请人，账号和邀请关系在同一个事务里建。 事后不能改：改得动的话，返现归谁就成了谁先去找运营的问题。老账号没有这一行，第一次打开积分页时补一行， 但只补邀请码、邀请人留空 —— 自己注册的人事后认一个上家，等于白送一笔。

    service/galaxy/account/auth.go:91 · points.go:538
  2. 比例：模型的优先，其余走默认

    每个模型可以单独设一个比例（存在模型目录行上的 referral_bps），没单独设的跟着全局默认走 （存在 zt_galaxy_setting 的 referral.default_bps）。 默认值是 0：钱相关的默认只能是「不给」，比例由运营显式打开。

    service/galaxy/points.go:411
  3. 比例存的是万分之一，并且写进流水

    10% 存成 1000，算式是 实付 × bps ÷ 10000，全程整数。 用到的比例连同「按什么算的」一起记进流水行（rate_bps、base_amount）： 运营之后改比例，已经返过的不跟着变，账上也看得出当时是按多少算的。

    service/galaxy/points.go:380
  4. 入账复用同一段加减

    返现走的还是「改余额 + 写流水」那一个事务，txn_id 是 order:<订单号>:referral。 一张订单最多返一次，重复调用插不进流水，余额也就不会动。

    service/galaxy/points.go:384
  5. 它跑在购买事务之外，而且允许失败

    买的人已经拿到东西了，返现不该反过来把他的购买拖垮。所以返现在交付之后单独跑， 出错只记一行日志（带订单号），不向用户报错。代价是：漏掉的不会自动补，得照日志补。

    service/galaxy/points.go:347
渠道支付那条路也返。返现挂在「订单交付」这件事上，不在「用积分付款」上 —— PayOrder 履约完同样调一次。积分付的是积分、渠道付的是钱，而 1 积分 = ¥1，两者同一量纲，算式不用分叉。
04

额度在运行时怎么被烧掉

到这里钱已经变成密钥上的额度了。请求路径上有 Redis，但它一份钱也不管 —— Redis 负责的是「这次请求交给哪台机器、那台机器还有没有位置」，而余额从头到尾只在 MySQL 里， 并且是在节点报完成的那一刻同步扣的。

  1. 鉴权：每个请求一次 MySQL 点查，没有缓存

    网关从 X-Galaxy-Key / Authorization: Bearer / x-api-key 里取出明文， 算 sha256 之后按 key_hash 查一行。没有 Redis 缓存也没有进程内缓存 —— 代价是每个请求多一次点查，换来的是吊销立刻生效，而且没有任何一处缓存需要在签发、吊销、换发时去失效。

    service/galaxy/consumerkey.go:86 · repository/consumer.go:15
  2. 只看状态和有效期，不看余额

    鉴权检查的是：密钥存在、没被吊销、没到期。到期的顺手写成 expired 并进入冻结期。 之后的授权检查看的是 kind、provider、模型档。余额不在这条路上 —— 所以一把余额为 0 的密钥照样能发起请求，欠的那部分在结算时扣不动，被静默吸收。

    这也是「不能开放自助签发空密钥」的原因：签出来的空密钥是能用的。

    service/galaxy/consumerkey.go:98 · billing.go:104
  3. 放置：Redis 决定交给谁跑

    先看这把密钥有没有粘性绑定（galaxy:bind:{ck_…}:{lane}，默认 30 分钟不用就过期）， 有就直接回原来那台机器 —— 命中的话提示词缓存还在，成本和延迟都低得多。没有就在车道里挑一台。 机位、并发、提供者的配额检查和入队是一段 Lua，原子完成。

    service/galaxy/unit.go:117 · redisctl/script.go:17
  4. 节点领活、跑完上报

    节点 BLPOP 队列拿到请求 id，再取请求体（单独一个 60 秒就过期的键）。 跑完调 /agent/v1/units/:id/complete 交回用量。Hub 自己能解析的用量以 Hub 的为准， 对不上超过阈值会记一条差异并扣信誉。

    galaxy-api/pkg/agent/handler.go · service/galaxy/unit.go:584
  5. 结算的两道闸

    第一道在 Redis：settle 脚本发现这次请求已经是 settled 就直接返回，重复上报到不了后面。 第二道在 MySQL：消费账本按 <rid>:<attempt>:<unit> 唯一， 账本一行一行写，只对真的插进去的那些行扣余额。批量写完再按总额扣一次的话，一次重放就是白发一笔钱。

    service/galaxy/unit.go:727 · billing.go:96
  6. 扣减本身：又是一次条件更新

    UPDATE … SET balance = balance − ? WHERE key_id = ? AND unit = ? AND balance ≥ ?。 扣不动返回 0 行，这个结果目前被忽略：P0 的内测密钥可能压根没有这个单位的余额行， 当时选择只记账不阻断。要把额度真正变成硬约束，得把这个返回值接起来，并且在请求路径上加一道余额检查。

    repository/consumer.go:83
  7. 没定价的单位不进账本，也就不扣额度

    zt_galaxy_price 里没有对应 (kind, unit) 的行，或者单价是 0， 这个单位就只记计量、不进账本、不扣余额。线上价格表目前是空的，所以现在实际上一分额度都没扣过。

    service/galaxy/billing.go:60
这条链路上的 Redis 键装的是什么过期
galaxy:bind:{ck_…}:{lane}这把密钥上次落在哪台机器（粘性）默认 30 分钟不用即失效
galaxy:seats:{cid}某台机器上正占着位置的密钥按位置到期时间剔除
galaxy:q:{cid}发给某台机器的待领队列领走即出队
galaxy:req:{rid}一次请求的运行状态（含是否已结算）24 小时
galaxy:req:{rid}:body请求体，给节点领活时取60 秒
galaxy:quota:{cid}:{unit}:…提供者那侧的已用 / 预留计数跟着计费窗口
一个和账无关、但值得知道的副作用。粘性绑定和机位是按密钥 id 记的， 吊销和换发都不会去清它们：被吊销的密钥下一个请求就会被挡在鉴权那一步，但它占着的那个机位 最长可能留到绑定过期（默认 30 分钟）才被回收。换发出来的新密钥则是「从头开始找机器」，会丢掉原来的机器亲和。
05

幂等键一览

每一次余额变动都对应一行流水，流水的 txn_id 就是这次变动的名字。 重放一次请求写不进第二行，也就不会多记一笔钱。谁生成这个名字，决定了它能挡住什么。

txn_id哪本账谁生成挡住什么
recharge:<请求号> 积分 管理端前端，打开充值框时 运营连点、超时重发、网络重试
purchase:<请求号> 积分 使用端前端，每准备一单一个 连点两下、超时重试、并发提交
order:<订单号>:pay 积分 服务端（老客户端不带请求号时） 同一张单被付两次
order:<订单号>:referral 积分 服务端，按订单号 返现补跑、支付回调重推
<订单号>:topup:<unit> 额度 服务端，按订单号和单位 同一张单重复充额度
<新密钥>:renew:in|out:<unit> 额度 服务端，续期换发时 余额搬两遍
<rid>:<attempt>:<unit> 额度 服务端，按这一次执行 同一次调用被结算两遍（换机重试算另一次 attempt）
唯一索引是最后一道，不是唯一一道。积分这边是「插得进流水才算数」： 先改余额、再插流水，插不进就连余额一起回滚。额度那边是「插进去了才动余额」： 账本一行一行写，只对真的插进去的那些行扣余额 —— 批量写完再按总额扣一次的话，一次重放就是白发一笔钱。
06

两条状态机

订单的状态推进全部是条件更新（WHERE status = ?），所以并发的两次履约只有一个能赢， 输的那个去读当前状态，不会再发一遍额度。

07

为什么是这样

为什么积分余额不放 Redis

积分是钱，它的权威值只能在一个地方。放 Redis 会带来两个新问题：缓存和库不一致时以谁为准， 以及「先扣缓存再落库」中间挂掉的那笔怎么办。而积分的读写频率很低 —— 一个人一天也充不了几次、买不了几单， 一次带索引的行更新完全扛得住。

额度那边不一样：它在请求路径上被高频消耗，所以那条路上有缓存和计数器，但余额本身仍然只在 MySQL。

为什么余额变动必须和流水同事务

「余额少了但查不到为什么」是账务上最不能出现的状态。放在一个事务里，账就只有两种结果： 要么钱和它的解释一起存在，要么两样都不存在。

为什么扣积分和履约也要同事务

分开的话就得处理「积分扣了、密钥没发出去」，那需要一套补偿：定时扫、自动退、人工兜底。 放在一个事务里，这类中间态压根不会产生，也就不用写那套补偿代码 —— 少写的代码是最可靠的代码。

为什么返现反而在事务之外

返现是给另一个人加钱，和这笔购买没有原子性要求。放进去只会让购买多一个失败原因： 邀请人的账户出点问题，下单的人就买不成了。放出来的代价是可能漏 —— 但它按订单号幂等，补起来是安全的。

为什么请求号由前端生成

服务端生成的话，它认不出「这是同一次点击的重试」还是「这是第二次购买」。请求号跟着那一次操作走： 同一个框、同一次点击就是同一个号，成功之后才换新的。

为什么订单要带模型和额度的快照

套餐随时可能改价、改量、改绑定的模型。已经下的单必须按下单那一刻的口径履约和返现， 否则运营改一次价，历史订单的账就全变了。

为什么金额都是整数

积分、价格、返现比例全部是整数：积分与金额按「微」存（1_000_000 = 1）， 比例按万分之一存。钱不能有任何一步经过浮点 —— 连 SQL 里的 SUM 都显式转成整数， 因为不同引擎给出的类型不一样。

为什么邀请码单独一张表

邀请码要唯一索引，而账号表是两端共用的：共享端的人没有使用端的邀请码，一半是空串会直接撞唯一键。 两端也各有一套码，一端的码填到另一端会明确报「邀请码无效」，而不是悄悄把返现记到另一个人头上。

08

会出错的地方，和该怎么办

现象实际发生了什么处置
运营充值点了两下，只多了一笔 第二次撞了同一个 txn_id，事务回滚，返回的是第一笔 正常，不用管
「充值请求号已被另一笔充值用过」 同一个请求号换了人或数额，前端把号用串了 关掉充值框重新打开再充
用户说买了但没看到密钥 购买成功的响应只回一次明文；重放那次不带 去密钥页用「查看密钥」取，服务端存的是密文
购买报「积分不足」，但余额看着是够的 这一单的金额大于余额，或者上一笔购买还没返回、余额已经被扣 刷新积分页看实际余额；扣了没交付的情况不存在，两件事同事务
邀请人没拿到返现 五道闸之一没过：没有邀请人、比例是 0、订单未交付、金额为 0，或者返现那一步真的报错了 先看管理端有没有设比例；确认设了就查日志里的分享返现失败 order=…，按订单号补跑是安全的
额度看着没被扣 只有定了价的单位才进账本、才扣额度；zt_galaxy_price 没有对应行时只记计量、不扣费 先看价格表有没有种子数据（galaxy_seed.sql）
老密钥看不到明文 这次改动之前签发的密钥，库里没有密文 续期换发一次，新密钥就能看了
