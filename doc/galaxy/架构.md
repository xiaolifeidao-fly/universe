# Galaxy 共享算力池 · 架构文档

## 1. 总览

```
 消费者                       Galaxy Hub (galaxy-api, Go)                       节点 (ai-bridge pool 模式, TS)         上游
 官方 SDK / 平台客户端        ┌────────────────────────────────────┐            ┌──────────────────────────┐
      │                       │  适配器 relay │ delivery │ videofarm │            │  provider  llm-chat      │
      │ HTTPS 短连接 / SSE    │  ─────────────────────────────────  │  长轮询 ◀──│            delivery-task │  订阅登录态
      ├──────────────────────▶│  通道层: 信封 · 放置 · 额度 · 计量  │  chunked ◀─│            video-*       │ ───────────▶ Anthropic
      │◀──────────────────────│  传输层: next · stream · report     │  report ◀──│  贡献: claude-main …     │             ChatGPT
      │                       │  控制面 Redis │ 权威 MySQL │ OSS签名 │            │  三层闸门 · 凭据 · 透传  │             Kling …
      │  presigned PUT/GET    └────────────────────────────────────┘            └──────────────────────────┘
      └────────────────────────────────▶  OSS  ◀────────────────────────────────────────┘ presigned GET/PUT
```

三个参与方、三段链路：

| 链路 | 方向 | 传输 | 承载 |
|---|---|---|---|
| 消费者 → Hub | 消费者发起 | HTTPS 短连接，响应可为 SSE | 官方 SDK 兼容请求、平台原生 API、产物签名申请 |
| Hub ↔ 节点 | **节点发起** | HTTP 长轮询 + chunked 上行 + 短请求 | 工作单元下发、事件流上行、心跳、终态 |
| 节点 → 上游 | 节点发起 | HTTPS | 用本机订阅凭据的真实上游调用；或本机计算 |
| 消费者 / 节点 ↔ OSS | 各自发起 | presigned URL | 产物字节，Hub 不经手 |

## 2. 设计原则

1. **节点主动出站，永不入站。** 提供者机器不开端口，Hub 不知道节点地址。
2. **Redis 是唤醒与控制面，不是数据面。** 响应字节与产物永不进 Redis；MySQL 是账目与业务状态的权威。这与现有 `redisqueue` 的定位一致。
3. **Hub 不搬产物字节。** 只签发 presigned URL；大文件在消费者、节点、OSS 之间直传。
4. **供给单元是贡献，不是节点。** 座位、额度、队列、绑定、限流全部以贡献为主键。
5. **通用层对业务参数不透明。** 信封、放置、额度、传输、账本只认 `contract`；业务参数只在适配器的 parse 进、onEvent 出两处被解读。
6. **平台侧计量优先。** 次数、时长 Hub 自己计；token 从透传的流里自己解析；节点自报仅作对账。
7. **帧语义与传输解耦。** 消息类型与字段固定，传输层可换。
8. **两侧对称校验。** Hub 是路由权威，节点必须再校验一次能力白名单；`agent-local` / `job-local` 类 kind 的执行边界由节点自己守。
9. **契约单一事实来源。** JSON Schema 与 kind 注册文件同时喂 Go 与 TS。
10. **先按现有骨架落地，不提前做分布式。** 单 Hub 实例 + 内存节点表撑到几百节点；扩展路径预留，不预建。

## 3. 分层架构

```
业务层    任务宇宙 · 视频养号 · 视频剪辑 · (以后)      编排 / DAG / 业务状态机 / 业务账本语义
──────────────────────────────────────────────────────────────────────────────
能力层    capability registry                       kind → 原语 · provider · 计量单位 · schema · 策略
──────────────────────────────────────────────────────────────────────────────
通道层    relay │ session │ job                     统一信封 · 放置 · 额度 · 计量 · 取消 · 状态机
──────────────────────────────────────────────────────────────────────────────
传输层    next 长轮询 · chunked 上行 · report · OSS 直传      字节怎么走
──────────────────────────────────────────────────────────────────────────────
节点层    ai-bridge pool 模式 + provider 插件         codex · claude · video-api · ffmpeg · gpu-model
```

每一层只认识下一层的抽象：

- 业务层不知道什么是节点，只提交工作单元、消费事件与产物引用。
- 能力层是静态注册表（`kind.yaml`），Hub 启动时读入，放置与额度按它做决策。
- 通道层不知道什么是「视频」或「任务」，只处理三种原语的状态机。
- 传输层不知道原语，只搬帧。
- 节点层按 (kind, provider) 加载 provider，执行并产出统一事件。

接新业务只动业务层、能力层、节点层的对应目录。

## 4. 三种原语

| | relay | session | job |
|---|---|---|---|
| 形态 | 同步请求 / 响应，流式 | 有状态多回合 | 异步长任务 |
| 时长 | 秒级 | 回合秒 ~ 分钟 | 分钟 ~ 小时 |
| 载荷 | 内联（≤ bodyLimit） | 内联 + 工作区引用 | 全部 OSS 引用 |
| 输出 | 字节流原样透传 | 事件流 + 上下文增量 | 进度事件 + 产物引用 |
| 上下文 | 消费者客户端 | 服务端账本 + 节点 thread + Git 远端 | 无，输入自包含 |
| 亲和 | 软（prompt cache） | 硬 + 显式迁移 | 无，数据引力 |
| 失败重试 | 首字节前可改派 | 按 seq 幂等 | 按 attempt 幂等，任意节点重跑 |
| 幂等键 | requestId | (sid, seq) | (jobId, attempt) |
| 现有参照 | `ai-bridge` relay 模块 | `delivery-task-planner` 会话 | `zt_delivery_command` 租约 / 活动 / 完成 |

job 原语是现有 delivery 命令通道（lease / renew / activity / cancelRequested / attachments）的去业务化版本：去掉 `user_id` 与工作目录耦合，附件换成 OSS 引用。

## 5. 连接模型

### 5.1 为什么方向要反过来

现有 ai-bridge 是 inbound：监听 `127.0.0.1:8787`，靠 token 与 IP 白名单放行。公共池里提供者在 NAT 与家庭宽带后面，没有公网 IP；即便有，让成千上万台带订阅凭据的个人机器暴露服务也不可接受；动态 IP、休眠、断网重连让「可回拨地址表」无法维持。因此节点主动出站，请求沿这条出站链路反向下发。

### 5.2 为什么用 HTTP 三端点而不是 WebSocket

两者复杂度接近。选 HTTP 三端点的理由：与现有 `remote_worker.py` 的 claim / lease / report 模式同构，团队熟悉；`ai-bridge` 不引入新依赖；多实例下节点的 `next` 可落任意实例。帧语义固定，将来要换 WebSocket 只换搬运方式。

| 端点 | 方式 | 作用 |
|---|---|---|
| `GET /agent/v1/next` | 长轮询，≤ 25s | 领活。请求体列出有空位的通道 |
| `POST /agent/v1/units/{id}/stream` | chunked 上行 | 边收上游边推 SSE 字节；一次响应一条连接 |
| `POST /agent/v1/units/{id}/progress` `…/complete` | 短请求 | 进度、续租、终态 + usage 对账 |

取消信号搭在 `next` 与 `progress` 的响应体里，不单独轮询。

### 5.3 为什么响应流不进 Redis

1. 节点够不到 Redis（不能暴露），队列只能在 Hub 内部，节点侧连接一条也省不掉。
2. 一次响应几百到上千个 SSE chunk，走 Redis 就是每 chunk 一写一读，百路并发即数十万 ops，数据面与故障域绑死在 Redis；同实例直传是 0 次 Redis 操作。
3. 队列会无限吸收，TCP 背压消失；消费者卡住时节点仍全速拉上游，烧的是提供者额度。`proxyRelay` 的 `pipeline()` 天然把背压顶到上游 fetch。
4. 取消要再开一路轮询，延迟即成本。

### 5.4 实例粘性

消费者连接落在实例 A。`next` 可由任意实例服务（请求体在 Redis，寿命短、体积小），但 `next` 的响应里带 `streamURL` 指向实例 A 的内部地址，节点的上行直推 A。客户端连接与节点上行在同一进程内对拷，Redis 不碰数据。跨实例 pub/sub 转发不做。

## 6. 控制面与数据面

| 存储 | 职责 | 不放什么 |
|---|---|---|
| Redis | 待派 rid 队列（按贡献）、等待队列、节点 / 贡献心跳与负载、座位集合、绑定（带 TTL）、单位化额度计数器、取消标志、请求体（≤ bodyLimit，TTL 60s）、Responses id → 贡献映射、rid → 实例路由 | 响应字节、产物、账目 |
| MySQL | 贡献、节点、座位绑定快照、工作单元、单元事件、额度窗口、计量流水、账本 session / turn / checkpoint、订单与算力密钥（含有效期）、消费者余额、提供者积分账本、同意记录、定价、产物元数据 | 高频计数器 |
| OSS | 产物字节、session checkpoint | 任何含用户或节点身份的对象键 |

Redis 计数器与 MySQL 流水定期对账；Redis 丢失时拒绝新单、按 MySQL 重建计数器。

## 7. 供给模型

```
节点 (一台机器, 一个 node token)
 ├─ 贡献 claude-main   kind=llm.chat provider=claude_oauth models=sonnet-* seats=3 seatConc=2 quota=[…] schedule=22:00-08:00
 │    ├─ 座位#1 ← 消费者 A
 │    ├─ 座位#2 ← 消费者 B
 │    └─ 座位#3 ← 空
 ├─ 贡献 codex-main    (未勾选, Hub 不可见)
 └─ 贡献 ffmpeg        kind=video.edit.render provider=ffmpeg-local seats=1 quota=[cpu.seconds…]
```

- **授权对象是平台**：提供者把贡献授权给平台，不指定消费者；消费者购买后持有带有效期的算力密钥，请求到达时由放置算法决定落在哪个贡献。
- **探测 ≠ 贡献**：节点 `probe()` 发现本机能力，主人勾选后才申报。
- **贡献是主键**：`contrib:{cid}` 状态、`q:contrib:{cid}` 队列、`bind:{consumerKey}:{lane}` 绑定、`quota:{cid}:{unit}:{window}` 计数、限流状态全部按贡献。
- **座位**是消费者与贡献的粘性绑定；**座位并发**限制同一消费者在该贡献上的并行请求；`seats × seatConcurrency ≤ 节点 gate 并发`。
- **有效座位数**由余量与窗口剩余时间动态计算，主人配置只是上限。
- **通道**：节点的 `next` 只列出有空位的贡献，Hub 只在这些队列上阻塞。这是 `remote_worker.py` 「只读通道 + 执行通道」双通道拉取的推广。

## 8. 放置与亲和（概览）

请求到达后四步：

1. 硬钉（Responses `previous_response_id`）或已有绑定且贡献健康 → 直接入该贡献队列。多数请求走这条，2 ~ 3 次 Redis 操作。
2. 硬过滤：kind 与版本支持、provider 有贡献、model 命中白名单、在线且未限流、未排空、`seatsUsed < seatsEff`、各单位余量 > 预留、`inflight < conc`、资源需求（job）。
3. 打分：空座位、余量短板、当前空闲、首字节延迟、信誉、数据引力。
4. Lua 原子绑定座位 + 入队；无候选进等待队列至多 `maxWaitMs`。

亲和按 kind：relay 软（忙则溢出，不改绑定）、session 硬（迁移是显式操作）、job 无（幂等重跑 + 数据引力）。完整算法见设计文档第 4 节。

## 9. 上下文模型

| 层 | 内容 | 权威 | 跨节点迁移 |
|---|---|---|---|
| 业务层 | 任务 / 需求 / 阶段 / 交付物引用 / 回合摘要 | 服务端账本 | 天然在服务端 |
| 执行层 | CLI thread（对话全文、工具轨迹、模型缓存） | 节点 | 账本重建新 thread（有损）或 checkpoint 导入（高保真，绑 CLI 版本） |
| 工作区层 | 文件、分支、未提交改动 | Git 远端 | 回合结束推分支记 sha，新节点 fetch 到同一 sha |

原则：**服务端账本是业务真相，节点 thread 是执行缓存。** 每个回合结束节点把 `contextDelta` 交给服务端追加，节点死了服务端仍拥有完整业务上下文。relay 原语没有这一层：上下文在消费者客户端，换节点只损失 prompt cache。

## 10. 适配器架构

| 部件 | 位置 | 语言 | 装在哪 | 职责 |
|---|---|---|---|---|
| 契约 | `galaxy/business/<kind>/contract/` | kind.yaml + JSON Schema | Hub 与节点 | 入参 / 上下文增量 schema、能力注册 |
| Hub 适配器 | `server/galaxy-hub-api/adapters/<business>/` | Go module | 服务器 | 挂消费者路由、parse、route、estimate、toUnit、写回、extractUsage、错误体 |
| 节点 provider | `galaxy/business/<kind>/node/` | TS | 提供者机器（随 ai-bridge 插件分发） | 按 (kind, provider) 执行，产出统一事件 |

路由键是 `(kind, provider)`：kind 选 Hub 适配器，(kind, provider) 选节点 provider，model 再做贡献白名单过滤。同一 kind 内不同协议族（Anthropic Messages / OpenAI Responses）是适配器内部的两个「协议族」分支，不拆 kind：业务语义、计量单位、定价一致。

插件包不携带任何服务端代码；Hub 不携带任何节点执行代码。

## 13. 安全架构

| 主体 | 凭据 | 中间件 | 说明 |
|---|---|---|---|
| 消费者 | `sk-` 算力密钥（购买后签发，带有效期） | `RequireConsumerKey()` | 校验存在、未吊销、未过期、余额；绑定允许的 kind / provider / 模型档、并发与速率 |
| 节点 | node token（配对码换取） | `RequireNodeToken()` | `CallerID` 覆盖请求体身份；撤销即拒连 |
| 管理 | 现有用户 token | `RequireAdmin()` | 经 manager-api |

边界：

- **同意记录**：提供者配对前必须存在当前条款版本的同意记录；消费者密钥签发时记录数据告知确认。两者都是硬前置，缺失即拒绝。
- **凭据不出节点**：Claude OAuth、Codex auth.json 只在节点读取，Hub 与消费者永远拿不到。
- **节点白名单自校验**：收到的单元 kind / provider / model 不在自己申报的贡献内立即拒绝；`agent-local` / `job-local` 类 kind 意味着在主人机器上执行命令，这条边界不信任 Hub。
- **匿名化**：消费者看不到节点，节点看不到消费者；日志只记 requestId、cid、keyAlias。
- **presigned**：单 key、短 TTL、限大小；对象键不含用户或节点信息。
- **内容策略**：网关侧拦截违规与异常请求，保护提供者账号。
- **抽检**：Hub 随机以自有账号重放请求比对，识别伪造响应。
- **产物清场**：节点 `complete` 后删除本地副本（协议约束 + 信誉）。

## 14. 与现有系统的关系

| 现有部件 | 关系 |
|---|---|
| `ai-bridge` relay 模块 | pool 模式复用 `credentials/`、`core/queue.ts` 三层闸门、`core/proxy.ts` 透传、`core/request.ts` 生命周期；`server.listen`、`auth.tokens`、`ipAllowlist`、`admin` 在 pool 模式整体不生效 |
| `app-api/pkg/commands` + `redisqueue` | 设计哲学的来源（MySQL 权威、Redis 唤醒、claim / lease / report）；本期不改，任务宇宙先以 `delivery` 适配器接入新链路，P3 再迁移 |

| `service/identity` | 提供者与购买密钥的用户挂在现有用户体系；共享池按平台维度运行，池内表 `biz_line` 固定为 `galaxy`；任务宇宙等按空间运行的业务在各自适配器里携带真实空间 |
| `service/delivery` | `delivery` 适配器通过 `galaxy-api/pkg/local` 适配成 ports 形状注入；`service/galaxy` 不直接 import |
| `manager-api` / `client/manager` | 池水位、结算、封禁、争议、审计的后台落点 |
| `zt_delivery_cloud_sync_file` + OSS | 产物与 checkpoint 存储的现成通道；需补 presigned 签发 |

## 15. 演进路线
