# Galaxy 共享算力池 · 详细设计

编号约定：协议消息以 `类型.动作` 命名；Redis key 以冒号分段；表名 `zt_galaxy_{实体}`；所有时间为 UTC 毫秒或 RFC3339。

## 1. 统一信封

### 1.1 WorkUnit

```jsonc
{
  "id": "u_01J8…",                 // 全局唯一，ULID
  "kind": "llm.chat",              // 能力注册名
  "kindVersion": 1,
  "primitive": "relay",            // relay | session | job，由 kind 决定，调用方不可填
  "family": "anthropic",           // 协议族（relay 用）：anthropic | openai
  "provider": "claude_oauth",      // 路由键
  "model": "claude-sonnet-4-5",    // 路由键，做贡献白名单过滤
  "consumerKey": "ck_…",           // 匿名化后的消费者标识（不是 sk- 明文）
  "affinityKey": "ck_…:sess-a",    // 亲和键
  "hardPin": null,                 // 硬钉的 cid（Responses 链式 / session）
  "cid": "c_…",                    // 放置后填：贡献 id
  "seq": 0,                        // session 回合序号
  "attempt": 1,                    // job 重跑次数
  "deadline": 1757260000000,
  "inputs":  [ { "name": "body", "inline": "<bytes>" } ],
  "outputs": [],
  "metering": { "estimate": { "llm.output_tokens": 4096, "llm.calls": 1, "time.seconds": 120 },
                "actual":   {} },
  "state": "queued",
  "error": null,
  "createdAt": 1757259900000
}
```

### 1.2 Payload 二态

```jsonc
{ "name": "body",  "inline": "<bytes>", "contentType": "application/json" }
{ "name": "clip1", "ref": { "store": "oss", "key": "galaxy/video.edit.render/u_…/clip1.mp4",
                            "size": 734003200, "sha256": "…", "contentType": "video/mp4",
                            "expiresAt": "2026-09-14T00:00:00Z" } }
```

阈值 `inlineMaxBytes` 默认 256KB，超过强制 ref；relay 原语例外，内联上限为 `bodyLimit`（默认 4MB）。`ArtifactRef.key` 不含任何用户、密钥、节点信息。

### 1.3 状态机

```
queued ──placed──▶ placed ──claimed──▶ running ──▶ completed
   │                  │                   │  ├──▶ failed(retryable) ──▶ queued  (attempt+1，仅 idempotent kind，≤ maxAttempts)
   │                  │                   │  └──▶ failed(final)
   │                  │                   ├──▶ cancelled
   └──expired ◀───────┴───────────────────┴──▶ expired（deadline 或租约过期）
running 内 job 可重复上报 progress；relay 在首字节后进入 streaming 子状态（决定失败语义）
```

### 1.4 RouteKey 与 KindSpec

```go
type RouteKey struct { Kind string; KindVersion int; Family, Provider, Model, AffinityKey string; HardPin string }

type KindSpec struct {
    Kind string; Version int; Primitive string
    Providers []string
    Metering struct{ Units []string; Trusted []string }
    Placement struct{ Affinity string; Requires map[string]any; LocalityHint string }
    Retry struct{ Idempotent bool; MaxAttempts int }
    Lease struct{ RenewSec, MaxRunSec int }
    Retention struct{ Inputs, Outputs string }
    Context struct{ Schema string; Resume string }   // none | ledger | checkpoint | ledger+checkpoint
    Input struct{ Schema string; MaxInlineBytes int }
}
```

## 2. 节点通道协议

所有节点侧请求带 `Authorization: Bearer <node-token>`、`X-Galaxy-Node: <nodeId>`、`X-Galaxy-Contract: <契约版本>`。Hub 用凭证认定的节点身份覆盖请求体中任何节点字段。

### 2.1 配对

```
POST /agent/v1/pair            body { "code": "8F3K-2Q9M", "displayName": "fly-mbp", "bridgeVersion": "0.2.0" }
→ 200 { "nodeId": "n_…", "token": "gnt_…", "hubInstanceHint": null }
```

配对码由平台在提供者控制台生成，一次性、10 分钟有效；**只对已记录当前条款版本同意的提供者签发**，`pair` 时 Hub 再校验一次同意记录，缺失返回 `403 consent_required`。节点把 token 以 sha256 落盘（复用 `auth/token-store.ts` 的存储方式），明文只在内存。

### 2.2 hello / contributions.update

```
POST /agent/v1/hello   （contributions.update 同一端点，语义为全量替换）
{
  "bridgeVersion": "0.2.0",
  "contract": 1,
  "resources": { "os": "darwin", "cpu": 10, "memGB": 32, "gpu": null, "diskFreeGB": 210, "netMbps": 300 },
  "contributions": [
    {
      "cid": "claude-main",
      "kind": "llm.chat", "kindVersion": 1,
      "provider": "claude_oauth",
      "models": { "allow": ["claude-sonnet-*"], "deny": ["claude-opus-*"] },
      "seats": 3, "seatConcurrency": 2,
      "quota": [
        { "unit": "llm.output_tokens", "limit": 2000000, "window": "day", "resetAt": "00:00+08:00" },
        { "unit": "time.seconds",      "limit": 14400,   "window": "day", "resetAt": "00:00+08:00" },
        { "unit": "llm.calls",         "limit": 800,     "window": "day", "resetAt": "00:00+08:00" }
      ],
      "schedule": [ { "from": "22:00", "to": "08:00", "tz": "Asia/Shanghai" } ],
      "upstreamOK": true
    }
  ]
}
→ 200 { "accepted": ["claude-main"], "rejected": [], "quotaEffective": { "claude-main": [ …hub 侧生效值… ] } }
```

Hub 校验：kind 已注册且版本兼容；provider 在 kind 的 providers 内；seats ≤ 平台上限；quota 单位属于 kind 声明的单位。契约版本不匹配返回 `426 contract_mismatch`，节点停止重试并提示升级。Hub 侧额度为权威：主人在控制台改了，`quotaEffective` 会与节点本地不同，节点以 Hub 为准更新展示副本。

### 2.3 heartbeat

```
POST /agent/v1/heartbeat   每 15s
{
  "lanes": [
    { "cid": "claude-main", "inflight": 2, "queued": 0,
      "quotaLeft": { "llm.output_tokens": 1483022, "time.seconds": 9120, "llm.calls": 512 },
      "throttledUntil": null, "upstreamOK": true, "paused": false },
    { "cid": "ffmpeg", "inflight": 1, "queued": 0, "quotaLeft": { "cpu.seconds": 7200 }, "cachedArtifacts": ["galaxy/…/clip1.mp4"] }
  ]
}
→ 200 { "cancel": ["u_…"], "drain": [], "quotaUpdate": { … }, "serverTime": … }
```

Hub 45s 未收到心跳即把该节点全部贡献摘除；`throttledUntil` 非空的贡献退出候选；`cachedArtifacts` 是 LRU 有限集合（≤ 64 个 key），用于数据引力。

### 2.4 next（领活）

```
GET /agent/v1/next?waitSeconds=25
{ "lanes": [ { "cid": "claude-main", "free": 2 } ] }          // 满了的通道不列
→ 200 { "unit": { …WorkUnit（inputs 内联体在 inputs[].inline，ref 带 presigned GET）… },
        "lease": { "token": "lt_…", "expiresAt": …, "renewSec": 60 },
        "streamURL": "https://hub-3.internal:10004/agent/v1/units/u_…/stream",
        "cancel": [] }
→ 204  超时无活
```

Hub 实现：对列出的 `q:contrib:{cid}` 做 `BLPOP … timeout=waitSeconds`；弹出 rid 后读 `req:{rid}` 与 `req:body:{rid}`，校验单元的 kind / provider / model 仍在该贡献范围内（贡献可能刚被改），写入租约，返回。`streamURL` 指向 `req:{rid}.instance`。

### 2.5 stream（上行推流）

```
POST {streamURL}
Headers: Transfer-Encoding: chunked, X-Galaxy-Lease: lt_…, X-Galaxy-Upstream-Status: 200,
         X-Galaxy-Upstream-Headers: base64(json{ "request-id":…, "anthropic-ratelimit-…":… })
Body: 上游响应字节原样（SSE 或 JSON）
→ 200 { "received": 183920 }   或   409 lease_invalid / 410 unit_cancelled
```

- 首个 chunk 到达即视为「首字节」，Hub 把 `X-Galaxy-Upstream-Status` 与白名单头写给消费者并 flush。
- Hub 侧对该 rid 的 `EventWriter` 直接对拷到消费者响应；同时 relay 适配器的 usage 解析器窥探事件。
- 消费者断开 → Hub 以 `410` 结束上行连接并写 `cancel:{rid}`；节点收到 410 立即 abort 上游 fetch。
- 空闲超时：Hub 侧 `streamIdleTimeoutMs`（默认 60s）无字节即判 `node_fault`。
- session / job 原语的 `turn.event` / `progress` 同样可以走本端点（事件为 NDJSON），也可用 2.6 的短请求。

### 2.6 progress / renew

```
POST /agent/v1/units/{id}/progress
{ "lease": "lt_…", "seq": 7, "progress": { "pct": 42, "stage": "render", "previewRef": {…} }, "renew": true }
→ 200 { "cancelRequested": false, "lease": { "expiresAt": … } }
```

频率限制每单元 ≥ 1s 一次；`renew:true` 续租。`cancelRequested:true` 是取消搭车的第二条路径。

### 2.7 complete

```
POST /agent/v1/units/{id}/complete
{ "lease": "lt_…", "state": "completed",                     // completed | failed | cancelled
  "error": null,                                             // { "class": "upstream_fault", "code": "upstream_429", "retryable": true, "message": "…" }
  "outputs": [ { "name": "out.mp4", "ref": {…} } ],
  "usage": { "llm.input_tokens": 1820, "llm.output_tokens": 964, "llm.cache_read_tokens": 1500 },   // 节点自报，对账用
  "contextDelta": { … },                                     // session 用
  "workspaceRef": { "remote": "origin", "branch": "req/…", "sha": "…" },   // session 用
  "checkpointRef": {…},                                      // session 可选
  "ms": 8231 }
→ 200 { "settled": { "llm.output_tokens": 964, "llm.calls": 1, "time.seconds": 9 } }
```

Hub 以自己解析到的 usage 结算；节点 usage 与 Hub 值偏差 > 10% 记 `usage_mismatch` 事件，累计影响信誉。

### 2.8 取消

三条路径，任一先到即生效：`stream` 上行被 410 中断；`heartbeat` / `next` 响应里的 `cancel[]`；`progress` 响应里的 `cancelRequested`。节点收到后 abort provider，并以 `state=cancelled` 调 `complete`。

### 2.9 session / turn 消息

session 原语在同一传输上使用以下 unit 子类型（`unit.primitive = "session"`）：

| 消息 | 方向 | 字段 | 语义 |
|---|---|---|---|
| `session.open` | Hub → 节点（作为 `next` 返回的 unit，`op:"open"`） | sid, kind, contextRef, workspaceRef | 新会话落在此贡献 |
| `session.resume` | 同上，`op:"resume"` | sid, fromSeq, ledgerRef, workspaceRef, checkpointRef? | 跨节点续接 |
| `turn.start` | 同上，`op:"turn"` | sid, seq, input, deadline | 一个回合 |
| `turn.event` | 节点 → Hub（`stream` NDJSON） | sid, seq, event | 文本 / 工具 / 进度 |
| `turn.end` | 节点 → Hub（`complete`） | sid, seq, usage, contextDelta, workspaceRef, checkpointRef? | 回合终态 |
| `session.close` | 双向 | sid, reason | 结束 |

`seq` 单调递增；重复的 `turn.start(seq=n)` 节点返回已有结果不重跑。

## 3. 消费者 API

所有请求带 `Authorization: Bearer sk-…`。Hub 先校验密钥：不存在或已吊销 → `401 key_invalid`；已过期 → `401 key_expired`；余额不足 → `402 insufficient_balance`；kind / provider / 模型不在允许范围 → `403 scope_denied`。响应体形态由适配器决定（relay 返回官方形态；平台原生接口返回 `httpx.JSON` 信封）。

### 3.1 relay（官方 SDK 兼容）

| 路径 | 族 | 说明 |
|---|---|---|
| `POST /v1/messages` `POST /v1/messages/count_tokens` | anthropic | 请求体原样透传；可选头 `x-galaxy-session` |
| `POST /v1/responses` `POST /v1/chat/completions` | openai | `previous_response_id` 触发硬钉 |
| `GET /v1/models` `GET /v1/models/{id}` | 两族共用 | 模型发现。清单由 `galaxy.models` 声明，条目同时带两族字段 |

两族在 P0 同时开放（决策 D-01）。

模型清单是**部署方的对外声明**，不从节点的 `availableModels` 汇总 —— 汇总会随着谁在线而抖动，也把每个提供者的上游情况摊给了所有消费者。它也不参与派单：能不能真派出去仍看各贡献自己的允许/拒绝规则，清单里多写一个没人提供的模型换来的是一次 `no_capacity`。第三方客户端接入时的第一步就是打这条路由，拿不到清单便不让用户往下配。

新版 Codex（app-server / Desktop）是这条路由上的例外：它打的是 `GET /v1/models?client_version=…`，要的是自己那份 model manifest —— 外层键为 `models`，每条除 `slug`、`display_name`、`supported_reasoning_levels`、`shell_type`、`visibility`、`supported_in_api`、`priority`、`support_verbosity`、`truncation_policy`、`experimental_supported_tools` 之外，**还必须带 `base_instructions` 或 `model_messages.instructions_template`**，那是 Codex 的系统提示词，客户端会拿它替换内置的那份。

Hub 默认不接这一路：解析不了的时候 Codex 回落到自己的内置清单与内置提示词，功能是好的，代价只是它每隔几分钟往自己日志里记一次 refresh 失败。部署方配了 `galaxy.codex_manifest`（一份清单文件的路径）才开，开了之后 Hub 从这个文件里挑出 `galaxy.models` 声明过的条目**原样**返回，条目里的字段一个不解读 —— 它们属于 Codex 自己的协议，中间插一层我们的结构体只会把新版本的字段吃掉。这也意味着提示词跟着那份文件走，所以清单得来自可信来源，不能自己编一份填进去。

共享设置里「允许 / 拒绝调用的模型」那两个框的候选项同理，出自**已上架的模型目录**（`GET /provider/model-options`，`zt_galaxy_model` 按厂商分组），不是节点报的 `availableModels`：上游抽一次风那份就空半天（节点侧探测失败会降级成空清单），而主人这会儿填的是一条长期生效的规则。节点报的那份仍然给出去，但只做「这台机器有」的标注 —— 机器上没有也照样能填，一台登录态刚过期的机器不该改写主人的设置。按厂商分组是因为一条车道只吃得下自己那一族：`relay_claude` 的允许名单里填 gpt 是白填。分组键取自贡献视图上的 `category`（claude / codex，和用量分类同一个函数算），两个框收的仍是**通配模式**，所以必须保留自由输入 —— 候选项只是省去手敲。

错误体形态与官方一致（沿用 `RELAY_PATHS` 的 `errorBody`）。Hub 自身错误映射：无候选 `503 no_capacity` + `retry-after`；密钥余额不足 `402 insufficient_balance`；模型不在允许档 `400 model_not_allowed`。

### 3.2 平台原生

| 路径 | 说明 |
|---|---|
| `POST /v1/artifacts` `{ name, size, contentType, kind }` → presigned PUT + ref | 上传输入 |
| `GET /v1/artifacts/{key}` → presigned GET | 下载输出 |
| `POST /v1/delivery/sessions` / `POST /v1/delivery/sessions/{sid}/turns` / `GET …/turns/{seq}/events`（SSE） / `GET …/context` | 任务宇宙 |
| `POST /v1/videofarm/jobs` / `GET …/jobs/{id}` / `POST …/jobs/{id}/cancel` | 视频类 |

### 3.3 控制台接口（`/api/galaxy/*`）

用**用户令牌**鉴权、返回统一信封，和 `/v1/*` 那套按 `sk-` 密钥鉴权的路完全分开：
密钥明文只在签发那一次出现，控制台手里没有、也不该有。服务端按令牌解析出
「这个人名下的密钥 / 贡献集合」再过滤，请求参数只能在这个集合内**收窄**。

两个桌面端各只用其中一半：Nova（贡献端）只打 `provider/*`，Orbit（使用端）只打
`consumer/*`，访问另一端的路由返回 404。

| 路径 | 给谁 | 说明 |
|---|---|---|
| `GET provider/dashboard` | Nova 今天 | 在线状态、本轮连续在线起点、四个积分口径、今日/昨日执行统计、七天趋势。一次查完 —— 这些数字互相解释，分开取会给出对不上的两半 |
| `GET provider/records?paged=1&day&model&state&cid` | Nova 使用记录 | 分页 + **当前筛选条件**下的统计；仍然匿名化（C-12），不含消费者身份与请求内容 |
| `GET provider/ledger?type&offset&limit` | Nova 收益 | 积分账本分页。`settle` 是收益，`payout` 是提现，`clawback` 是争议追回 |
| `GET/POST provider/payouts` | Nova 收益 | 提现申请与列表。金额由服务端按 `galaxy.payout_rate` 折算，请求里只带积分数 |
| `GET consumer/dashboard?days` | Orbit 页头 | 密钥数、按单位合并的余额、今日调用、近 N 天花费、首字延迟 |
| `GET consumer/usage/records?day&keyId&state` | Orbit 使用记录 | 逐笔扣费。`GET consumer/usage` 是同一段时间的汇总，两者粒度不同：汇总回答「这个月花了多少」，逐笔回答「那一次为什么扣了这么多」，申诉从后者进去。**失败的单元不进这张表**（含 `total`）—— 失败不扣费，摆在扣费明细里只会让人怀疑那次扣没扣；失败次数由 `consumer/dashboard` 报 |

`day` 是服务端算的时间窗（`today` / `yesterday` / `7d` / `30d` / `YYYY-MM-DD`），
不接受前端传来的 from/to：跨零点那一刻两边的「今天」会差一天，而同一页上的
统计数字和列表行数必须是同一个口径。

## 4. 放置算法

### 4.1 输入

`RouteKey`（适配器 `Route()` 产出）、`KindSpec`、贡献内存快照（由心跳维护，字段见 Redis `contrib:{cid}`）。

### 4.2 步骤

```
1  if hardPin != "" :                                   // Responses 链式 / session 硬亲和
       cid = hardPin; 若贡献不在线 → 返回 error(node_unavailable, 不改派)；否则 goto 6
2  cid = GET bind:{consumerKey}:{lane}                  // lane = kind|provider
   if cid != nil && healthy(cid) && !draining(cid) && quotaOK(cid, estimate) && inflight<conc:
       goto 6                                           // 90% 路径
   if cid != nil && affinity == soft && busy(cid):
       等待 spillWaitMs；期间有槽 → goto 6；否则本次溢出，不改绑定，继续 3
3  候选 = 硬过滤(所有贡献):
       kind/version 支持 ∧ provider 匹配 ∧ model ∈ allow ∖ deny ∧ online ∧ now ≥ throttledUntil
       ∧ 上游余量高于主人划的线（upstreamLeft_w > floor_w，观测缺失视为通过）
       ∧ !draining ∧ schedule 内 ∧ seatsUsed < seatsEff ∧ ∀d∈units: quotaLeft_d > reserve_d + estimate_d
       ∧ inflight < conc ∧ 资源需求满足(job)
4  if 候选 = ∅ : ZADD q:wait rid score=deadline；等待 ≤ maxWaitMs 被心跳唤醒重试；超时 503 不计费
5  cid = argmax score(候选)；平手取 lastBoundAt 最早
6  Lua 原子: 校验座位/余量 → SADD node:seats SET bind(TTL) HINCRBY contrib.inflight
            HINCRBY quota 预留 → LPUSH q:contrib:{cid} → SET req:{rid} 字段
   失败(被抢) → 回到 3 重选（最多 3 次）
```

### 4.3 有效座位数

```
burn_d(cid)   = 该贡献最近 1h 每座位维度 d 的平均消耗率；样本不足用同 kind 全池均值
hoursLeft     = 当前窗口剩余小时数（按该维度的窗口）
seatsEff = min( seats,
                ⌊ quotaLeft_tok   / max(ε, burn_tok   × hoursLeft) ⌋,
                ⌊ quotaLeft_calls / max(ε, burn_calls × hoursLeft) ⌋,
                quotaLeft_sec ≥ minSessionSec ? seats : 0 )
∃d: quotaLeft_d < reserve_d  ⇒ seatsEff = 0
```

### 4.4 打分

```
score = w1·(1 − seatsUsed/seatsEff)                  空座位多            w1=0.30
      + w2·min_d(quotaLeft_d / windowLimit_d)         余量短板厚          w2=0.25
      + w3·(1 − inflight/conc)                        当前空闲            w3=0.20
      + w4·latencyScore(p50 首字节, 归一到 0..1)      快                  w4=0.10
      + w5·reputation(0..1)                           靠谱                w5=0.10
      + w6·localityHit(inputs ∩ cachedArtifacts)      数据引力(job)       w6=0.05
```

权重可配；relay 把 w6 置 0，job 把 w1 置 0。

### 4.5 亲和与迁移

| 原语 | 绑定 | 忙时 | 节点掉线 | 额度将尽 |
|---|---|---|---|---|
| relay | 软，`bindIdleTTL` 续期 | 等 `spillWaitMs` 后溢出一次，不改绑定 | 解绑，下次重放置 | 贡献 draining，新请求重放置 |
| session | 硬，随 sid | 排队不溢出 | `migrating` → 选新贡献 → `session.resume` | draining，在两次回合之间迁移 |
| job | 无 | 任意候选 | 租约过期 → attempt+1 重派 | 不派新 job |

## 5. 额度引擎

### 5.1 单位注册表

```
llm.input_tokens  llm.output_tokens  llm.cache_read_tokens  llm.cache_write_tokens  llm.calls
time.seconds
video.output_seconds  video.input_seconds  video.frames
gpu.seconds  cpu.seconds
storage.bytes  egress.bytes
```

每个单位声明：可信来源（hub | stream | node）、聚合方式（sum）、展示精度。

### 5.2 授权与窗口

授权行 `(cid, unit, limit, window, resetAt)`。`windowKey` 计算：`day` → `YYYYMMDD`（按 resetAt 时区偏移），`week` → ISO 周，`month` → `YYYYMM`，`total` → 常量 `all`。Redis 计数器 `quota:{cid}:{unit}:{windowKey}` 的 expire 对齐窗口末尾 + 1 天（对账余量）。

### 5.3 预留—结算

```
reserve(cid, estimate):  Lua 内对每个 unit: cur + reserved + est ≤ limit ? INCRBY reserved est : 全部回滚并失败
settle(cid, actual):     INCRBY used actual；DECRBY reserved est；记 meter_record
expire(rid):             DECRBY reserved est（租约过期、改派、取消未开始时）
```

`used` 与 `reserved` 分开存（`quota:{cid}:{unit}:{w}:used` / `:reserved`），余量 = `limit − used − reserved`。MySQL `zt_galaxy_quota_window` 每分钟从 Redis 快照，对账以 `meter_record` 求和为准。

### 5.4 阈值与摘除

`used/limit ≥ 0.8` 触发 `quota_warn` 事件通知主人；`≥ 1.0` 或余量 `< reserve_d` 时贡献 `draining`；窗口翻转后自动恢复。

### 5.5 estimate 规则

| kind | estimate |
|---|---|
| llm.chat | `llm.output_tokens = max_tokens ?? 4096`，`llm.input_tokens = ⌈bodyBytes/3⌉`，`llm.calls = 1`，`time.seconds = 120` |
| delivery.task | 按该 phase 最近 100 回合的 p90 |
| video.edit.render | `video.output_seconds` = timeline 时长，`cpu.seconds` = 时长 × 分辨率系数 |

## 6. 计量与结算

### 6.1 平台侧 usage 解析（relay）

Hub 在对拷时以 SSE 解析器窥探事件，不修改字节：

| 族 | 事件 | 取值 |
|---|---|---|
| anthropic | `message_start.message.usage` | input_tokens、cache_creation_input_tokens、cache_read_input_tokens |
| anthropic | `message_delta.usage` | output_tokens（累计值取最后一次） |
| anthropic 非流式 | 响应 JSON `usage` | 同上 |
| openai responses | `response.completed.response.usage` | input_tokens、output_tokens、input_tokens_details.cached_tokens |
| openai chat | `chunk.usage`（需 `stream_options.include_usage`；缺失时 Hub 注入该选项并在写回时剥掉多出的最后一个 chunk） | prompt_tokens、completion_tokens |

`llm.calls` 由 Hub 计 1；`time.seconds` = 首字节前从 `placed` 起、其后到 `complete` 的总时长，向上取整秒。解析失败（上游格式变化）记 `usage_parse_failed`，回退到节点自报并标记待审。

### 6.2 失败语义

| 情况 | 改派 | 消费者计费 | 提供者贡献 | 信誉 |
|---|---|---|---|---|
| 首字节前节点报错 / 掉线 / 租约过期 | 是（≤ maxAttempts） | 否 | 否 | node_fault 扣 |
| 首字节后节点掉线 | 否，502 | 否（默认全免，可配按已产出） | 否 | 扣 |
| 消费者主动断开 | 否 | 按已产出 usage | 按已产出 | 无 |
| 上游 429 / 5xx | 是，且该贡献 `throttledUntil` | 否 | 否 | 无 |
| 输入非法 / 内容违规 | 否，4xx | 否 | 否 | 消费者扣 |
| 排队超时 | — | 否 | — | — |
| 抽检判定伪造 | — | 追回 | 追回 + 封禁 | 清零 |

上表第一行的前提是「Hub 知道节点掉线了」，而这件事没有想象中自然：relay 的消费者连接
同步挂在 Hub 上等回传，节点消失时不会有任何人来收尾 —— 进程被 kill 既不产生上行的 EOF，
也不会有 complete。三道时限负责把这种局面收口：

| 时限 | 覆盖的窗口 | 判定 |
|---|---|---|
| `attachTimeoutMs` | 派单之后一直没有节点认领上行：单元还在队列里没人领，或者领走它的机器在打上游的路上挂了 | `node_offline`，首字节前可改派 |
| `nodeProbeIntervalMs` | 已认领上行、但首字节之前心跳断了（断网、断电这类连 TCP 都不会断的走法） | `node_offline`，首字节前可改派 |
| `lease.maxRunSec` | 以上都没触发的残局 | `lease_expired`，不改派 |

心跳探测在首字节之后同样有效，和 `streamIdleTimeoutMs` 并行，谁先发现算谁：
进程被 kill 时 TCP 立刻报错，比心跳快得多；而断电、拔网线、休眠这类走法根本不产生 FIN，
连接就那么半开着 —— 那时候上行的读是最慢的一条证据，反倒要靠心跳先说话。
两者分工也因此清楚了：心跳回答「机器还在不在」，`streamIdleTimeoutMs` 回答
「机器在、但这条流哑太久了」，后者的阈值该设多少由 `galaxy_stream_gap_ms` 的分布决定（14 节）。

三道时限触发时 Hub 要自己补一次 `FailUnit` ——
节点侧不会再有终态上报，预留的额度与并发只能由 Hub 还回去，
否则那台机器每失联一次就永久少一个并发位。

节点侧对应地在退出时主动为在跑的单元报一次 `node_shutdown`（可改派）。
时限是给崩溃与断电兜底的，而重启 Nova 这种最常见的情形不该让消费者等满一个时限。

### 6.3 双账本

```
consumer_ledger   (keyId, txnId, type: topup|reserve|settle|refund|expire, unit, amount, price, balanceAfter, rid)
provider_ledger   (cid, txnId, type: contribute|settle|payout|clawback, unit, amount, price, rid)
platform_ledger   (txnId, type: fee|baddebt, amount, rid)
```

结算幂等键 `rid + attempt`。定价表 `zt_galaxy_price (kind, modelId, unit, price, providerPrice, currency, effectiveFrom)`。

**中转站定价（决策 D-02 / D-03）**：`llm.chat` 按 token 计价，四个 token 桶互不重叠 —— `llm.input_tokens`（未命中缓存的新增输入）、`llm.output_tokens`、`llm.cache_read_tokens`、`llm.cache_write_tokens` 各有自己的单价；`llm.calls` 与 `time.seconds` 不计价，只作供给侧额度与统计。其他 kind 的定价待各业务定义（O-01）。**不计价的行不进使用端的账单汇总**（`GET consumer/usage`）—— 那张表每一行都该是一笔钱，判据是有没有单价而不是这一行收了多少（小额向下取整成 0 的仍是计价行）；它们的量在逐笔明细里照旧看得到，运营后台 `AdminUsage` 与 `hub /usage` 仍然全量返回。

**上下游各自定价（决策 D-04 修订，2026-09-19）**：一行价有两个数 —— `price` 向使用者收，`providerPrice` 结给共享者，差额记平台 `fee`。两个数**互不推导**：

- 调对外价不再自动改所有共享者的收入。想给使用者降价，不必同时砍掉供给侧。
- 共享者看不到抽成。供给侧账本那一列记的是 `providerPrice`，不是对外价 —— 原先记的是对外价，拿它和 `amount` 一除就是抽成比例。共享端界面也不再写「70% 归你、平台留 30%」。
- `providerPrice` 高过 `price` 是合法配置（定向补贴），平台那一笔记成负的 `fee`，三本账照样对得平。
- `provider_share` 是老口径，只在 `providerPrice` 为 0 的存量行上回落，迁移脚本 `20260919_galaxy_provider_price.sql` 跑完就不再走到。

**按模型定价（2026-09-19）**：单价的维度是 `kind × 模型 × 单位`。`modelId` 空串是**该 kind 的兜底价**，不是「一个叫空串的模型」：

- 取价先找这个模型自己的行，**按单位**找不到才回落到兜底行。只给 `output` 定了模型价，`input` 仍然走兜底 —— 按行回落会让只填一档的模型把其余几档静默归零。
- 兜底行是硬要求：某个单位连兜底价都没有，那个单位就查不到价，而查不到价是**静默算 0**，不报错。「有量无价」那张告警因此只认兜底行，模型行消不掉它。
- 门户卡片上的价同样按模型回落。回落到兜底行才标「统一价」（`Priced = false`）；回落到模型自己的计价行时，卡片上那个数就是它真会被收的价。
- 账单（`UsageReport`）按模型分行。合并成一行的话，那一行的 `unitPrice` 只能是几个模型里随便一个的价。

在这之前整张表只按 kind 定价：opus 和 haiku 都是 `llm.chat`，同样一百万 token 结给共享者的钱一模一样，而门户上两者标价能差几十倍 —— 平台毛利随使用者调哪个模型漂移，且没有任何地方拦得住。

**模型分组：平台在卖的那个单位（2026-09-22）**

分组是**模型底下的一层**：同一个模型可以卖成「标准」「深度」「快速」几个档次，价挂在分组上，
中转、鉴权、派单都以它为单位。

| 挂在分组上的 | 含义 |
|---|---|
| 价 | `zt_galaxy_price.group_id`，含对外价与结算价。空串是**这个模型的通价**，没单独定价的分组按它算 |
| 推理强度档位 | `efforts_json`，这个分组卖哪几档。空数组 = 不限 |
| 快速 | `allow_fast`，卖不卖快速通道 |

三条硬规则：

- **取价三级回落**：`kind 兜底 → 模型通价 → 分组价`，由粗到细逐层盖，每一层**按单位**分别盖。
  分组只给 `output` 定了价，`input` 仍然走模型通价 —— 按行回落会让只填一格的分组把其余几格静默归零。
- **密钥选中分组才签得出来**（`CreateConsumerKey`）。一个模型只能选一个分组：一次请求只认模型，
  选两个就回答不了「按哪份价收」。存量密钥（`groups_json` 为空）落在各模型的默认分组上，
  这是迁移期的退路，不是常态。
- **共享者加入分组才接得到那个分组的单**（`zt_galaxy_contribution.groups_json`，派单硬过滤）。
  名单为空是**不限**，不是「都不接」—— 把「不知道」当成「不接」，迁移那一刻全网机器会一起掉出候选，
  而界面上每台都还显示着共享中。

**推理强度与快速：从请求体收进分组（2026-09-22）**

这两个旋钮原先由客户端在请求体里自己拨（`output_config.effort` / `reasoning.effort`、`service_tier`），
而它们直接换算成钱：深档一次请求烧掉的推理 token 比浅档多一个量级，快速档上游自己就按更贵的价收。
拨旋钮的是客户端内置的默认值（Claude Code 默认 high，Codex 默认 medium），不是买单的人做的选择 ——
平台按一份价收、上游按另一份价扣，差额全由平台垫。

收进分组之后，**一切按分组的属性决策**（`contract.GroupPolicy.Apply`，Hub 在鉴权之后、构造单元之前执行）：

| 请求带来的 | 分组卖 | 结果 |
|---|---|---|
| 强度不在档位表里 | 有档位表 | 夹到表里**最浅**的一档，并改写请求体 |
| 强度在表里，或表为空 | — | 原样透传，一个字节都不动 |
| `service_tier: priority` | 不卖快速 | 改写成该族的普通档（Claude `standard_only` / Codex `default`），这一次不算快速 |

两个要点：

- **夹而不是拒绝**。客户端的默认档是它自己内置的，拒绝的话使用者既看不懂也改不了，
  而他的每一次请求都是 400。
- **必须真的改写请求体**，不能只改记账：上游照着请求体里那一档跑，平台按分组卖的浅档收钱，
  两边都不报错，对账也发现不了（两头记的是同一个错档）。老模型（只有 `thinking.budget_tokens`）
  改回的是**预算**而不是塞一个它不认识的 `output_config`。

**档位名一律不对外**。它是上游的内部刻度（`low…max` / `minimal…ultra`），
摆到使用端、共享端、官网上，等于让上游的字段名替平台解释自己在卖什么；上游换一次词表，
三个端的文案一起失效。只有管理端在「绑定强度」那个多选里出现档位名。
单元行上仍然记 `effort`（上游这一次实际按哪档跑的），那是事实记录，排障与争议裁决要它。

**三个端看到三份不同的价（2026-09-19）**：同一张 `zt_galaxy_price`，三个端各取自己那一半：

| 端 | 看得到 | 在哪 |
|---|---|---|
| 管理端 | 对外单价 + 结算单价 + 平台毛利 | 共享算力池 → 价目表 |
| 使用端 Orbit | 对外单价（模型广场、账单、套餐售价） | `/consumer/models`、`/consumer/usage`、`/consumer/store` |
| 共享端 Nova | **只有结算单价** | `/provider/models` |

共享端那一页（`ProviderModels`）刻意不带对外价，也不带毛利：两个数一相除就是平台抽成，而抽成不是共享者要做的决定。他要做的决定是「开放哪些模型」，那只需要三样东西 —— 跑它记多少积分、自己的名单放不放它过、机器上有没有它。后两件事**分开显示**：允许了但上游没有，照样一单都接不到，而那不是设置错了。收益按模型归集要 join 回 `zt_galaxy_unit`（模型只记在单元行上，账本里没有），单元行已清的归进空串那一组 —— 丢掉它们会让这一页的合计比收益页少一截。

**提供者收益（决策 D-04）**：以平台积分记账，`provider_ledger.unit = credit`，`credit_account` 持有余额。P1 前消费侧金额只记账不扣款。

**提现**：申请单独一张表 `payout`，账本上只在**受理**那一刻记一笔 `payout` 流水。
账本只前进不回退，而提现在钱真的打出去之前还有一段人工过程（待打款 / 驳回 / 重试）；
把这段状态塞进账本会让账本变得可修改，就对不平了。受理时先条件扣积分
（`balance >= amount`）再建单：反过来做，两步之间进程挂掉就会留下一张已受理却
没扣过账的单子。驳回时反向记一笔把积分还回账户，而不是删掉原来那笔 ——
删了就对不出「这笔钱申请过又退回来了」。

可提现 = 账户余额 − 争议期（`galaxy.payout_hold_days`，默认 7 天）内刚结算的部分。
争议期内的积分留在余额里（它确实是这个人的）但提不出来：一旦争议成立要原路追回，
钱已经打出去就追不回来了。

### 11.3 运行循环

```
启动: 读 token → probe() → 加载贡献对应 provider（未贡献的不 import）→ hello
主循环（每贡献一个 lane worker，共享一个 next 长轮询）:
  lanes = 有空位的贡献 → GET next → unit
  白名单校验: unit.kind/provider/model ∈ 该贡献申报范围 且 contract/*.schema 校验通过，否则 complete(failed, capability_mismatch)
  gate.acquire(provider=cid, principal=unit.consumerKey, limit=seatConcurrency)
  provider.run(unit) → 事件 → stream 上行 / progress / complete
心跳线程: 每 15s heartbeat，处理响应里的 cancel / drain / quotaUpdate
贡献变更: 重新 hello（全量替换）；被停的贡献 draining，等在途完成后释放
断线: 指数退避 1s→30s + 抖动；重连后 hello；在途单元一律作废（complete 不可达则由 Hub 租约过期处理）
```

### 11.4 安全

- token 明文只在内存；日志只记 requestId / cid，不记内容与凭据。
- `job-local` / `agent-local` provider 只在贡献明确启用时加载；执行目录为临时 worktree，禁用主人 git 凭据；`complete` 后删除。
- 凭据失效（`credentials.resolve()` 抛错）→ 该贡献 `upstreamOK=false`，随心跳上报。

## 13. 安全设计

| 项 | 设计 |
|---|---|
| 消费者密钥 | `sk-` 前缀 + 32 字节随机；Hub 存 sha256；购买后签发，默认有效期 30 天；到期进入冻结期 30 天，可续期换发（余额转入新密钥）；每密钥并发与 RPM；允许的 kind / provider / 模型档 |
| 同意记录 | 提供者：配对码签发与 `pair` 双重校验当前条款版本的同意记录；消费者：密钥签发时记录数据告知版本与确认时间；条款升版后旧同意失效，提供者下次 hello 被要求重新同意 |
| 节点令牌 | 配对码一次性、10 分钟；token 32 字节随机，sha256 存库；撤销即 401，节点停止重试 |
| presigned | 单 key、PUT 限 `Content-Length`、TTL 15 分钟；GET TTL 1 小时；对象键不含身份 |
| 白名单 | Hub 放置过滤 + 节点收单校验双重 |
| 内容策略 | 适配器 `Parse` 后、放置前执行；命中 `content_policy` 不派单 |
| 抽检 | 每贡献每日随机 ≤ 1% 请求以 Hub 自有账号影子重放，比对结构相似度；低于阈值记 `audit_probe`，累计两次摘除 |
| 匿名 | `consumerKey` 为密钥的匿名标识；节点日志与心跳不含消费者信息 |
| 传输 | 全部 HTTPS；节点校验 Hub 证书；`streamURL` 内网地址仅在 Hub 多实例部署时可达节点（经内网网关） |

| `galaxy_usage_mismatch_total` | cid |

`galaxy_stream_gap_ms` 记的是一次上行里**最长的一段静默**，含「上游给了响应头之后隔多久吐出第一个字节」那一段。
它是 `streamIdleTimeoutMs` 该设多少的唯一依据：那个阈值要盖住正常请求的静默上限，
没有这条分布，调它就只能在「放太松、节点断网要等满一分钟」和「调太紧、开始误杀慢上游」之间猜。
故意不带维度 —— 要回答的是「阈值该设多少」，那是一个全局问题；定位具体某台机器慢看日志。

日志字段：requestId（消费者 ← Hub ← 节点三段同一值）、unitId、kind、provider、cid、keyAlias、state、ms。不记 body、不记 token、不记凭据。审计表：贡献变更、封禁、结算、争议。

## 16. 测试策略

- **契约双端测试**：`galaxy/business/*/contract/fixtures/` 的输入样例同时跑 Go（jsonschema）与 TS（ajv），CI 要求两侧结果一致。
- **usage golden**：用真实抓包的 Anthropic / OpenAI SSE 流作为 golden，`ExtractUsage` 输出必须与流内 usage 相等；上游格式升级时先补 golden。
- **放置单测**：Lua 脚本用 miniredis；并发抢座位、余量边界、窗口翻转、溢出与硬钉用例。
- **失败语义集成测试**：模拟节点在首字节前 / 后掉线、消费者断开、上游 429，验证改派、计费、信誉。
- **节点侧**：pool 模式不监听端口（`lsof` 断言）；白名单校验拒绝错派单元；断线重连后在途作废。
- **端到端**：官方 SDK → Hub → 节点 → 模拟上游，响应字节与直连逐字节比对（除限流头值）。
