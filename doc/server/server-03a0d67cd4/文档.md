# 构建 `server/web-api` Docker 镜像与运行配置

## 1. 任务目标

为 `server/web-api` 提供可在 Docker 中构建和启动的运行形态，使聚合 HTTP 服务能在 Go 多模块 `go.work` 布局下稳定编译，并在容器运行时通过环境变量注入监听地址和外部连接配置。镜像不得固化当前 `configs/application.properties` 中的数据库、Redis 或第三方服务实际连接信息。

本任务产物服务于后续部署，不改变 HTTP 路由、业务装配、数据库表结构或鉴权策略。

## 2. 已核对现状

### 2.1 模块与构建关系

- 工作区根为 `server/`，`server/go.work` 使用 Go 1.21，纳入 `common`、`contract`、`delivery-api`、`service`、`web-api` 五个模块。
- `web-api/go.mod` 通过相对 `replace` 引用相邻的 `common`、`contract`、`service`、`delivery-api`。本地 `build.sh` 在 `server/web-api` 中使用 `GOWORK=off go build -o bin/web-api .`，依赖这些相对路径仍然可达。
- 因此 Docker 构建上下文必须是 `server/`，不能只将 `server/web-api` 作为上下文。建议 Dockerfile 存放在 `server/web-api/Dockerfile`，构建命令使用 `docker build -f web-api/Dockerfile -t universe-web-api .`（在 `server/` 目录执行）。与构建上下文匹配的忽略文件应为 `server/.dockerignore`。

### 2.2 当前启动与配置行为

- `web-api/main.go` 先执行 `httpx.Boot("web-api")`，再启动 Gin；`/healthz` 已由路由提供，可作为 Docker 健康检查入口。
- 当前监听地址优先级为 `WEB_API_ADDR` > `application.properties` 的 `server.address` > `:10001`；本地 `start.sh` 使用相同规则探测端口。
- `httpx.Boot` 固定读取工作目录下的 `configs/application.properties`，从 `sqlconn` 建立 MySQL 连接；配置文件缺失或 `sqlconn` 为空会直接启动失败。
- Redis、LLM 和部分第三方服务配置目前保留在 `application.properties`，当前代码对其中大部分尚无读取点；本次不应无依据地改变其业务接入逻辑。
- 当前配置文件包含实际或疑似实际的连接端点与敏感值，Docker 构建过程不得将其复制进最终运行镜像，也不得在文档、示例命令或 Dockerfile 中重复这些值。

### 2.3 参考项目结论

- 指定参考目录的 `build.sh` 与当前 `server/web-api/build.sh` 一致，均采用 `GOWORK=off` 编译当前模块。
- 参考 `start.sh` 同样通过 `WEB_API_ADDR` 覆盖 `server.address` 并轮询 `/healthz`；当前项目的脚本已在端口占用提示上做了更细化处理。
- 参考 `application.properties` 使用 `server.port`，而当前 `main.go` 与 `start.sh` 实际读取的是 `server.address`。容器实现必须以当前代码契约 `WEB_API_ADDR` / `server.address` 为准，不能恢复使用未被读取的 `server.port`。

## 3. 实现范围

### 3.1 必须新增或修改的文件

1. `server/web-api/Dockerfile`
   - 使用多阶段构建：Go 1.21 构建阶段和精简运行阶段。
   - 构建阶段以 `/src`（或等效目录）保留 `common`、`contract`、`delivery-api`、`service`、`web-api` 的相对目录关系；先复制各 `go.mod` / `go.sum` 下载依赖，再复制源码并执行 `GOWORK=off go build`。
   - 为 Linux 容器生成 `web-api` 二进制；建议关闭 CGO，运行镜像使用非 root 用户。
   - 最终镜像只包含运行二进制、容器启动脚本及无敏感默认值的运行配置模板（若采用模板方案），不得包含源码、Go 工具链、`bin/`、`logs/`、`run/` 或真实 `application.properties`。
   - 声明服务监听端口 `10001`（`EXPOSE 10001`），实际端口可由运行时 `WEB_API_ADDR` 覆盖。
   - 使用 `HEALTHCHECK` 请求 `http://127.0.0.1:<容器端口>/healthz`；运行镜像须提供健康检查所需的最小 HTTP 客户端，或由启动脚本提供等效且可执行的检查方式。

2. `server/.dockerignore`
   - 以 `server/` 为 Docker 上下文设置白名单或等效严格规则，只保留构建 `web-api` 所需的五个模块、`go.work` 与必要模块文件。
   - 排除 `.git`、编辑器文件、测试/覆盖率产物、`bin/`、`logs/`、`run/`、本地配置文件、密钥和其他不参与本镜像构建的服务目录。
   - 若需要在镜像中保留配置样例，使用独立的无敏感模板文件；不得通过取消忽略真实 `web-api/configs/application.properties` 来实现。

3. `server/web-api` 的容器启动配置（文件名由实现确定，如 `docker-entrypoint.sh`、`configs/application.docker.properties` 或 `.env.example`）
   - 容器以前台进程方式启动二进制，不复用本地 `start.sh` 的 `nohup`、PID 文件、端口探测和日志重定向逻辑。
   - 在执行二进制前生成或选择运行配置，确保工作目录内存在 `configs/application.properties`，以满足 `httpx.Boot` 的现有固定路径。
   - 对配置采用“环境变量优先、无敏感默认值”的规则：至少支持 `WEB_API_ADDR` 和数据库 DSN 环境变量（建议名称 `WEB_API_SQLCONN`）覆盖；启动时数据库 DSN 缺失应输出明确错误并以非零状态退出。
   - 容器内默认监听地址为 `:10001`。`WEB_API_ADDR` 允许覆盖端口或绑定地址；当端口改变时，部署侧必须同步调整端口映射和健康检查配置。
   - 可为今后已接入的 Redis/外部服务预留无敏感的环境变量映射，但不能要求尚未被当前代码使用的变量，也不得把敏感配置写入镜像层。

4. 视实现需要修改 `server/common/middleware/httpx/httpx.go`
   - 若只靠入口脚本无法满足“服务从容器环境读取连接与监听配置”，应在配置加载后对允许的环境变量覆盖配置键，至少覆盖 `sqlconn`；监听地址继续由 `main.go` 的 `WEB_API_ADDR` 读取。
   - 环境变量覆盖必须保持本地开发兼容：未设置环境变量时继续读取现有 `configs/application.properties`，不改变调用 `httpx.Property` 的模块边界。
   - 不得将配置读取逻辑扩散到领域包；配置仅保留在 `main` / `common/middleware/httpx` 等装配和基础设施层。

## 4. 配置契约

| 用途 | 环境变量 | 配置键 | 优先级与要求 |
| --- | --- | --- | --- |
| HTTP 监听地址 | `WEB_API_ADDR` | `server.address` | 环境变量优先；容器默认 `:10001`。 |
| MySQL 连接 DSN | `WEB_API_SQLCONN` | `sqlconn` | 环境变量优先；容器运行时必须提供，缺失即失败。 |
| Redis 地址（预留） | `WEB_API_REDIS_ADDR` | `redis.addr` | 仅在实现配置通用覆盖时映射；不改变当前未接入逻辑。 |
| Redis 密码（预留） | `WEB_API_REDIS_PASSWORD` | `redis.password` | 仅运行时注入，禁止写入镜像。 |
| Redis 模式（预留） | `WEB_API_REDIS_MODE` | `redis.mode` | 可选，无值时沿用配置模板。 |

配置模板仅提供键名、空值或安全的本地占位说明；真实凭证通过容器编排平台的 Secret、环境变量或挂载文件注入。不要提交 `.env`、生产 DSN、密码、令牌或私有网络地址。

## 5. 非目标与约束

- 不新增 Docker Compose、Kubernetes 清单、CI 发布流水线或镜像仓库推送配置，除非后续任务明确要求。
- 不修改 `build.sh`、`start.sh`、`stop.sh` 的本地开发行为；容器启动使用独立前台入口。
- 不修复当前项目其他尚未完成模块或其整体 `go build` 问题；本任务只保证构建 `web-api` 所需的模块闭环。
- 不更改端口为参考项目旧的 `8091`，也不将 `server.port` 作为新的运行契约。
- 不在构建日志、Dockerfile 参数默认值或说明文档中输出敏感连接值。

## 6. 验收标准

1. 在 `server/` 目录执行 `docker build -f web-api/Dockerfile -t universe-web-api .` 能成功完成多阶段构建，且构建上下文不需要复制整个仓库。
2. 使用有效的 `WEB_API_SQLCONN` 和可选的 `WEB_API_ADDR` 启动容器后，进程保持前台运行；服务在映射端口的 `/healthz` 返回成功。
3. `WEB_API_ADDR=:10001` 时，容器以 `10001` 提供服务；未传该变量时同样使用容器默认 `:10001`。
4. 未提供数据库 DSN 时，容器启动明确失败，错误信息指出缺少的环境变量或配置项；不得在运行时静默连接构建时写入的 DSN。
5. 最终镜像中不存在真实 `configs/application.properties`、源码、Go 编译工具链、`bin/`、`logs/`、`run/` 及敏感环境文件。
6. 不设置容器环境变量时，本地从 `server/web-api` 运行既有 `build.sh` / `start.sh` 的配置优先级不发生回归。

## 7. 建议验证步骤

```bash
# 在 server/ 下构建；WEB_API 的相邻模块必须在此上下文内。
docker build -f web-api/Dockerfile -t universe-web-api .

# 用部署平台提供的安全 DSN 替换 <mysql-dsn>，不要将真实值写入命令历史或文档。
docker run --rm -p 10001:10001 \
  -e WEB_API_SQLCONN='<mysql-dsn>' \
  -e WEB_API_ADDR=':10001' \
  universe-web-api

curl -fsS http://127.0.0.1:10001/healthz

# 验证缺失连接配置会失败。
docker run --rm universe-web-api
```

## 8. 交付边界结论

后续实现应优先采用“`server/` 构建上下文 + `web-api/Dockerfile` + `server/.dockerignore` + 独立前台 entrypoint + 环境变量覆盖配置”的组合。该方案既保持多模块相对 `replace` 可解析，也避免将当前本地 `application.properties` 的敏感配置带入镜像，并与现有 `WEB_API_ADDR` 监听优先级兼容。
